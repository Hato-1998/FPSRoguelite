## 1. 넣을 파일 (§7 크롭 완료본)

전부 `Docs/Handoff/PlayerChar_Arcade/` 에 있다. 1024×1024, 인물 높이 = 캔버스 88%(900px),
세 장 **같은 배율·같은 발높이**, 배경 투명(RGBA).

| 파일 | 뷰 | 비고 |
|---|---|---|
| `PlayerCharArcade_front.png` | 정면 | 원본 = `sd_out/v19_fullclosed_*` |
| `PlayerCharArcade_side.png`  | 측면 | **왼쪽 향함**(= 캐릭터의 좌측면). 원본 = `sd_out/v26_side_goggles_*` |
| `PlayerCharArcade_back.png`  | 후면 | 원본 = `sd_out/v28_back_hem_*` |

배경이 투명이라 툴의 자동 배경제거를 아예 안 거친다. **투명 PNG 를 거부하는 경우에만**
같은 폴더의 `*_ongrey.png`(어두운 회색 배경 합성본)를 쓴다.
🔴 밝은 배경본은 만들지 않았다 — 의상이 오프화이트라 밝은 배경에서는 실루엣 대비가 없다.

🔴 **한 장에 세 뷰가 나란한 "삼면도 시트"는 만들지 않았고, 만들면 안 된다.** 그런 시트를
   단일 이미지 모드에 넣으면 캐릭터 셋을 만들거나 납작한 부조가 나온다. 다시점 모드는
   **뷰당 낱장 파일**을 받는다 — 위 3장이 그 형태다.

## 2. 두 번 돌린다 (A/B) — 어느 쪽이 나은지 아직 모른다

다시점이 단일 이미지보다 낫다는 건 **일치가 완벽할 때** 성립한다. 우리 3장은 "같은 캐릭터"
까지는 왔지만 직교 투영이 아니고 뷰 간 재킷 볼륨이 다르다. 반대로 이 캐릭터는 좌우 대칭 +
완전 봉쇄 재킷 + 3색이라 정면 한 장만으로도 추론 여지가 크다. **재 보는 게 싸다.**

| 갈래 | 스킬 | 입력 |
|---|---|---|
| **A** | `이미지→3D` | `PlayerCharArcade_front.png` **한 장만** |
| **B** | `멀티뷰를 3D로` | 위 3장 전부(front / side / back 슬롯에 각각) |

같은 프롬프트로 두 번. 결과를 나란히 놓고 §5 로 판정한다.
※ 2026-09-08 시점 배너에 "3D Agent 이벤트 — 모든 프리미엄 기능 잠금 해제"가 떠 있어
  `멀티뷰를 3D로`(유료 표시)가 열려 있다. **이 창이 닫히기 전에 B 를 돌려 둘 것.**

## 3. 프롬프트

이미지가 형태를 정하고, 텍스트는 **재질·색·금지사항**을 잡는다. 형태를 텍스트로 다시 설명하려
들면 이미지와 싸운다 — 아래는 그래서 재질·색 위주다.

### 3-1. 영문 (정본 — 이걸 넣는다)
```
Stylized chibi game character. Flat solid colors, hard-edged cel shading, crisp
outlines. No gradients, no photographic texture, no noise, no grunge, no wear.

Strictly three colors: off-white, near-black, and sky blue.
No orange, no red, no magenta, no pink, no green, no purple. No pure white, no pure black.

Closed oversized long jacket covering torso and hips, high standing collar,
black centre zip line, glowing sky-blue band along the hem. Black leggings.
Chunky platform sneakers, sky-blue trim, dark soles. Light blue bob hair with
blunt bangs. Sky-blue tinted goggles over the eyes, over-ear headphones.

Left-right symmetrical. A-pose, arms slightly away from the body, empty hands.
Simple readable silhouette, chunky rounded forms, no thin parts.

No weapons, no accessories, no belt, no straps, no pouches, no bag, no gloves,
no text, no logo, no base, no stand.
```

### 3-2. 짧은 판 (입력 길이 제한에 걸리면)
```
Chibi game character, flat solid colors, hard cel shading, no texture, no gradient.
Only off-white, near-black and sky blue - no orange, red, magenta, pure white or pure black.
Closed oversized long white jacket with glowing sky-blue hem band, black leggings,
chunky sneakers, light blue bob hair, sky-blue goggles and headphones.
Symmetrical, A-pose, no accessories, no weapons, no base.
```

### 3-3. 한국어 참고 (넣지 말 것 — 대조용)
평면 단색 + 하드 셀셰이딩, 그라디언트·텍스처·노이즈 없음. 색은 오프화이트/거의 검정/하늘색
**3색만** — 주황·빨강·마젠타 금지(적 예약 대역), 순백·순흑 금지. 완전히 잠긴 오버사이즈 롱
재킷(높은 스탠딩 칼라, 중앙 검정 지퍼선, 밑단 하늘색 발광 띠) + 검정 레깅스 + 청키 플랫폼
스니커즈. 하늘색 보브 + 일자 앞머리, 하늘색 틴트 고글, 오버이어 헤드폰. 좌우 대칭, A포즈,
빈손. 무기·액세서리·벨트·스트랩·파우치·가방·글러브·글자·받침대 전부 없음.

🔴 **주황 금지는 취향이 아니라 규칙이다** — `ArtDirection.md §A-3-4` 의 `#FF6B2C` 는 적 공격
   텔레그래프 예약색이고, 플레이어에 쓰면 적 200~300 속에서 아군이 적으로 읽힌다
   (ADR 0016 **I1**, 복구 불가 등급). 결과에 주황이 섞여 나오면 그 결과는 버린다.

## 4. 설정

| 항목 | 값 | 이유 |
|---|---|---|
| **텍스처 생성** | 🔴 **1차 런은 끈다** | 아래 「텍스처 토글」 참조 |
| 리메시 | **낮게 잡지 말 것** | 실루엣이 복셀 격자를 표현해야 한다. 폴리 예산은 여기서 병목이 아니다 — **플레이어는 동시 1~4명**이고, 액터당 비용 최소화 원칙은 적 스웜(200~300)에 걸리는 규칙이다 |
| export | **FBX + GLB 둘 다** | 후속 경로가 갈린다. FBX = 언리얼 임포트, GLB = Blender 왕복 |
| 시드/재시도 | 같은 입력으로 여러 번 | 화면에 `무료 재시도` 칩이 있다 |

**🔴 텍스처 토글 — 1차 런은 끈다** (2026-09-08 화면에서 `텍스처 생성` 스위치 확인, 기본 OFF)

세 가지가 같은 방향을 가리킨다.
1. **이 런이 답하는 질문이 전부 형태다** — 뒤통수·등이 뭉개지는가 / 다리가 재킷과 융합됐는가
   (스키닝 가능성) / 실루엣이 복셀화에 쓸 만한가. 텍스처는 이 중 무엇도 답하지 않는다.
2. **텍스처가 있으면 형태 판정을 방해한다.** 색이 칠해진 모델은 "완성된 것"처럼 읽혀서
   뭉갠 덩어리를 가린다. 실루엣·토폴로지를 볼 땐 무채색 모델이 낫다.
3. **어차피 Meshy 텍스처는 출시에 못 쓴다** — ADR 0016 **I7 = 텍스처 없음, 평면 채색만**.
   색은 우리가 LUT 로 재저작한다(드론 행이 잡아둔 것과 같은 입장). 그러니 지금 굽는 건
   버릴 것을 사는 셈이고, 화면 설명대로 **비용도 더 낮다** — A/B 두 번 돌릴 여력이 생긴다.

⚠️ 대신 **이 런으로는 §5 의 색 4항목을 검증할 수 없다**(색 자체가 없다). 색 판정은 우리
   머티리얼 저작 단계로 넘어간다 — "색은 통과했다"고 기록하지 말 것.
⚠️ 텍스처 토글이 **형상 생성에 영향을 주는지는 미확인**이다(보통 별도 단계지만 Meshy 파이프라인은
   안 봤다). 형태가 이상하면 켜고 한 번 더 뽑아 대조해 볼 것.
색 참조가 필요해지는 시점(LUT 저작 시 어느 면이 어느 색인지 대조)에만 켜서 한 번 더 뽑는다.

**복셀 스킬(`픽셀 블록 친구`)을 시험한다면 — 이 숫자를 요구할 것:**
> **세로 43블록** (= 161.25cm ÷ 3.75cm 격자, `PlayerCharacter_ResumePrompt.md` §2-0·§2-1)

격자 크기나 블록 수를 지정할 수 없으면 **복셀화 트랙 A 는 탈락**이고 B′(매끈하게 뽑아
Blender Remesh Blocks 로 복셀화)로 간다. 이게 §3 트랙 A/B′ 미결 결정의 실질적 판정 기준이다.
※ 우리 삼면도는 의도적으로 **매끈한 애니 그림체**로 그렸다(각진 복셀 그림으로는 B′의 매끈한
  모델을 못 얻는다) — 그래서 A/B′ 어느 쪽으로 가든 그대로 입력으로 쓸 수 있다.

## 5. 판정 (결과를 받으면 이 순서로)

🔴 색 — 여기서 걸리면 나머지를 볼 필요 없다
- [ ] 주황·빨강·마젠타 픽셀 0 (`#FF3B4E`·`#FF6B2C`·`#FF1E7A` 계열)
- [ ] 고글 틴트가 하늘색/파랑
- [ ] 순백·순흑 없음
- [ ] 3색 유지 — 재킷 오프화이트 / 레깅스·솔 거의 검정 / 액센트 하늘색

형태
- [ ] 재킷이 **닫혀 있고** 골반 아래까지 내려오는가(열리거나 짧아지면 실루엣 계약 파기)
- [ ] 고글 + 헤드폰이 **머리에 붙어** 있는가(공중에 뜬 링이면 실패)
- [ ] 좌우 대칭인가
- [ ] 손·발이 뭉툭하고 얇은 파트가 없는가
- [ ] 받침대·바닥판이 붙어 나오지 않았는가

구조(임포트 전에 확인)
- [ ] 섹션 1개 / 머티리얼 1개인가
- [ ] 뒤통수·등이 뭉개지지 않았는가 ← **A(단일)와 B(다시점)를 가르는 항목**
- [ ] 다리가 재킷과 융합되지 않고 분리돼 있는가 ← 스키닝 가능성이 여기 걸린다

## 6. 받은 뒤 반드시 손대야 하는 것 (기대치 조정)

**① 좌표계** — Meshy 는 Y-up · 미터 · 정면 임의. Blender 에서 **cm · Z-up · 정면 +X · 원점 중심**
으로 정규화한 뒤 FBX. 임포트 후 **바운드 min/max 로 정면 축을 반드시 확인**할 것
(`Docs/PlayerCharacter_ResumePrompt.md` §1 함정 2, `fbx-metre-cm-armature-scale-trap`).

**② 🔴 `리그` 스킬은 우리 문제를 안 풀어준다.** 3P 몸체는 **Blu 스켈레톤(108본)** 위에 슬라이드
4클립 · 벽 4자세 · 로코모션이 얹혀 있다. Meshy 오토리그는 자기 본 구조를 만들므로 그 애니
8종과 맞지 않는다. **스키닝·웨이트 전이는 여전히 사람 손**이다(§8③). 눌러보는 건 자유지만
그 결과로 리깅 작업이 없어졌다고 판단하지 말 것.

**③ 라이선스** — Meshy Free = **CC BY 4.0(Meshy 크레딧 표기 필수)**, Pro($20/월) 무표기.
   이벤트로 프리미엄 기능이 열린 것이 **라이선스까지 바꿔주는지는 별개이고 미확인**이다.
   출시 에셋으로 쓸 거면 이건 확인하고 넘어가야 한다(`Docs/Research/ExternalModelingTools_2026-09-06.md` §3).

**④ 이미시브** — 밑단 띠·고글의 발광은 Meshy 가 텍스처의 밝은 색으로만 낸다. 실제 발광은
   우리 머티리얼에서 다시 배선해야 한다.

**⑤ 등 발광 패널이 후면 원본에 없다.** SD 단계에서 밑단 띠·중앙 봉제선과 상충해 포기했다
   (§2-4 결정④는 유효, 이월). Meshy 가 대화형이므로 **3D 단계에서 후속 지시로 되찾는 것**을
   먼저 시도해 볼 만하다 — "등 중앙에 발광 사각 패널 추가".

## 7. 🔴 실측 결과 — 텍스처 단계는 색을 못 지킨다 (2026-09-08, 1차)

멀티뷰 지오메트리(무텍스처) → `재질(텍스처) 재입히기` 를 §3 프롬프트 + 수정본(피부 분리,
아웃라인 요청 제거)으로 돌린 결과.

**색 = 하드 폴** — `§A-3-4` **적 예약 대역(빨강)이 대면적으로 들어왔다.**
- 스니커즈 갑피 = 어두운 빨강/마룬
- 고글 프레임 = 빨강/핑크
- 헤드폰 컵 = 마룬
- 밑단 하늘색 발광 띠 = **소멸**(크림색 립 니트로 대체됨)

프롬프트에는 `No orange, red, magenta, pink, green, purple` 가 있었고, **파트별 양성 배정도
있었다**(`near-black ... headphone cups`, `sky blue ... goggle lenses, sneaker trim`).
둘 다 무시됐다.

🔑 **결론: 이 단계에서 텍스트로 색을 통제할 수 없다.**
`ImagePrompt_v5_SD.txt` §1 이 적어둔 것과 같은 구조다 — *"'주황 넣지 마'라고 쓰는 건 부탁이지만,
SD 네거티브의 `orange, red, magenta` 는 실제 억제 메커니즘이다."* **Meshy 텍스처 단계에는 그
억제 메커니즘이 없다.** 게다가 "스니커즈 = 빨강/흰색 배색", "헤드폰 = 빨강 액센트"는 모델의
prior 가 아주 강한 지점이라, 양성 배정으로도 못 이겼다.

→ **프롬프트를 고쳐서 수렴시키려 하지 말 것.** 확률 게임이지 수정이 아니다.
→ 이건 **ADR 0016 I7(텍스처 없음, 평면 채색만)을 뒤집는 게 아니라 확인해 준다.** 색은 원래
   우리가 머티리얼/LUT 로 저작하기로 돼 있었다. 이 결과는 그 결정이 옳았다는 증거다.

**머리색이 청록(teal-green)으로 샜다** — Meshy 에이전트 본인이 지적했다. 이건 `ImagePrompt_v5_SD.txt`
가 SD 에서 이미 잡아둔 규칙 2(**"SD 의 `cyan` 은 초록으로 샌다 → `sky blue`/`light blue` 를 쓴다"**)와
**같은 현상이 다른 도구에서 재현된 것**이다. 프롬프트에는 `sky blue` 라고 썼는데도 샜다.
→ 시안 계열은 **도구를 가리지 않고 초록 쪽으로 끌린다.** 어느 생성 도구를 쓰든 결과의 hue 를
   실측할 것이고, 최종 색은 어차피 우리 머티리얼에서 확정한다(위 결론과 같은 방향).

**평면성도 폴** — 퀼팅 누빔, 천 짜임, 접힘 그림자, 립 니트 소맷단이 구워져 나왔다.
`no photo texture` · `no ambient occlusion` · `no baked shadows` 전부 무시됐다. 같은 원인.

**폴리 수** — 1,928,648 tris / 1,008,390 verts. 플레이어가 동시 1~4명이라 적 스웜만큼
빡빡하진 않지만 이대로는 못 쓴다. **리메시 필수**.

**형태 쪽에서 오히려 좋아진 것** — 손이 **뭉툭한 벙어리장갑형**으로 나왔다(무텍스처 1차에서
손가락이 가늘게 갈라져 나온 게 §2-2 "맨팔 2칸 하한" 정신과 충돌했었다). 재킷 봉쇄·기장,
고글·헤드폰 부착, 머리색, 레깅스는 유지.

**그래서 다음** — 텍스처에 더 쓰지 말고 **무텍스처 지오메트리로 돌아간다**. FBX+GLB 내보내기 →
A 런(정면 1장) 과 비교 → 형태 채택 판정 → 색은 우리 머티리얼 단계에서.
색 참조본이 필요하면 지금 것 하나로 충분하다(**출시에는 절대 쓰지 않는다** — 적 예약색 포함).

## 8. 🔴 파이프라인 차단 — Free 플랜은 3D 모델을 내려받을 수 없다 (2026-09-08)

무텍스처 지오메트리를 FBX/GLB 로 내보내려고 `다운로드` 를 눌렀더니 **포맷 선택창이 아니라
「패키지 업그레이드」 결제창**이 떴다. 접근성 트리에서도 `다운로드` 버튼 옆에 **`PRO` 배지**가
확인된다. Free 플랜 기능표의 "3D 모델 다운로드 무제한"은 **Pro 이상 항목**이다.

🔑 **배너의 "3D Agent 이벤트 — 모든 프리미엄 기능 잠금 해제"는 생성 기능에 걸리는 것이지
   다운로드에는 걸리지 않는다.** 즉 **만들 수는 있는데 가져올 수가 없다.**
   §2 의 A/B 비교도, §5 의 구조 판정(섹션 수·tris·다리 분리)도, Blender 정규화도 전부
   파일이 있어야 하는 작업이라 **여기서 파이프라인이 멈춘다.**

**결제 결정이 필요하다(사용자 몫).** 2026-09-08 화면 표시값:

| 플랜 | 가격 | 이 트랙에 걸리는 것 |
|---|---|---|
| Free (현재) | ₩0 · 월 100 크레딧 | **다운로드 불가** · CC BY 4.0(크레딧 표기 필수) |
| Pro | ₩28,869/월 (연간 ₩173,214, Meshy 7 출시 50% 할인 · 6개월 무료 표기) | 다운로드 무제한 · **비공개 라이선스**(표기 불필요) · 월 1,000 크레딧 · 작업당 무료 재시도 |

💡 **§6③ 에 미해결로 남겨둔 라이선스 문제와 같은 결제로 해소된다** — Free 산출물은 상업 배포 시
   Meshy 크레딧 표기가 필수인데, Pro 는 비공개 라이선스라 표기 의무가 없다. 즉 "다운로드"와
   "출시 사용 가능"이 하나의 결정으로 묶인다.

⚠️ **결제 전에 따져볼 것** — 이 트랙에서 Meshy 가 실제로 준 것은 **지오메트리 한 벌**이다.
   텍스처는 §7 에서 색을 못 지켜 폐기했고, 리깅은 §6② 대로 Blu 스켈레톤과 안 맞는다.
   그러니 결제의 실질 대가는 "이 지오메트리를 쓸 수 있게 되는 것" 하나다. 그 값어치는
   **A/B 비교 없이는 판단할 수 없는데, 그 비교 자체가 다운로드를 요구한다** — 닭과 달걀이다.
   → 실무적 순서: 한 달 Pro 로 내려받아 판정하고, 채택 안 되면 해지. 자동갱신 확인할 것.

### 8-1. ✅ 해제됨 (2026-09-08, 사용자 결제)
사용자가 **Pro 결제 완료**. 이로써 두 가지가 동시에 풀렸다 — **다운로드 가능** + **비공개 라이선스**
(§6③ 의 CC BY 4.0 표기 의무 소멸). 아래 §10 이 그 위에서 할 일이다.
⚠️ **자동갱신 여부는 사용자가 확인할 것.** 채택 판정이 끝나면 계속 쓸지 결정한다.

## 9. 리깅 — "UE 마네킹에 맞출 수 있는가" (2026-09-08 조사)

사용자 질문: *"리깅은 Blu 스켈레톤보다 UE 메카님에 맞출 수 있는지가 중요해 보이는데 가능한가?"*
→ **가능하다. 그리고 전제를 한 군데 고쳐야 한다 — 이 프로젝트는 이미 마네킹 기반이다.**

### 9-1. 이미 있는 것 (ADR 0002 실측, 커밋된 에셋)

```
/Game/Characters/Retarget/
  IK_UE4Mannequin      자동 생성 20체인
  IK_Blu               자동 생성 실패 → 20체인 손 정의
  RTG_UE4Man_to_Blu    20/20 매핑 + 자동 정렬
/Game/Characters/Blu/  IK_MannySrc · RTG_Manny_to_Blu
```
현행 3P 애니의 출처가 **UE4 Mannequin 팩(774개)**이고, 그중 **426개를 이 다리로 리타게팅**해서
쓰고 있다. 즉 "마네킹 호환"은 새로 사야 하는 능력이 아니라 **이미 깔린 등뼈**다.

### 9-2. 이름 규칙은 게이트가 아니다 — 이미 한 번 뚫었다

| | UE4 Mannequin | Blu |
|---|---|---|
| 골반 | `pelvis` | `hips` |
| 척추 | `spine_01/02/03` (**3**) | `spine`/`chest` (**2**) |
| 어깨 | `clavicle_l/r` | `shoulder_L/R` |
| 발끝 | `ball_l` | `toes_L` |

이름도 계층 개수도 다르고 `apply_auto_generated_retarget_definition()` 은 Blu 에서 **20체인 중 3개만**
찾아냈다. **20개를 손으로 정의해서 해결했고 그 에셋이 커밋돼 있다.** → 임의 리그를 마네킹 다리에
얹는 것은 **일회성 작업이고 이 리포는 이미 그 방법을 안다.** Meshy 가 마네킹 이름으로 뽑아줄
필요가 없다.

### 9-3. 🔴 진짜 게이트는 스켈레톤이 아니라 **비례**다

ADR 0002 실측(Blu vs 마네킹):

| | 비율 | 결과 |
|---|---|---|
| 키 | 1.008 | 사실상 동일 |
| 다리 | 0.983 | 로코모션 잘 옮겨진다 |
| **팔(상완+전완)** | **0.725** | **여기서 깨진다** |
| 레퍼런스 포즈 | T-pose vs A-pose (46.9° 차) | 자동 정렬이 −47° 롤로 흡수 |

*"키와 다리는 사실상 같고 팔만 27.5% 짧다. 그래서 로코모션은 잘 옮겨지고 무기 파지만 문제가 된다."*
가장 빠듯한 `Jog_Aim_F_Loop` 에서 **팔 여유가 2.17cm** 밖에 안 남았다.

**ENE 는 Blu 보다 훨씬 더 멀다.** §2 스펙 = **5.375등신**(마네킹 ~7.5) · **머리 폭 41.25cm 가 어깨 30cm 보다 넓다** ·
다리가 키의 53.5% · 과장된 신발. Blu 가 팔 27.5% 부족으로 2.17cm 여유였는데, 치비는 그보다
크게 어긋난다. **양손 소총 파지가 깨지는 지점**이 여기다.

### 9-4. 그래서 판단

- **"Meshy 가 리그를 준다"는 결제 근거가 못 된다.** 리깅은 애초에 Meshy 에서 올 물건이 아니었다.
  더 안전한 길은 **Meshy 리그를 아예 안 쓰고 Blender 에서 기존 스켈레톤으로 웨이트 전이**하는 것 —
  그러면 새 메시가 처음부터 프로젝트가 굴리는 스켈레톤 위에서 태어난다. §6② 는 이 점에서
  불완전했다("맞지 않는다"까지만 썼고, 이 리포가 이미 임의 리그를 다리에 얹는 법을 안다는 걸
  안 적었다). Meshy 의 값어치는 **메시 한 벌**이지 리그가 아니다.
- **완화 요인** — 1P = 총만(ADR 0015)이라 이 몸체는 **팀원 시점(3P)과 로비에서만** 보인다.
  20m 거리의 치비에서 양손 그립 오차의 허용치는 1인칭보다 훨씬 넉넉하다(§1 "투자 규모를 여기에 맞춰
  판단한다"). **깨진다 = 채택 불가가 아니라, 어디까지 허용할지의 문제.**
- **재는 방법은 이미 있다** — ADR 0002 이 쓴 판정 기준(*"소총은 강체라 두 손 사이 거리가 무기
  형상으로 고정된다"* → 두 손 간격 vs 팔 뻗음 여유)을 ENE 비례에 그대로 적용하면 된다.
  단 그 실측도 **메시 파일이 있어야** 한다(§8 결제 게이트).

## 10. 🔴 실행 계획 — 메시 → 리깅 → 애니 (Pro 결제 후, 새 세션은 여기서 시작)

### 10-0. 먼저 알아야 할 것 — 이 프로젝트의 애니 현황 (2026-09-08 조사)

**Meshy 애니를 쓸지 말지는 "결손이 실제로 있는가"부터 답해야 한다.** 현황:

| 출처 | 수량 | 상태 |
|---|---|---|
| UE4 Mannequin 팩 → Blu 리타게팅 | **426개** | 커밋됨. 다리 = `RTG_UE4Man_to_Blu` (§9-1) |
| UE 안의 3P 커스텀 애니 | **단 2개** — `Blu_W2_Slide_Loop` · `Blu_Wall_Slip` | 나머지 6개는 2026-08-03 사용자 결정으로 **삭제**(깨진 소스에서 나온 것들, `Docs/WorkLog.md`) |
| Blender repo 원본 8포즈 | 8 | `NeonV_locomotion.blend` (별도 Blender repo, 경로 = §1). **애니의 진실원천** — 액션 편집은 거기서만 |

→ **로코모션·무기 동작은 이미 채워져 있다.** Meshy 600+ 모션이 메울 결손이 실제로 있는지
   **먼저 확인하고** 착수할 것. 없으면 애니는 범위 밖이다.
⚠️ Meshy 모션은 **자기 리그 기준**이라 또 리타게팅이 필요하다 — 이미 마네킹 다리가 깔려 있는데
   두 번째 다리를 놓는 중복 투자가 될 수 있다(§9-2).

### 10-1. Phase 1 — 다운로드 (제일 먼저. 모든 판정이 여기 막혀 있었다)

무텍스처 지오메트리(멀티뷰 B 결과) **FBX + GLB 둘 다** → `Docs/Handoff/PlayerChar_Arcade/meshy_out/`.
텍스처본도 **색 참조용으로만** 함께 받는다(§7 대로 출시 사용 금지 — 적 예약색이 박혀 있다).

### 10-2. Phase 2 — A/B 판정 (§2 의 미완 실험)

A 런 = `이미지→3D` + `PlayerCharArcade_front.png` **한 장만**, 프롬프트는 §3-1 그대로,
**텍스처 생성 OFF**(§4). 생성 → 다운로드 → B 와 나란히 놓는다.
판정 = §5 의 **구조** 항목. 특히 *뒤통수·등이 뭉개지는가*(A/B 를 가르는 항목) ·
*다리가 재킷과 융합되지 않고 분리된 솔리드인가*(스키닝 가능성이 여기 걸린다).
실측은 헤드리스로 — 섹션 수 · tris · 바운드 min/max.

### 10-3. Phase 3 — 비례 실측 (결제 전에는 불가능했던 것)

`ADR 0002` 의 판정 기준을 ENE 에 그대로 적용한다: **"소총은 강체라 두 손 사이 거리가 무기
형상으로 고정된다"** → 두 손 간격 vs 팔 뻗음 여유. Blu 기준선 = 가장 빠듯한 `Jog_Aim_F_Loop`
에서 **여유 2.17cm**(§9-3). ENE 가 이보다 얼마나 나빠지는지가 숫자로 나온다.
⚠️ 실제 무기는 **Synty 모듈러(전장 77.7cm)** 다 — 애니가 전제한 팩 M4(83.5cm)로 재면 틀린다
   (ADR 0002 「검토자의 오류 ①」: *구조 판정 전에 실제 사용 에셋을 먼저 확인해야 한다*).
같이 할 것: 등신·팔·다리 실측 → **§2 스펙표를 실측값으로 갱신**(§0-A 미해결 항목).

### 10-4. Phase 4 — 리깅

두 갈래를 **비용으로 비교**한다. 판정 기준 = *어느 쪽이 기존 426 리타겟 애니를 그대로 받는가*.

| 갈래 | 방법 | 위험 |
|---|---|---|
| **A. Meshy 오토리그** | `리그` 스킬 → 나온 본 이름·계층 조사 → IK Rig + Retargeter 로 마네킹 다리에 연결 | 리그 품질이 통제 밖. 치비 비례에 자동 리깅이 잘 붙는지 미지수 |
| **B. Blender 웨이트 전이 (기본값)** | Meshy 리그를 무시하고 기존 스켈레톤(Blu 또는 마네킹)에 새 메시를 스키닝 | 재킷이 골반을 지나 접혀야 하는 문제(§0-A 스키닝 비용)는 그대로 남는다 |

**B 가 기본값이다** — 새 메시가 처음부터 프로젝트가 굴리는 스켈레톤 위에서 태어난다(§9-4).
A 는 "Meshy 리그가 쓸 만한가"를 재는 실험으로만 돌린다.
🔴 함정: 기존 스켈레톤을 지정한 임포트는 뼈가 안 맞으면 **그 Skeleton 에셋을 통째로 덮어쓴다**
   (메모리 `ue-import-overwrites-target-skeleton`). 충돌 창이 뜨면 Done 금지.
🔴 함정: 리그드 GLB 헤드리스 임포트 = 에디터 크래시(`glb-import-crash-use-fbx`). 리깅 포함이면 FBX.

### 10-5. Phase 5 — 애니메이션 (§10-0 확인 후에만)

결손이 확인되면: Meshy 애니 라이브러리에서 후보를 고르고 → 리타게팅 비용을 산정해 →
**사용자 결정**을 받는다. 결손이 없으면 **범위 밖으로 닫고 보드에 사유를 남긴다.**

### 10-6. 브라우저 조작 함정 (2026-09-08 실측)

- **스크린샷이 자주 타임아웃한다**(3D 캔버스가 무겁다, `Page.captureScreenshot` 30s 초과).
  **`read_page`/`find` 를 우선**하고 스크린샷은 `scale` 0.6 근처로 줄여 찍는다.
- **캔버스의 모델을 클릭하면 채팅 입력창에 첨부 칩이 붙는다.** 모르고 보내면 의도치 않은
  컨텍스트가 들어간다 — `Remove attachment` 버튼으로 지울 것.
- 에이전트 대화 URL = `meshy.ai/ko/agent/<id>?chat=<id>`. 워크스페이스에서 `?sidebar=agent` →
  「최근 항목」 카드로 복귀할 수 있다.
- 크레딧: **Pro = 월 1,000(최대 100 에셋)**. 유료 호출 전에는 사용자 확인을 받는다.
