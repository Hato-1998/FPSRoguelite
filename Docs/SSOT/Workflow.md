## 6. 작업 방식 / 규칙

### 6-1. 환경 / 경로

### 6-2. 프로덕션 방식 원칙 (필수)
- 코드/개발은 **프로덕션 품질**. 엔진 템플릿 편의 단축은 지양
- **C++ = 로직/베이스 클래스 / 콘텐츠 바인딩 = BP 서브클래스·DataAsset·config** (데이터 드리븐). **에셋 경로를 C++에 하드코딩 금지**(`ConstructorHelpers` 지양)
- 네트워크 = 서버 권위 + Push Model. 엔진 API는 소스 대조 후 사용
- 디버그/테스트 스캐폴딩(DrawDebug, 콘솔 커맨드, 임시 로그, 플레이스홀더 메시)은 **검증용으로만 허용** — 프로덕션 전환 대상임을 명시·추적(§8)하고 `#if !UE_BUILD_SHIPPING` 등으로 게이트하거나 제거
- 잠깐의 동작 테스트는 단축 가능하나, **남는 코드는 프로덕션 기준**

### 6-3. 코딩 / 빌드 규칙
- UE5 코딩 컨벤션 준수(Epic Coding Standard). `.editorconfig` 적용: C++ 탭 들여쓰기, eol=crlf
- 빌드 타깃 버전: `BuildSettingsVersion.V6`, `EngineIncludeOrderVersion.Unreal5_7`
- 엔진 API/매크로/플래그는 **추론 금지 — 엔진 소스에서 실제 사용례를 grep**해 대조 후 작성
- 네트워크: **P1부터 서버 권위 + Push Model**. 솔로 후 retrofit 금지
- 검증 없이 "완료" 보고 금지 — 빌드/스모크/`git diff` 중 하나로 자체 검증

### 6-4. 진행 핸드오프 규칙 (다른 세션/AI 인수인계)
> **2026-08-07 전면 이관(사용자 결정): 작업 추적·핸드오프의 SSOT = Notion PM 보드(§6-9).** `PROGRESS.md`는 보드로 안내하는 포인터만 남는다.
- 작업 시작 전 **이 문서(Game.md) + PM 보드(§6-9 조회 절차)** 를 먼저 본다
- 큰 작업은 단계 완료 시점과 **세션 중단 전 반드시 보드 행을 갱신**한다 — 상태·담당 + 행 페이지에 인계 컨텍스트(한 일/다음 단계(파일·함수 단위)/빌드·검증법/블로커/미커밋 콘텐츠 목록)
- 커밋 메시지에 단계·검증 결과를 명확히. 상세 이력은 `git log --oneline`. 긴 경위·함정은 여전히 repo 문서(`Docs/WorkLog.md`·`Docs/Troubleshooting.md`)에
- 설계 변경은 **이 문서(Game.md)를 먼저 갱신**
- **각 P 단계는 전용 `phase/` 브랜치에서 작업**(§6-7). 세션 중단 전 보드 행 `브랜치` 속성에 **현재 활성 브랜치명**을 명시

### 6-5. 모델 / 작업 흐름 정책 (전역 HotL 준수)
- 새 작업은 **플랜 우선**. HIGH_RISK(파일 생성/수정/삭제, 빌드, 커밋)는 승인 후 실행
- **작업을 먼저 2갈래로 나눈다** (판정 기준 = §6-5-2 트리거 표):

| 갈래 | 조사·플랜 | **플랜 게이트** | 구현 | 검증 | **머지 게이트** |
|---|---|---|---|---|---|
| **코어 / 구조 설계 / 리팩토링** | Opus | **Fable ①** | Sonnet 위임 | Opus | **Fable ②** |
| 그 외(기능 추가·버그 수정·콘텐츠 배선 등) | Opus | — | Sonnet 위임(`claude-sonnet-5`) | Opus 직접 | — |

> 🔄 **2026-08-26 전환 (사용자 결정)** — 종전엔 코어 갈래를 **Fable이 주도**했다(설계·지시·판정 전부).
> **Fable 사용량 문제로 기본 주도자로 쓸 수 없어**, Fable을 **두 지점에서만 부르는 검증자**로 바꾼다.
> 세션은 **항상 Opus로 시작**한다 — "세션 자체를 Fable로 시작"하는 모드는 폐지.
>
> **부수 효과 = 종전 파이프라인의 알려진 약점이 구조적으로 해소된다.** 종전 §6-5-2는
> *"C1 설계자와 C3 판정자가 같은 Fable이라 독립된 시각이 레드팀 하나뿐"* 이라고 스스로 적어 뒀다.
> 이제 **설계자(Opus) ≠ 검증자(Fable)** 라 두 게이트 모두 원래부터 독립 시각이다.
> 비용 때문에 고른 안이지만 검증 구조로도 더 낫다.

- 코어 갈래 상세 = **§6-5-2**. 그 외 갈래는 종전과 동일(2026-07-02 위임 기본 Haiku→Sonnet 5 전환)
- **불변 규칙**: 검증·판정을 **하위 모델(Sonnet/Haiku)에 위임 금지**. 최종 판정 권한은 **Opus에게** 있고, 코어 갈래에서는 **Fable 두 게이트를 통과**해야 한다
- 단순 한 줄 수정·읽기 전용 조회는 모델 분리 없이 즉시 처리

#### 6-5-1. 멀티에이전트 팬아웃 예산 (상한 필수)
서브에이전트/워크플로를 띄울 때 **에이전트 수에 반드시 상한**을 건다. (도입 2026-07-15 — 상한 없는 팬아웃으로 에이전트 71개·서브에이전트 토큰 552만을 태워 세션 사용 한도를 소진시킨 사고. 지출의 ~90%가 검증 단계였고 검증 65건이 실제로 잡은 교정은 1건.)

- **총 에이전트 ≤ 12개**가 기본 상한. 초과하려면 **먼저 규모·예상 비용을 사용자에게 말하고 승인**받는다.
- **차원(dimension)당 검증 에이전트 ≤ 2개.** 조사 결과가 낸 주장마다 검증자를 1:1로 붙이는 패턴 **금지** — 주장 수는 예측 불가(실측 10~14개/차원)라 상한이 없으면 폭발한다. 검증 대상은 **결론을 뒤집을 수 있는 주장만** 1~2개로 추린다.
- **설계 체크**: 스크립트를 쓰기 전에 "최대 몇 개가 뜨는가"를 계산한다. **답이 상수가 아니고 앞 단계 출력 길이에 비례하면 그 자체가 설계 결함** → `.slice(0, N)`으로 자르고, 자른 사실을 `log()`로 남긴다(조용한 절삭 금지).
- **모델/사고량 계층화**: 사실 확인·grep 대조 등 값싼 단계는 `model:"sonnet"`, 최고 난도 판정에만 상향. 전 단계에 Opus+`effort:"high"`를 깔지 않는다.
- **규모 정합**: grep 몇 방으로 판정되는 질문(호출처 census, "이 경로가 도달 가능한가")은 에이전트 3~5개로 충분하며 대개 워크플로 자체가 불필요하다. ultracode가 켜져 있어도 이 상한은 유효하다(ultracode = "철저히"이지 "무한히"가 아님).

#### 6-5-2. 코어 / 구조 작업 = Opus 주도 + **Fable 2게이트** 파이프라인
**게임의 뼈대를 정하는 작업은 Opus가 조사하고 설계하고, Fable이 그 플랜을 검증하고, Sonnet이 명세대로 구현하고, 머지 직전에 Fable이 한 번 더 검증한다.**

(도입 2026-08-07 = Fable 주도 / **개정 2026-08-26 = Opus 주도 + Fable 2게이트**, 둘 다 사용자 결정.
근거: 구조 결정은 한 번 틀리면 되돌리는 비용이 커서 **가장 깊게 추론하는 모델을 꼭 태워야 하지만**,
Fable을 기본 주도자로 쓰면 **사용량이 감당되지 않는다**. 그래서 Fable을 *플랜이 굳기 전*과
*코드가 main에 들어가기 전* — **되돌리기 비용이 가장 싼 두 지점**에만 놓는다.)

##### (1) 이 파이프라인을 타는가 — 트리거
아래 중 **하나라도** 해당하면 코어 갈래다.

| # | 조건 |
|---|---|
| T1 | 새 서브시스템·클래스 트리를 **신설** |
| T2 | 여러 클래스에 걸친 **구조 변경 / 리팩토링** (기계적 치환 포함) |
| T3 | **복제·수명주기·GAS·성능 경로**가 얽힌 설계 |
| T4 | 확장 스키마 설계(카드·무기·적 규약 등 "새 규약을 데이터로 추가" 구조) |
| T5 | **코어 도메인** 헤더를 만짐 — `Source/FPSRoguelite/{Public,Private}/` 하위 `Core`·`Hero`·`Combat`·`Weapon`·`Enemy`·`Director`·`Run`·`AbilitySystem`·`Card`·`Boss`·`Messages` |

**해당 없음** → 기존 §6-5 흐름(구현=Sonnet / 검증=Opus). 한 줄 수정·기존 패턴 반복·콘텐츠 배선·단순 버그 수정은 코어 폴더를 만져도 코어 갈래가 아니다(T5는 *구조를 건드릴 때* 걸리는 조건이다).
애매하면 **코어로 올린다** — 설계를 얕게 해서 재작업하는 비용이 Fable 한 번보다 크다.

> 📋 이 판정은 PM 보드의 **`추천모델`** 칸(`Fable`/`Opus`)에 미리 적혀 있다(§6-9 (2)). 행을 집을 때 거기서 갈래를 읽으면 되고, **기준의 SSOT는 이 표다** — 칸과 어긋나면 이 표가 옳다.

##### (2) 운영 모드 — Fable을 어디에 놓는가
**세션은 항상 Opus로 시작한다.** Fable은 **서브에이전트로만**, **정확히 두 번** 부른다.

| 게이트 | 시점 | Fable이 받는 것 | Fable이 내는 것 |
|---|---|---|---|
| **① 플랜 게이트** | 플랜이 굳기 **전**, 사용자 승인 **전** | Opus가 모은 조사 결과 + 플랜/명세 초안 | 플랜의 결함·놓친 대안·제1원리 위반 지적. **통과 / 반려** |
| **② 머지 게이트** | 구현·빌드·검증이 **끝난 뒤**, main 머지 **직전** | 브랜치 diff (§6-6-1 레드팀 프라이머) | P1/P2/P3 지적. **P1 잔존 시 머지 금지** |

> 종전의 "세션 자체를 Fable로 시작"(모드 A)은 **폐지**다 — 사용량이 감당되지 않는다.
> 보드 행 로그에 "다음 세션은 Fable로 시작"을 남기던 관행도 함께 폐지.

**게이트 ②는 §6-6-1 레드팀 게이트 그 자체다** — 별도로 한 번 더 부르지 않는다(그러면 Fable을 줄인 의미가 없다).

##### (3) 5단계
| 단계 | 담당 | 하는 일 | 산출물 |
|---|---|---|---|
| **C0 조사·기반체크** | **Opus** (값싼 조사는 Sonnet 위임) | 기존 인프라 전수조사, 엔진 소스 대조(전역 ENGINE SOURCE FIRST), 관련 SSOT·메모리 수집, **실측으로 전제 확인** | 컨텍스트 정리 |
| **C1 설계·명세** | **Opus** | 구조 확정 + **헤더 수준 인터페이스**까지. `.cpp` 본문은 쓰지 않는다 | `Docs/Specs/<유닛ID>_<키워드>.md` (템플릿 = `Docs/Specs/_TEMPLATE.md`) — **커밋한다** |
| **G1 플랜 게이트** | **Fable**(서브에이전트) | C0 결과 + C1 플랜을 받아 **적대적으로 검증**. 반려면 C1으로 되돌린다 | 통과/반려 + 지적 목록 |
| **(승인)** | **사용자 + Opus** | G1을 통과해 나온 플랜으로 최종 확인. 여기서 사용자가 결정한다 | 승인 |
| **C2 구현** | **Sonnet 위임** | 명세를 **축자적으로** 구현. 시그니처·필드·클래스의 추가/변경 금지 | 코드 |
| **C3 검증** | **Opus** | 명세 대비 diff 대조 → 빌드(§6-6) → 헤드리스 스모크·자동화 | 판정 |
| **G2 머지 게이트** | **Fable**(서브에이전트) | 브랜치 diff 적대 리뷰 = **§6-6-1**. **P1 잔존 시 머지 금지** | 통과 시 머지(§6-7) / 반려 시 C2로 |

- **G1에 무엇을 넘기는가**: C0의 **실측치와 대조군**을 반드시 함께 넘긴다. 플랜만 넘기면 Fable이 전제를 검증할 수 없어 "그럴듯한지"만 보게 된다.
- **명세 갭**: C2에서 명세에 없는 판단이 필요해지면 Sonnet은 **추측해서 채우지 말고 멈추고 보고**한다. 갭은 C1으로 돌아가 Opus가 명세를 고친다. **갭이 구조를 바꾸면 G1을 다시 태운다.**
- **명세는 살아 있는 문서다**: 통과 후 실제 구현과 어긋난 부분이 있으면 명세를 실제에 맞춰 갱신하고 상태를 `구현완료`로 바꾼다.
- ✅ **종전의 구조적 약점(설계자 = 판정자)은 이 개정으로 해소됐다.** 설계는 Opus, 두 게이트는 Fable이라 **원래부터 독립 시각**이다. 다만 §6-6-1의 **"스폰 프롬프트에 설계 변호를 싣지 않는다"** 규율은 **그대로 유지**한다 — 이제 게이트 성립의 *필요조건*은 아니지만, 변호를 실으면 검증이 여전히 얕아진다.
- ⚠️ **새로 생긴 약점 = G1과 G2 사이가 길다.** 그 사이의 판단(구현 중 나온 설계 결정, C3에서 고친 것)은 **Fable을 안 거친다.** 그래서 C3 검증에서 *"플랜에 없던 구조 결정이 몇 개 들어갔는가"* 를 세고, **하나라도 있으면 G2 프롬프트에 그 목록을 명시**한다.

##### (4) 프롬프트 작성 규칙 (모델마다 정반대다)
**Fable에게 — 처방하지 말고 맥락을 줘라.**
- ❌ 단계별 지시("먼저 X 조사하고, 그다음 Y 설계하고…"). 구형 모델용 스캐폴딩은 **Fable의 출력 품질을 오히려 떨어뜨린다.**
- ✅ **목표 + 제약 + 성공 기준**만 주고, 대신 **컨텍스트를 두껍게** 실어라(해당 `Docs/SSOT/` 도메인 파일, 관련 메모리, 기존 코드 인용, 제1원리).
- 아래 3줄은 고정으로 붙인다:
  - `진행·완료 주장은 이 세션의 도구 결과와 대조해서만 보고할 것. 검증 안 된 것은 "미검증"이라고 명시할 것.`
  - `요청 범위 밖의 정리·리팩토링·추상화 추가 금지. 하지 않기로 한 것은 비목표에 적을 것.`
  - `턴을 끝내기 전 마지막 문단을 확인할 것. 계획·질문·다음 단계 약속이면 지금 도구로 실행할 것.`

**Sonnet에게 — 문자 그대로 따르게 써라.**
- Sonnet 5는 지시를 **축자적으로** 이행한다. "전부 적용" 같은 말은 **대상을 열거**한다.
- 명세 파일 경로를 주고: `이 명세를 축자적으로 구현. 시그니처·필드·클래스의 추가/변경 금지. 명세에 없는 판단이 필요하면 멈추고 "명세 갭"으로 보고.`
- 위임은 항상 최신 Sonnet(`model="sonnet"` = `claude-sonnet-5`).

**effort**: Fable 게이트(G1·G2) = `high`(최고 난도만 `xhigh`) / Sonnet 구현 = `high` / 대조·census 같은 값싼 단계 = `low`.

##### (5) 비용·지연 가드 (필수)
- **Fable은 출력 100만 토큰당 $50** — Opus 5의 2배, Sonnet 5의 약 3.3배. **이 단가가 2026-08-26 개정의 직접 원인**이다: 세션을 통째로 Fable로 굴리면 모든 턴이 그 단가라 감당이 안 됐다.
- **Fable 호출은 코어 갈래당 2회(G1·G2)가 상한**이다. 더 부르고 싶으면 그 전에 사용자에게 말한다.
  - 예외 = **G1 반려 후 재제출**. 반려는 통과가 아니므로 재제출은 새 호출이 아니라 같은 게이트의 2회차다. 다만 **같은 게이트 3회차부터는 사용자에게 보고**한다(명세가 아니라 요구가 흔들린다는 신호).
- **조사·grep·census는 절대 Fable에 시키지 않는다.** Opus가 하거나 `model="sonnet"` 서브에이전트로 내린다. Fable은 **판정에만** 쓴다.
- **Fable 턴은 수 분 걸릴 수 있다.** 백그라운드로 띄우고 대기를 전제로 진행하며, 끝났는지 반복 확인(폴링)하지 않는다.
- §6-5-1 팬아웃 상한(**총 에이전트 ≤ 12**)은 이 파이프라인에서도 그대로 유효하다.
- **폴백**: Fable이 거부(refusal)하거나 쓸 수 없으면 **Opus가 그대로 진행하고, 게이트를 건너뛴 사실을 명세 메타와 보드 행 로그에 기록**한다. 조용히 넘어가지 않는다.

#### 6-6-1. 레드팀 리뷰 게이트 (머지 전 적대 코드리뷰)
> 2026-08-07 전환: 종전 외부 Codex diff 게이트(`Scripts/codex-review.ps1`)를 **내부 Fable 레드팀 서브에이전트**로 대체. 사용자 결정.
> 계기 = `codex review`에 적대 페르소나를 넣을 방법이 없다는 게 실증됨(인자는 CLI가 거부, `AGENTS.md` 안내는 대조군에서 리뷰 형식 미변경) + 사용량 한도·무응답. **잃은 것 = 외부 모델 교차검증**(Codex는 사각이 Claude와 다른 모델이었다). 그 손실은 설계 토론 채널(§10 ConsultLoop)에 Codex를 남겨 부분적으로만 메운다.

**언제** — **§6-5-2 코어 갈래(T1~T5)일 때만** 머지 직전 1회. 그 외 갈래(콘텐츠·수치·BP배선·에셋·국지 버그수정)는 게이트를 건너뛰고 빌드 + 헤드리스 스모크 + `git diff` 자기비판으로 끝낸다(범위 규칙 SSOT = `Docs/ConsultLoop.md` §0-1).

**어떻게** — **Opus가**(개정 2026-08-26: 세션은 항상 Opus다) `Agent` 도구로 **`model="fable"`, `subagent_type="general-purpose"`, 백그라운드**로 레드팀을 띄운다. **이것이 §6-5-2 (2)의 게이트 ②** 다 — 머지 단계 Fable 검증을 따로 한 번 더 부르지 않는다. 프롬프트 원문 = **[`Docs/InternalRedTeamReview.md`](../InternalRedTeamReview.md)**(페르소나 + 출력 계약 + P1/P2/P3 심각도 정의) — 경로만 주고 읽게 한다.
> 실측(2026-08-07 첫 가동): **약 14분 · 157k 토큰 · 도구 18회**로 출력 계약 100% 준수. **느리니 백그라운드 필수, 폴링 금지**(§6-5-2 (5)).

**🔒 독립성 — 차단이 아니라 스폰 프롬프트 통제 + 취급 규칙이다.**
설계한 본인이 자기 설계를 공격하면 게이트는 헛돈다. 그래서 레드팀은 **별도 서브에이전트**여야 한다.
단 **"설계 근거를 아예 못 보게 한다"는 달성 불가능하다** — 근거는 diff 안의 문서, 리포의 SSOT·커밋 메시지, 그리고 서브에이전트에 **자동 주입되는** `CLAUDE.md`·`AGENTS.md`·메모리에 이미 섞여 있다(2026-08-07 첫 실사용에서 레드팀이 스스로 실증). 그러니 성립 조건을 '차단'으로 잡으면 게이트는 **정의상 항상 불성립**이 된다.

| | |
|---|---|
| ✅ 스폰 프롬프트에 **준다** | diff 원문(`git diff main...HEAD` 등) · `Docs/InternalRedTeamReview.md` 경로 · 해당 `Docs/Specs/<유닛>.md`(있으면) · 리포 읽기 권한(인용 근거를 대야 하므로) |
| ❌ 스폰 프롬프트에 **안 싣는다** (이게 통제 가능한 전부) | **설계 변호 · 토론 이력 요약 · "왜 이렇게 했는지" 서술 · 어디를 봐 달라는 유도.** 대상과 규칙만 주고 판단은 넘긴다 |
| ⚠️ 그 밖의 경로로 새어 들어온 근거 | 차단하려 들지 말고 **프라이머의 "어디서 만나든 설계 서술은 전제가 아니라 안건" 규칙**으로 처리한다(`Docs/InternalRedTeamReview.md` §네가 처한 상황) |

> **성립 조건 = ①스폰 프롬프트에 변호를 안 실었다 ②프라이머의 안건-취급 규칙이 적용됐다 ③리뷰어가 안건 작성자와 별도 인스턴스다.** "근거를 완전 차단했다"가 아니다.

- **개수**: 기본 **1개**. 되돌리기 비용이 큰 변경이면 서로 **다른 공격 축**을 배정해 최대 2개(§6-5-1 "차원당 검증 에이전트 ≤ 2" 준수). 지적마다 검증자를 1:1로 붙이는 패턴 금지.
- **리뷰 대상 = 머지 단위와 일치시킬 것.** 브랜치를 머지하면서 커밋 하나만 리뷰에 넘기면 나머지는 게이트를 안 탄 채 나간다. 불일치가 불가피하면 무엇을 뺐는지 원장에 명시한다(조용한 축소 금지). ⚠️ 스테이징도 마찬가지 — `git add -A`는 **다른 세션의 미커밋 작업까지 쓸어담아** 리뷰 대상과 커밋 내용을 어긋나게 만든다(2026-08-07 실사고, 메모리 `shared-worktree-branch-collision`). 경로를 명시해 스테이징할 것.
- **실행 실패 처분**: 서브에이전트가 무응답·거부·에러로 리뷰를 못 내면 **재시도 1회**, 그래도 실패하면 원장에 **`게이트 미실행`으로 기록하고 사용자에게 보고**한다. 조용히 스킵하거나 무기한 대기하지 않는다(빈 결과를 통과로 오독한 실사고와 같은 실패군).
- **판정**: 레드팀은 **지적만** 낸다. 통과/반려는 검증 주체가 판정한다(§6-5 표). 지적을 기각하려면 **근거**(제1원리 조항 / 코드 인용 / 실측치)를 대야 하고, 못 대면 기각이 아니라 미해결로 남긴다(`Docs/ConsultLoop.md` §3-1 기각 원장 규칙을 그대로 적용).
- **P1이 하나라도 남아 있으면 머지 금지.** P2는 고치거나 근거를 대고 기각. P3는 후속으로 넘겨도 된다.
- **결과 보관**: 지적과 처리 결과(수용/기각+근거)를 `Docs/Specs/<유닛>.md` **§13 레드팀 지적 원장**(명세가 없는 유닛이면 머지 커밋 메시지)에 남긴다. 별도 덤프 폴더를 만들지 않는다.
- ⚠️ **지적 0건은 통과 근거가 아니다.** 프라이머가 "무엇을 봤는지 + 안전하다고 보는 근거"를 대게 하므로, 그게 비어 있으면 리뷰가 안 돈 것으로 본다(빈 결과를 통과로 오독한 실사고 2026-08-07).

### 6-7. 브랜치 전략 (Phase 단위 워크플로)
**모든 작업 단위**는 `main`에 직접 커밋하지 않고 **전용 브랜치에서 작업 → 검증 통과 후 `main`에 머지**한다. (도입 2026-05-30. 이전 main 히스토리는 소급 적용하지 않음.)

> ⚠️ **적용 단위 정정 (2026-08-11, 레드팀 P2)** — 종전 이 절은 *"로드맵(§7-3)의 각 **P 단계**"* 에만 걸려 있었다. `Roadmap.md` §7-6이 **P 축을 종료하고 M(마일스톤) 축으로 넘긴** 뒤에도 이 문장을 그대로 두면, 문자 그대로 읽을 때 **M 배정 작업에는 브랜치 규율·머지 전 검증 게이트가 형식상 비적용**이 된다. 그래서 단위를 "P 단계" → **"작업 단위(= 보드 행 1건 또는 묶음, 마일스톤 배정분 포함)"** 로 넓힌다. 라이프사이클·검증·`--no-ff` 규칙은 **그대로**다.

- **브랜치명**: 마일스톤 작업 = `<type>/<키워드>`(§6-8 type 재사용, 예: `feat/status-effects`, `docs/release-milestones`) · 구 P 단계 = `phase/<단계소문자>-<핵심키워드>` (예: `phase/p2-spawndirector`)
- **머지**: `--no-ff` 머지 커밋(phase 경계가 main 히스토리에 보이도록)
- **원격**: phase 브랜치도 `origin`에 push(백업/리뷰 협업)

라이프사이클:
1. **분기** — `git checkout main` → `git checkout -b phase/<단계>-<키워드>` → `git push -u origin phase/<단계>-<키워드>`
2. **작업** — 해당 phase 구현·문서를 이 브랜치에서만 커밋(모델 배분 = §6-5. **코어/구조/리팩토링이면 §6-5-2 Opus 주도 + Fable 2게이트 5단계**)
3. **검증(머지 전 필수)** — 빌드(§6-6) → 헤드리스 스모크 → **(코어 갈래일 때만)** 레드팀 리뷰 게이트(§6-6-1 = **§6-5-2 게이트 ②**, Fable 서브에이전트 · 브랜치 diff). 그 외 갈래는 게이트 대신 `git diff` 자기비판으로 대체. 검증 없이 머지 금지(§6-3). **최종 판정 주체 = Opus**(하위 모델 위임 금지)이되, 코어 갈래는 **게이트 ②를 통과해야** 한다. **P1 잔존 시 머지 금지**
4. **핸드오프** — phase 완료/세션 중단 전 **PM 보드 행 갱신**(상태·담당·브랜치 + 인계 컨텍스트, §6-4·§6-9)
5. **머지** — `git checkout main` → `git merge --no-ff phase/<단계>-<키워드> -m "merge(phase): <단계> <요약> — 검증 통과"` → `git push origin main`
6. **정리** — `git push origin --delete phase/<단계>-<키워드>` + `git branch -d phase/<단계>-<키워드>`

> 전역 `claude/` 브랜치 클린업 정책과 prefix(`phase/`)로 분리되어 충돌 없음.

### 6-8. 커밋 메시지 컨벤션
형식: **`type(scope): <한 줄 요약>`** — Conventional Commits 콜론 형식. `[type]` 대괄호 금지(commitlint·git-cliff 등 툴 호환 + 기존 히스토리 일관).

- **type**(필수):

| type | 용도 |
|------|------|
| `feat` | 새 기능 추가 |
| `fix` | 버그 수정 |
| `content` | BP·DataAsset·umap 등 **콘텐츠** 변경(C++ 로직 아님 — §6-2 데이터 드리븐 경계) |
| `perf` | 성능 개선(기능 변경 없음 — 적 수백·성능예산이 제1원리, 원칙1) |
| `refactor` | 리팩토링(기능 변경 없음) |
| `docs` | 문서(`Docs/SSOT/`·`Game.md`·README 등) |
| `style` | 포맷팅·세미콜론 등(코드 동작 변경 없음) |
| `test` | 테스트(자동화·스모크) 추가·수정 |
| `chore` | 빌드·설정·툴(`.uproject`·`*.Build.cs`·gitignore·스킬·슬래시커맨드) |
| `plan` | 계획·신규 유닛 기록(플랜모드 산출물) |
| `merge` | `--no-ff` 검증 통과 통합 지점 마커(§6-7) |
| `revert` | 커밋 되돌림 |

- **scope**(권장): 작업 단위 ID(`U11a`·`V3`·`P7`) 또는 서브시스템(`camera`·`pm`·`gitignore`).
- **config 분류**: 게임플레이 값(`DefaultGame.ini` 밸런스 등) = `content` / 빌드·플러그인 설정(`DefaultEngine.ini`·`*.Build.cs`) = `chore`.
- **머지 커밋**: `merge(phase): <단계> <요약> — 검증 통과`(§6-7 라이프사이클 5와 동일).

예: `feat(U11a): 로비 허브/Steam 세션/Seamless 트래블` · `content(V0): 무기 DA 8종 비주얼/사운드 배선` · `perf(spawn): 플로우필드 갱신 주기 분할`.

##### (3) 작업 전 절차 (클레임)
1. **보드 조회**(위 SQL 1회) — 진행중 전체 + 대기·차단·결정대기.
2. **크리티컬 확인** — 미착수 크리티컬이 있으면 지금 요청과 무관해도 사용자에게 먼저 보고.
3. **행 확보** — 내 작업이 보드에 없으면 생성(상태=대기, 우선순위는 아래 (5)로 판단, 출처=사용자지시/에이전트발견).
4. **선행 확인** — `선행작업`이 미완료(완료 아님)면 착수 금지. 다른 작업을 고르거나 사용자에게 보고.
   - **마일스톤 순서 확인**((8) 개시 규칙) — 이 행의 `마일스톤`보다 앞선 마일스톤에 활성 행이 남아 있으면 기본값은 **그쪽 먼저**다. 당겨 쓰려면 예외 3가지 중 하나에 해당해야 하고 사유를 로그에 남긴다.
5. **병렬 충돌 검사** — 진행중 행들과 `주요경로`/`영역`이 겹치면 착수 전 사용자에게 보고(기본값 = 겹치면 대기).
6. **클레임** — 상태=진행중, `담당`=`<클론폴더>@<브랜치> · MMDD-키워드`, `브랜치` 기입.
7. **경합 확인** — 클레임 직후 행을 재조회해 `담당`이 나인지 확인(Notion엔 트랜잭션이 없다). 다른 세션이면 양보하고 1로.

##### (4) 작업 후 / 중단 시 절차
1. **상태 갱신** — 완료(검증 통과, `완료커밋`에 해시) / 검증중(사람 확인 대기) / 차단(사유를 로그에) / **폐기**(트랙을 접었거나 대상이 사라짐 — 판정 기준은 아래 (5)) / 핸드오프면 진행중 유지 + `담당` 비우고 재개 메모.
2. **로그 append** — 행 페이지에 1~3줄: 결과·커밋 해시·다음 단계. 인계 컨텍스트(검증법·함정·미커밋 콘텐츠)도 행 페이지 본문에(§6-4).
3. **파생 등록** — 작업 중 발견한 개선점=백로그, 실행 영향 있는 문제=하이/미듐/로우로 신규 행.
4. **후행 차단 해제** — 내 완료로 선행이 풀린 행이 있는지 확인. **내 완료로 그 마일스톤의 활성 행이 0이 되면 사용자에게 보고**((8) 상태 갱신 트리거).
5. 완료 상세 경위는 기존 관례대로 `Docs/WorkLog.md` 맨 위로(증상→해결은 `Docs/Troubleshooting.md`).

##### (5) 우선순위 규칙 (5단계)
| 등급 | 의미 | 부여 주체 |
|---|---|---|
| **크리티컬** | 사용자가 지시하는 긴급사항 — 존재 시 무조건 최우선 착수 | **사용자 전용** (에이전트 부여·강등 금지) |
| **하이** | 현재 트랙을 막거나 게임 실행/검증을 막는 것 | 담당 에이전트 판단 |
| **미듐** | 현재 트랙 범위 내 일반 작업 | 담당 에이전트 판단 |
| **로우** | 범위 밖이거나 급하지 않음 | 담당 에이전트 판단 |
| **백로그** | 실행상 문제 없으나 개선할 점(리팩토링 후보·문서 드리프트 등) | 누구나 등록 |

- 승격/강등은 사용자(PM) 권한 — 에이전트는 로그에 제안만 남긴다.
- 상태 축: 대기 / 진행중 / 검증중 / **결정대기**(사용자 결정 필요 — PM 인박스 뷰) / 차단 / 보류 / 완료 / **폐기**.
- **완료 vs 폐기 (2026-08-11 신설, 사용자 결정)** — 종전엔 `폐기`가 없어 폐기 건도 `완료`로 넣고 사유를 본문에 적는 우회를 썼다.
  그러면 나중에 "완료 = 실제로 한 것"으로 셀 수 없다. 이제 갈라 쓴다.
  - **완료** = 이 행이 맡은 일을 **실제로 해냈다**. `완료커밋`에 해시. — 범위 조정으로 남은 일을 신규 행으로 뺀 경우도 **완료**(맡은 부분은 끝났다). 조사만 하고 "문제 없음"으로 닫은 것도 **완료**(결론을 냈다).
  - **폐기** = **산출물 없이 트랙을 접었거나**, 대상이 사라져 **할 수 없게 됐다**(브랜치·코드 부재, 상위 결정으로 트랙 종결). `완료커밋`은 비우거나 `폐기(사유 요약)`.
  - 폐기 시 **사유를 행 본문에 반드시** 남긴다(왜 접었는지 + 되살리려면 무엇이 필요한지).
  - **되살릴 땐 그 행을 재사용하지 말고 신규 행**으로 연다 — 접힌 뒤 코드가 달라져 스펙을 다시 써야 하기 때문이다.

> 🔒 **이 경계는 도구 화이트리스트로는 강제되지 않는다.** `notion-update-page` 하나가 `insert_content`와 `update_properties`를 `command` 인자로 가르기 때문에, 도구 이름 단위 화이트리스트는 둘을 구분하지 못한다. 그래서 `PreToolUse` 훅(`Scripts/pm-board-guard.ps1`)이 `agent_type == "pm-board"`이고 `command != "insert_content"`일 때 `permissionDecision: "deny"`를 낸다. 훅 입력의 `agent_type`/`agent_id`는 **서브에이전트 안에서 발화할 때만** 채워지므로 메인 세션의 정당한 갱신은 통과한다. 입력 파싱에 실패하면 호출 주체를 알 수 없으므로 `deny`도 `allow`도 아닌 `ask`(사용자에게 물음)로 처리한다.
>
> ⚠️ **훅 배선은 공유되지 않는다.** `.claude/settings.json`은 `.gitignore` 대상(머신 로컬)이라 **스크립트만 커밋되고 배선은 클론마다 수동**이다. 배선이 없는 클론에서는 위 경계가 **에이전트 정의의 규칙일 뿐 도구 강제가 아니다.** 새 클론에서 켜려면 `settings.json`의 `hooks.PreToolUse`에 matcher `mcp__.*__notion-update-page`로 `Scripts/pm-board-guard.ps1`을 물린다.
