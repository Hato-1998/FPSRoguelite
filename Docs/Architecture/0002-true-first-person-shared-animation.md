# 0002. True First Person + 3P 애니메이션 단일화

- 상태: 채택
- 날짜: 2026-07-29
- 되돌리기 비용: 비쌈

## 맥락

무브먼트([ADR 0001](0001-player-movement-state-ownership.md))가 끝나고 **캐릭터 애니메이션을 배선할 차례**가 되었다. 그런데 배선하기 전에 구조를 먼저 바꿔야 한다는 것이 사용자 판단이었다 — **1인칭과 3인칭을 3인칭 애니메이션 에셋 한 벌로 다 덮기 위해서**다.

지금 구조는 그 반대로 되어 있다.

| | 현재 |
|---|---|
| 본인이 보는 것 | `FirstPersonArms`(`SK_FP_Manny_Simple`) + 1P 무기, 둘 다 `OnlyOwnerSee` |
| 남이 보는 것 | 3P 바디(`Blu_-_Rigged_Non_Constraint`) + `WeaponMesh3P`, 둘 다 `OwnerNoSee` |
| 카메라 | 캡슐의 자식, `Z = BaseEyeHeight` 고정 |
| 팔의 부모 | **카메라** ([FPSRCharacter.cpp:94-95](../../Source/FPSRoguelite/Private/Hero/FPSRCharacter.cpp)) |

즉 **1P와 3P가 메시도 애니메이션도 완전히 따로**다. 3P 애니 팩 한 벌로 양쪽을 덮으려면 이 분리를 없애야 하고, 그러면 카메라·ADS·무기 데이터·관전이 전부 딸려 온다. 코드를 쓰기 전에 방식을 확정해야 했다.

## 목표와 비목표

**목표**

- 1인칭·3인칭을 **3P 애니메이션 에셋 한 벌**로 덮는다
- True First Person — 본인도 자기 몸을 본다
- 로컬 플레이어만 머리를 숨긴다
- 디버깅용 3인칭 카메라(스프링암) — 이후 **사망 후 아군 관전 카메라**로 승격
- 슬라이딩 애니메이션 직접 저작
- 4인 협동 · 리슨 서버 · 서버 권위 (ADR 0001과 동일)

**비목표** (사용자 확정)

- **1P 전용 팔 메시를 유지하지 않는다.** `FirstPersonArms` + `SK_FP_Manny_Simple` 폐기
- **PWAS(Procedural Weapon Animation System, 유료 구매분)를 쓰지 않는다.** 통째로 폐기
- **무기 DataAsset의 1P/3P 이원화 필드를 유지하지 않는다.** 한 벌로 통합
- **벽 매달리기·등반·벽점프·턱 넘김·에어 스트레이프 애니메이션은 이번 범위가 아니다.** 슬라이딩만 저작
- **루트모션을 쓰지 않는다.** 애니가 위치를 소유하면 ADR 0001 불변식 1·2와 정면 충돌
- **디버그 3P 카메라를 켠 상태의 사격 정확성은 보장하지 않는다.** 개발자용 토글이며, 그 상태의 사격 이상은 버그로 취급하지 않는다

**규모 상한** — 동시 플레이어 4명, 전용 서버 없음(리슨 서버), 적 동시 200~300. ADR 0001과 동일하며 이 결정으로 바뀌지 않는다. 플레이어 애니메이션 비용은 4명 상한이고 적은 이 경로를 쓰지 않는다(프로젝트 원칙 1).

## 불변식

어떤 세부 결정도 아래를 위반할 수 없다.

| # | 불변식 |
|---|---|
| 1 | **캡슐의 회전은 시선이 정한다.** 애니메이션은 메시의 상대 회전만 만든다 |
| 2 | **사격 원점과 화면 카메라는 항상 같은 값이고, 그 값은 캡슐 축에서 반지름 이상 멀어지지 않는다** (2026-07-29 4차 정정 — 원문은 "캡슐 밖으로 나가지 않는다"였으나 스탠스 블렌드가 앉기마다 위반해 왔다. 벽 너머 사격을 막는 건 높이가 아니라 반지름이다. 아래 "축 2 공식 수정" 절) |
| 3 | **애니메이션은 이동 상태를 소유하지 않는다** (ADR 0001 불변식 6 계승) |
| 4 | **로컬 플레이어와 원격 관측자는 같은 메시·같은 애님 그래프를 본다.** 다른 것은 머리 가시성과 카메라뿐이다 |
| 5 | **머리를 숨기는 조건은 "이 폰의 눈으로 보고 있는가"다.** "로컬 플레이어인가"가 아니다 |
| 6 | **관전 리그는 관전 대상과 독립이다.** 각도·거리는 보는 쪽이 소유하고, 대상이 없어도 리그는 남는다 |
| 7 | **애니메이션 노티파이가 게임플레이 상태를 바꾸지 않는다** |
| 8 | **애니메이션 상태는 복제하지 않는다** |
| 9 | **런타임 코드는 본 이름을 알지 않는다** |
| 10 | **카메라 위치는 프레임당 한 번만 쓰인다** |

### 불변식 2의 전제 (중요)

이 불변식은 **"살아 있는 플레이어의 뷰 타겟은 언제나 자기 눈 앵커다"** 에 의존한다.

`확인됨` — `AActor::CalcCamera` (엔진 소스 `Engine/Source/Runtime/Engine/Private/Actor.cpp:3661-3680`)는 **첫 번째 `IsActive()` 카메라 컴포넌트**를 쓰고 `bFindCameraComponentWhenViewTarget`은 기본 `true`(`Actor.cpp:318`)다. 그리고 사격 원점은 [Hitscan GA:197](../../Source/FPSRoguelite/Private/AbilitySystem/Abilities/FPSRGA_WeaponFire_Hitscan.cpp)의 `Controller->GetPlayerViewPoint()` = **화면 카메라 그 자체**다(`PlayerController.cpp:1013-1016`).

따라서 살아 있는 플레이어의 뷰 타겟이 눈 앵커가 아니면 사격 원점이 그리로 따라간다. 개발 빌드의 디버그 3P는 이 전제를 깨지만 **출시 빌드에 없으므로 감수한다**(비목표).

> **전제를 깨는 기능을 시핑에 넣으려 하면 이 불변식을 먼저 다시 봐야 한다** — 킬캠, 처치 연출 카메라, 살아 있는 채로 하는 관전, 포토 모드가 전부 "살아 있는데 뷰 타겟이 딴 데"다.

### 각 불변식이 막는 사고

- **1번** — 이동 입력이 캡슐 방향 기준이다([FPSRCharacter.cpp:719·734](../../Source/FPSRoguelite/Private/Hero/FPSRCharacter.cpp)). 캡슐 요를 애니메이션이 만들기 시작하면 W가 "보는 쪽"이 아니라 "몸이 향한 쪽"으로 가고, 벽점프 방향([CMC:406](../../Source/FPSRoguelite/Private/Hero/FPSRCharacterMovementComponent.cpp))·슬라이드 조향([CMC:874](../../Source/FPSRoguelite/Private/Hero/FPSRCharacterMovementComponent.cpp))·후진 판정([CMC:909](../../Source/FPSRoguelite/Private/Hero/FPSRCharacterMovementComponent.cpp))이 전부 한 프레임 어긋난다. CMC:406의 기존 주석이 근거를 이미 적어 두었다 — *"the pawn's rotation is part of the replicated move, so client and server agree"*. 캡슐 회전이 애니 산출물이 되면 그 문장이 거짓이 되고 예측이 깨진다.
- **2번** — 아래 실패 흐름 ① 참조.
- **5번** — "로컬 플레이어인가"로 걸면 디버그 3P와 DBNO 3P에서 **머리 없는 캐릭터**가 보인다.
- **7번** — 재장전 완료·발사·장착 완료를 노티파이가 결정하면 몽타주 미할당·블렌드아웃 중 취소·프레임 드랍에서 상태가 영영 안 끝난다. ADR 0001 불변식 6은 *이동 상태*만 덮는데, 재장전·장착도 같은 사고를 낸다. 지금은 이미 옳게 되어 있다 — `ReloadTime`이 주인이고 몽타주가 재생속도로 맞춰진다(`Docs/AnimationPass_ContentGuide.md`). **명문화 비용 0.**
- **8번** — 하체 요 오프셋을 복제하면 4명×매 프레임 대역폭이 늘고, 서버 보정으로 캡슐이 되감길 때 오프셋은 안 되감겨 발이 미끄러진다. ADR 0001이 안 ㉯를 기각한 것과 같은 형태의 사고다.
- **9번** — `HideBoneByName`은 없는 이름에 **아무 일도 안 하고 조용히 실패한다**(`GetBoneIndex` → `INDEX_NONE` → return, 로그 없음). 이 프로젝트는 캐릭터를 이미 두 번 바꿨다(Infima 팔 → 마네킹 팔, BroBot → Blu).
- **10번** — 지금 이미 두 곳에서 카메라를 쓴다(`UpdateStanceCamera` = 캐릭터 Tick, `UpdateAimDownSights` = WeaponFire Tick). 눈 앵커와 ADS 보정이 더해지면 네 곳이 되고 순서에 따라 결과가 달라진다. `UpdateAimDownSights`의 기존 주석이 함수 안에서 이미 같은 규칙을 지키고 있다 — *"Fixed order: base → ADS blend → hip additive → write once"*. 그 규칙을 함수 밖까지 넓히는 것이다.

## 검토한 대안

논의는 축 넷으로 갈렸다.

### 축 1 — 상하체 회전

#### 안 ㉮ — 완전 결합 (현행 유지) **[기각]**

`bUseControllerRotationYaw = true`로 몸 전체가 카메라 요를 즉시 따라간다.

장점: 카메라가 단순하고 구현이 싸다.

**기각 사유 — 팩의 절반이 죽는다.** `Turn_In_Place_L/R_Loop` 4종, `Stand_Relaxed_L_45/90/135/180` 류 제자리 회전 16종, `Stand_Relaxed_To_Jog_L45_Fwd` 류 8방향 시작 전환 40종+ 는 전부 **몸의 방향 ≠ 시선 방향일 때만** 재생된다. 완전 결합에서는 그 각도 오차가 항상 0이라 **한 번도 재생되지 않는다.** 3P 관측자 눈에도 게걸음/미끄러짐으로 보인다.

#### 안 ㉯ — 물리 회전 분리 **[기각]**

`bUseControllerRotationYaw = false`로 캡슐 자체를 지연 회전시킨다.

**기각 사유 — 이동이 깨진다.** 위 "불변식 1이 막는 사고" 참조. W를 누르면 보는 쪽이 아니라 몸이 향한 쪽으로 가고, 몸은 늦게 따라오니 계속 어긋나 **원을 그리며 흐른다.**

#### 안 ㉰ — 시각 회전 분리 **[채택]**

캡슐 요는 시선에 즉시 붙여 두고(현행 그대로), **하체 지연은 메시 컴포넌트의 상대 요를 AnimBP가 반대로 돌려서** 만든다. 상체는 Aim Offset이 시선 정렬.

`일반적 패턴` — Lyra·ALS의 `RootYawOffset` 방식. 이 엔진 버전에서 직접 대조하지는 않았다.

장점: 팩의 회전·시작 전환이 전부 살아나면서 **이동 코드는 한 줄도 안 바뀐다.**
단점: 하체 회전이 순수 시각이라 충돌에 반영되지 않는다 — 캡슐이 원기둥이라 애초에 방향이 없으므로 실질 손해가 아니다.

### 축 2 — 카메라 위치의 규칙

#### 안 ㉮ — 눈 앵커: 캡슐 소유, head 본은 참고값 **[채택]**

카메라는 캡슐의 자식으로 남는다. head 본이 준 위치를 캡슐 중심 기준 오프셋으로 바꿔 **감쇠 계수를 곱하고 캡슐 안으로 클램프**한 뒤 적용.

장점:
- 벽 뚫기가 **구조적으로 불가능**하다 (클램프 대상이 캡슐 = 충돌 형상)
- 감쇠 0 = 현행과 완전히 동일 → **되돌리기가 값 하나**
- 시야와 사격 원점이 끝까지 같은 값이라 "보이는데 안 맞는다"가 생기지 않는다

단점: 몸 흔들림이 시야에 100%로는 오지 않는다. True FPS의 시각 이득이 감쇠 비율만큼으로 줄어든다. **이것은 미해소로 남긴다**(아래 반론 절 참조).

#### 안 ㉯ — head 소켓 직결 + 사격 원점 분리 **[기각]**

카메라를 head 소켓에 직결하고, 사격 원점은 `GetPlayerViewPoint` 대신 캡슐 파생 결정값으로 따로 뽑는다.

장점: 가장 "진짜" 시야.

**기각 사유 — 더 나쁜 것이 생긴다.** 화면이 벽을 뚫고 나간 순간 **보이는 곳과 쏘는 곳이 갈라진다.** 적이 화면에 보이는데 총알은 벽에 맞는다. FPS에서 가장 나쁜 종류의 버그이고, 플레이어가 원인을 알 수 없다. 코드 변경 범위도 더 크다(GA 3종 + 크로스헤어 + 반동 미리보기).

부수적으로, 이 안은 서버의 사격 원점 권위를 바꾼다 — 현재는 클라가 보고한 카메라 위치(`ServerUpdateCamera` → `FillCameraCache`, `ClientNetCamUpdateDeltaTime = 0.0166` = 사실상 매 프레임)를 쓰는데, 캡슐 파생값으로 바꾸면 **서버가 자기 시뮬 위치**를 쓰게 된다. 오차 크기는 측정하지 않았다(`판단`).

#### 안 ㉰ — 카메라를 현행 그대로 (캡슐 고정 높이) **[기각]**

가장 안전하고 작업량이 가장 적다. 감쇠 0인 ㉮와 같다.

**기각 사유 — 채택할 필요가 없다.** ㉮의 감쇠를 0으로 두면 정확히 이 안이 된다. 별도 안으로 유지할 실질 차이가 없어 ㉮에 흡수했다.

### 축 3 — ADS 정렬의 주인

현재 [UpdateAimDownSights](../../Source/FPSRoguelite/Private/Hero/FPSRCharacter.cpp)는 매 프레임 **팔 컴포넌트 전체의 트랜스폼을 역산해 덮어쓴다.** 무기 `AimSocket`을 카메라 정면 `ADSSightDistance`에 정확히 올려놓고, 그 부작용으로 흔들림·바브까지 사이트에서 상쇄한다 → **조준점 완전 고정.**

이것이 성립하는 이유는 팔이 카메라의 자식이라 자유롭게 움직일 수 있어서다. True FPS로 가면 **의존 방향이 뒤집혀** 몸 전체를 옮겨 사이트를 맞출 수 없다.

| 안 | 내용 | 판정 |
|---|---|---|
| ㉮ 애니메이션이 소유 | 팩 조준 포즈 그대로. 무기별 카메라 오프셋만 저작 | 기각 — 조준점 고정이 완전히 사라짐 |
| ㉯ 절차 정렬 유지 | 역산 대상을 팔 컴포넌트 → 상체 본 수정 노드로 이사 | 기각 — 난이도 최상, 모듈러 사이트 파츠 배선을 다시 풀어야 함 |
| **㉰ 혼합** | 팩 포즈를 기본으로 두고, 사이트가 중앙에서 벗어난 **잔여 오차만** 보정 | **채택** |

**보정 주체(카메라냐 상체 본이냐)는 구현 시점으로 미룬다.** 리타게팅 후 실제 오차 크기를 봐야 정할 수 있고, 아래 제약이 있으면 어느 쪽을 골라도 구조를 깨지 않는다.

> **제약** — ADS 보정을 카메라로 하든 상체 본으로 하든, **결과 카메라 위치는 캡슐 클램프를 통과해야 한다.** 보정을 클램프 앞에 두면 안 된다. (그렇게 하면 불변식 2가 ADS 경로로 되살아나 깨진다.)

### 축 4 — 관전 카메라의 소유

#### 안 ㉮ — 관전당하는 폰이 스프링암을 갖는다 **[기각]**

**기각 사유 — 관전자 둘이 충돌한다.** A·B 둘 다 다운, 둘 다 C를 관전. 스프링암은 C에 하나뿐이므로 **A가 마우스를 돌리면 B의 화면도 같이 돈다.** 예외가 아니라 항상 일어난다.

#### 안 ㉯ — 관전자가 소유하는 리그 액터 **[채택]**

`SetViewTarget` 대상이 폰이 아니라 리그가 된다. 디버그 3P도 같은 리그가 "자기 폰"을 보는 특수 경우로 처리한다.

원래 이 안은 비쌌다 — `bOnlyOwnerSee`/`bOwnerNoSee`가 **뷰 타겟 기준**으로 평가되기 때문이다([FPSRCharacter.cpp:1264](../../Source/FPSRoguelite/Private/Hero/FPSRCharacter.cpp)의 기존 주석이 이 함정을 이미 기록해 두었다). 그런데 **1P 전용 팔을 폐기하기로 하면서 `OnlyOwnerSee` 메시가 하나도 안 남아** 문제가 통째로 사라졌다. 비목표 하나가 다른 결정의 비용을 없앤 사례다.

## 근거

**왜 눈 앵커(축 2 ㉮)인가.** 이 게임은 적 200~300이 밀착하고 부서지는 문이 있어 **벽 밀착이 예외가 아니라 일상**이다. 사격 원점이 화면 카메라 그 자체라는 사실(불변식 2의 전제 절 참조)이 확인된 이상, 카메라가 캡슐을 벗어날 수 있는 구조는 벽 너머 사격을 허용한다. 클램프를 캡슐(= 충돌 형상)에 걸면 그 경로가 구조적으로 닫힌다.

**무엇을 포기했는가.** True First Person의 시각 이득 — 몸 흔들림이 시야에 오는 정도 — 이 감쇠 비율만큼으로 줄어든다. 감쇠를 1.0에 가깝게 올릴수록 클램프에 자주 걸려 시야가 튄다. 즉 **"진짜 같은 시야"와 "시야가 안 튀는 것"을 동시에 가질 수 없고, 후자를 택했다.**

**왜 시각 회전 분리(축 1 ㉰)인가.** 팩이 요구하는 것(몸이 시선을 늦게 따라감)과 이동 코드가 요구하는 것(캡슐 방향 = 시선 방향)이 정면 충돌한다. 회전을 두 층으로 나누면 — 캡슐은 즉시, 메시는 지연 — 양쪽이 각자 원하는 것을 얻는다. 이동 코드를 한 줄도 안 고치는 것이 이 안의 핵심 가치다.

**엔진 확장 지점을 버리는 것이 아니다.** 머리 숨김은 엔진의 `HideBoneByName`, 카메라는 엔진의 `CalcCamera` 분기, 하체 오프셋은 AnimBP의 표준 기능이다. 새로 만드는 것은 눈 앵커 규칙 하나뿐이다.

## 전환 조건

무엇이 참이 되면 이 결정을 다시 봐야 하는가.

- **눈 앵커의 감쇠를 0.7 이상으로 올려도 멀미가 없고 캡슐 클램프가 눈에 띄게 시야를 끊지 않을 때** — ㉯(head 소켓 직결)의 이득이 실재한다는 뜻이므로 재검토.
- **반대로 클램프가 자주 걸려 시야가 튈 때** — 감쇠를 낮춰 사실상 현행 고정 카메라로 수렴한다. 그 경우 *"True FPS로 바꿔서 얻은 것이 몸이 보이는 것뿐"* 임을 인정하고 여기에 추가 기록한다.
- **살아 있는 플레이어의 뷰 타겟이 눈 앵커가 아닌 기능을 시핑에 넣을 때**(킬캠·연출 카메라·살아 있는 채로 관전·포토 모드) — 불변식 2를 먼저 다시 본다.
- **리타게팅 후 왼손 오차가 IK로 못 덮을 만큼 클 때** — 캐릭터 메시 또는 애니 팩 선택 자체를 다시 봐야 한다.
- **플레이어 캐릭터를 또 교체할 때** — 불변식 9(본 이름을 코드에 두지 않는다)가 지켜졌다면 데이터 교체로 끝난다. 지켜지지 않았다면 그것이 먼저다.

## 검증 시나리오

### 정상 흐름 — 조깅 중 90° 우회전 → ADS → 사격 → 다운 → 관전 → 부활

| 단계 | 캡슐 | 메시(AnimBP) | 눈 앵커 | 사격 원점 |
|---|---|---|---|---|
| 회전 시작 | **즉시 90° 회전**(컨트롤 요) | 상대 요 = −90 → 몸은 아직 예전 방향, 다리가 `Turn_In_Place_R_Loop` | head 본이 좌우로 흔들림 → 감쇠·클램프 | = 카메라. 캡슐 안 |
| 회전 수렴 | 그대로 | 상대 요 → 0. 상체는 Aim Offset이 계속 시선 정렬 | 흔들림 감소 | 동일 |
| ADS | 그대로 | `W2_Stand_Aim_Idle` 포즈 → 사이트가 화면 중앙 근처 | 잔여 오차 보정 (**클램프 안에서**) | 동일 |
| 사격 | 그대로 | 발사 몽타주 | 반동은 컨트롤 로테이션에 (현행 유지) | 동일 |
| 다운 | 정지 | 다운 포즈 | — | — |
| 관전 | — | 아군 몸 **머리 있음** (내 눈이 아니므로 — 불변식 5) | 관전 리그가 소유 | — |
| 부활 | 복귀 | 머리 숨김 재적용 | 자기 폰으로 복귀 | 복귀 |

**이동·벽감지·슬라이드 코드가 한 단계에서도 등장하지 않는다.** 캡슐 회전이 안 바뀌었기 때문이며, 이것이 축 1 ㉰가 옳다는 증거다.

### 실패 흐름 ① — 벽에 등 붙이고 재장전

캡슐 반지름 34 / 반높이 88. Blu의 `head` 본은 **발에서 155.1cm**(에디터 실측 2026-07-29) = 캡슐 중심에서 +67.1. 원기둥 구간이 ±54이므로 반구에 13.1 들어간 지점이고, 그 높이의 캡슐 반지름은 √(34² − 13.1²) ≈ **31.4cm**.

> 최초 작성 시 이 값을 "발에서 약 165cm → 반지름 25cm"로 **추정**해 적었다. 실측으로 정정한다 — 여유가 문서보다 6cm 넓다. 구멍이 사라진 것은 아니고 더 큰 상체 기울임을 요구할 뿐이므로 아래 결론은 유지된다.

| 시각 | 일어나는 일 | 안 ㉮ (채택) | 안 ㉯ (기각) |
|---|---|---|---|
| t=0 | 벽 밀착. 캡슐이 벽에 막힘 | 정상 | 정상 |
| t=1 | 재장전 애니가 상체를 숙임 → head 본이 캡슐 경계를 넘음 | 오프셋 계산됨 | 카메라가 벽을 뚫고 나감 |
| t=2 | | **클램프가 캡슐 표면에서 멈춤** | 화면에 벽 반대편이 보임 |
| t=3 | 그 상태에서 발사 | 원점이 캡슐 안 → 벽에 맞음 | **적이 보이는데 총알은 벽에 맞음** |

㉮의 결과를 **수용한다.** 시야가 앞으로 나가다 멈추는 것은 어색하지만 규칙이 하나고("카메라는 캡슐을 못 나간다") 플레이어가 원인을 알 수 있다. ㉯의 결과는 원인을 알 수 없다.

### 실패 흐름 ② — 관전 중 대상이 사라진다

| 시각 | 서버 | A(관전자) 화면 |
|---|---|---|
| t=0 | A 다운, C를 관전 | C의 뒤 3P |
| t=1 | C도 다운 | 리그가 다음 Alive를 찾음 |
| t=1 | **Alive가 아무도 없음** | ← 구멍 |
| t=2 | A가 부활 | 리그 → 자기 폰 복귀 |

`확인됨` — 현재 코드 [FPSRReviveComponent.cpp:226](../../Source/FPSRoguelite/Private/Hero/FPSRReviveComponent.cpp)는 `if (Best && Best != SpectatedPawn)`이라 **Best가 없으면 아무것도 안 하고 마지막 대상을 계속 본다.** 그 대상이 다운되어 누워 있으면 팀 와이프 직전 몇 초 동안 전원이 시체를 본다.

리그 방식에서는 더 나빠진다 — 리그가 대상 폰을 따라다니므로 **대상이 파괴되면 리그가 붕 뜬다.**

→ 리그는 **"대상 없음"을 정식 상태로 가져야 한다**(마지막 위치에 정지 + 자유 회전). 불변식 6의 후반절("대상이 없어도 리그는 남는다")이 이것을 강제한다. 리그가 대상 폰에 붙어 있으면 애초에 이 상태를 가질 수 없다.

## 논의 중 제기된 반론

### 반론 1 — "디버그 3P 카메라로 쏘는 건 상정하지 않아도 된다" (사용자) → **수용, 판정을 뒤집음**

검토자는 디버그 3P를 켠 채 벽 뒤에서 쏘면 벽을 통과한다는 것을 지적하고, 불변식 2를 "사격 원점을 주는 것은 눈 앵커 하나다"로 정정하려 했다.

사용자가 두 근거를 제시했다.

1. 디버그 3P는 **에디터/개발자용 체크박스**이며 출시 기능이 아니다. 그 상태의 사격 이상은 버그로 치지 않는다.
2. 관전자는 관전 대상의 사격 원점이 1P냐 3P냐를 신경 쓰지 않는다.

둘 다 새 정보라 판정을 뒤집었다. **근거 2는 코드로 확인했다** — 관전자는 DBNO 상태고 [FPSRCharacter.cpp:649](../../Source/FPSRoguelite/Private/Hero/FPSRCharacter.cpp)의 `IsIncapacitatedLocal()`이 사격·교체·재장전·ADS를 전부 막는다. **관전 경로에는 애초에 사격이 없다.**

다만 사용자가 붙인 조건("코드가 복잡해진다면")을 검증한 결과 **비용 0짜리 길이 있었다** — 디버그 모드를 개발 빌드 한정으로 두는 것. 그래서 불변식을 지우는 대신 **전제를 명시하는 형태로 남겼다**(불변식 2의 전제 절). 지우면 나중에 킬캠·연출 카메라가 조용히 같은 구멍을 만들 때 검사에 안 걸린다.

### 반론 2 — 검토자의 오류: "3P 카메라를 리그로 옮기면 사격 원점 문제가 해결된다" → **철회**

틀렸다. 리그가 뷰 타겟이 되면 `GetPlayerViewPoint`는 그 리그의 카메라를 돌려준다. 문제가 고쳐지는 것이 아니라 캐릭터에서 리그로 **옮겨갈 뿐**이다.

리그로 가는 결정 자체는 유효하지만, 근거는 **관전자 둘이 같은 스프링암을 돌려 서로의 화면이 같이 돈다**는 것 하나뿐이고 사격 원점은 근거가 아니었다.

### 반론 3 — 검토자의 오류: 무기 DA 통합을 `비쌈`으로 판정 → **정정**

"기존 무기 DataAsset 전부 마이그레이션 필요"라고 판정했으나, 9개를 전수 조사하니 **3P 필드가 어디에도 저작되어 있지 않았다.** 잃을 데이터가 0이므로 `저렴`이다. 추정으로 비용을 판정한 오류다.

### 미해소로 남기는 것

**True FPS의 시각 이득이 감쇠 비율만큼으로 줄어든다.** 안 ㉮를 택한 대가이며 해소되지 않았다. "진짜 같은 시야"와 "시야가 안 튀는 것"은 동시에 가질 수 없고, 이 결정은 후자를 택했다. 감쇠 초기값을 정하고 PIE로 확인한 뒤 위 "전환 조건"에 따라 재평가한다.

### 불변식 후보였으나 올리지 않은 것 (D4 재수확 결과)

| 후보 | 안 올린 이유 |

## 알려진 비용 — 리타게팅

`확인됨` — 팩과 캐릭터의 스켈레톤이 다르다.

| | UE4 Mannequin (팩) | Blu (플레이어) |
|---|---|---|
| 골반 | `pelvis` | `hips` |
| **척추** | `spine_01` / `02` / `03` — **3개** | `spine` / `chest` — **2개** |
| 목 | `neck_01` | `neck` |
| 어깨 | `clavicle_l/r` | `shoulder_L/R` |
| 팔 | `upperarm_l` / `lowerarm_l` | `upper_arm_L` / `lower_arm_L` |
| 발끝 | `ball_l` | `toes_L` |

이름 규칙도 계층 개수도 다르므로 **IK Rig 2개 + IK Retargeter를 손으로 매핑**해야 한다. 자동 매칭은 성립하지 않는다.

예상되는 두 가지 어긋남:

1. **조준 오프셋** — 척추 3→2 압축은 리타게터가 처리하지만, 상하 조준 각도가 척추에 분배되는 비율이 달라진다. `W2_Stand_Aim_Point_U90`을 옮기면 Blu는 허리가 덜 젖혀지고 목이 더 꺾여 총구 방향과 화면 중앙이 어긋난다.
2. **왼손** — 소총은 양손 무기다. 총은 오른손 소켓을 따라가지만 팩의 왼손 위치는 UE4 마네킹 팔 길이 기준이다. 애니 비례의 Blu로 옮기면 왼손이 총열 그립에서 뜨거나 관통하고, 그 양이 애니마다 다르다. → **왼손 IK가 필수**이며 이 작업 비용의 상당 부분이다.

## 구현 결과 — 리타게팅 스파이크 (2026-07-29, 같은 날 이어서)

결정을 코드/에셋으로 옮기기 전에 **"알려진 비용 — 리타게팅"** 절의 미지수를 실측했다. 결정 자체는 유효하며 아래는 그 위에서 드러난 사실이다.

### 왜 지금 쟀는가

"전환 조건"에 *리타게팅 후 왼손 오차가 IK로 못 덮을 만큼 크면 캐릭터 메시 또는 애니 팩 선택을 다시 본다*고 적어 두었다. 이것이 **확정된 결정을 뒤집을 수 있는 유일한 미지수**였으므로 구현 착수 전에 확인했다. 나머지 미결 7건은 값 튜닝이라 뒤집히지 않는다.

### 만든 에셋 (구현에 그대로 쓴다)

```
/Game/Characters/Retarget/
  IK_UE4Mannequin      자동 생성 20체인
  IK_Blu               자동 생성 실패 → 20체인 손 정의
  RTG_UE4Man_to_Blu    20/20 매핑 + 자동 정렬
  _Spike/Blu_W2_*      검증용 리타게팅 4종 (삭제 가능)
```

`apply_auto_generated_retarget_definition()`은 마네킹에서 20체인을 전부 찾았지만 **Blu에서는 척추·목·머리 3개만** 만들었다(이름 규칙 불일치). 20개를 손으로 정의했다. 자동 정렬(`auto_align_all_bones`)이 양 상완에 넣은 **롤 −47°** 는 실측한 A/T 포즈 차이 46.9°와 일치했다.

### 실측 — 골격 비교

| | Blu | UE4 마네킹 | 비율 |
|---|---|---|---|
| 키 | 184.0 | 182.6 | **1.008** |
| 다리 | 81.4 | 82.8 | 0.983 |
| **팔 (상완+전완)** | **41.5** | **57.3** | **0.725** |
| 상완 | 19.9 | 30.3 | 0.656 |
| 척추 (골반→목) | 50.0 | 59.9 | 0.835 |
| `head` 본 높이 | **155.1** | 165.5 | 0.937 |
| 레퍼런스 포즈 | 2.6° = **T-pose** | 49.5° = **A-pose** | — |

**키와 다리는 사실상 같고 팔만 27.5% 짧다.** 그래서 로코모션은 잘 옮겨지고 무기 파지만 문제가 된다.

### 실측 — 리타게팅 후 두 손 간격

소총은 강체라 **두 손 사이 거리가 무기 형상으로 고정**된다. 이것이 판정 기준이다.

| 애니 | 두 손 간격 | 왼팔 뻗음 | 팔 여유 (최대 41.54) |
|---|---|---|---|
| `Stand_Aim_Idle` | 18.92 | 36.10 | 5.44 |
| `Crouch_Aim_Idle` | 20.72 | 35.80 | 5.74 |
| **`Jog_Aim_F_Loop`** | 20.50 | 39.37 | **2.17** ← 가장 빠듯 |
| `Stand_Aim_Reload` | 18.92 | 36.10 | 5.44 |

리타게팅 자체는 건전하다 — 발 높이가 레퍼런스와 정확히 일치(15.13)하고 본 길이가 보존된다.

### 검토자의 오류 2건 (기록으로 남긴다)

**① "왼손 IK로 8cm 부족" → 틀림. 팩의 M4로 계산했다.**

애니를 저작한 팩의 M4는 **전장 83.5cm의 리얼 비례**라 두 손을 32.48cm 벌린다. 그 값으로 재면 Blu는 8cm 모자란다. 그러나 **실제 게임 무기는 Synty 모듈러(전장 77.7cm, 스타일라이즈드)** 이고 요구 간격이 훨씬 짧다. *애니가 전제한 무기*와 *실제 장착할 무기*를 구분하지 않은 것이 원인이다. 구조 판정을 하기 전에 **실제 사용 에셋을 먼저 확인해야 한다.**

**② 마운트 소켓을 본 스페이스로 읽어 조립 좌표를 틀리게 봤다.** 스켈레탈 메시의 소켓 `relative_location`은 부모 본 기준이라 컴포넌트 좌표가 아니다. 액터를 실제로 스폰해 월드 좌표를 읽고서야 맞았다. **좌표계 추론 대신 조립해서 재는 편이 빠르고 옳다.**

### 실측 — Synty 소총 조립 좌표 (그립 마운트 = 원점, +Y 전방)

| 부위 | 위치 |
|---|---|
| 그립 (오른손) | (0, 0, 0) |
| 스톡 | (0, −7, 0) |
| 트리거 | (0, 6, 4) |
| 리드닷 / `SOCKET_Aim` | (0, 7.11, 12.62) / (0, 11.11, 17.12) |
| 매거진 | (0, 16, −5) |
| 배럴 | (0, 22, 10) |
| **핸드가드** | 마운트 (0, 51, 10), 뒤로 31.1 → **Y 20~51** |
| 총구 | (0, 55, 10) |

파지점을 그립 (0, −2.3, −3) / 핸드가드 뒤끝 (0, 20, 10)으로 잡으면 **무기가 요구하는 두 손 거리 = 25.81cm**(100% 기준).

### 결정 — 무기 스케일 85% (사용자 확정)

| 애니 | 85% 마진 | 88% 마진 |
|---|---|---|
| Stand_Aim_Idle | +2.42 | +1.65 |
| Crouch_Aim_Idle | +4.52 | +3.75 |
| **Jog_Aim_F_Loop** | **+0.73** | **−0.04** ❌ |
| Stand_Aim_Reload | +2.42 | +1.65 |

검토자는 88%를 제안했으나 **가장 빠듯한 애니에서 0.04cm 모자란다.** 사용자가 고른 85%가 네 개를 모두 통과한다. **판정 기준은 평균이 아니라 가장 빠듯한 애니여야 한다.**

**앞서 승인된 "A(축소) + B(그립 이동) 혼합" 중 B는 불필요해졌다** — 85%면 왼손이 핸드가드 뒤끝에 닿으므로 매거진웰로 파지점을 옮길 이유가 없다. A만 채택한다.

**왼손 IK는 여전히 필수다.** 애니별로 1.2~3.0cm를 당겨야 하고, 그 범위는 팔 여유 안에 있다.

### `hand_R` 부착 트랜스폼 (사용자가 에디터에서 직접 맞춘 값)

```
loc   = (-1.3685,  1.1761, -0.6856)
rot   = (P -0.7520, Y -77.5928, R -88.4732)
scale = 0.85
```

**아직 소켓으로 굽지 않았다.** UE 5.7 Python은 스켈레톤/메시에 소켓을 **추가**할 수 없다(`sockets` 배열이 protected, `rename_socket`만 노출). 구현 시점에 ① Persona에서 `hand_R`에 `SOCKET_Weapon`을 손으로 만들어 위 값을 넣거나 ② 무기 DA에 3P 부착 오프셋 필드를 두어 데이터로 처리한다. **불변식 9(런타임 코드는 본 이름을 모른다)를 지키려면 ②가 낫다.** 사용자 결정 = "지금 위치로 진행하고 추후 수정".

### 아직 확인 못 한 것

- **오른손이 그립을 쥐는 손 모양** — 손가락 회전은 애니가 주는 값이라 Synty 그립 각도와 맞는지 별도 확인 필요
- **스톡–어깨 접촉** — 사용자 조정으로 크게 개선됐으나 애니별로 다시 볼 것
- 리타게팅한 4종 외 나머지 애니

### 작업 중 겪은 운영 사고 (다음에 같은 일을 피하려고 남긴다)

- **`LevelEditorSubsystem.new_level()`을 VibeUE Python에서 부르면 에디터가 즉사한다.** 로그가 `Marshaling tool ... to game thread` 다음에서 끊기고 예외·크래시 덤프가 없다. `load_level`도 같다(2026-07-19 선례). *사용자 레벨을 안 건드리려고 임시 레벨을 만든* 조심이 오히려 죽였다 → **이미 열린 레벨에 스폰하고 끝나면 액터를 지운다.**
- 이 세션 내내 `LogPythonTools: Skipping auto-save: previous Python execution crashed` 플래그가 켜져 있어 **VibeUE 자동 저장이 꺼져 있었다.** 매 단계 `save_asset`을 명시 호출한 덕에 에셋 7개가 크래시에서 전부 살아남았다.
- `StaticMeshActor`는 기본 **Static 모빌리티**라 소켓 부착이 조용히 실패한다(`attach_to_actor`가 `True`를 반환해도 트랜스폼이 안 붙는다). 스폰 직후 `set_mobility(MOVABLE)`.

## 1인칭 시점 실측 — ADS 정렬 방식 재결정 (2026-07-29, 3차)

소켓을 굽고 나서 **실제 눈 위치에서 1인칭으로 렌더**해 봤다. 결과가 축 3(ADS = 혼합)의 전제를 뒤집었다.

### 먼저 정정 — 캡슐/눈높이를 C++ 기본값으로 잘못 적었다

| | 이 문서에 적었던 값 | **BP 실제값** |
|---|---|---|
| 캡슐 반높이 | 88 (C++ `InitCapsuleSize`) | **81** |
| BaseEyeHeight | 64 (엔진 기본) | **69.7** |
| 카메라 높이(발 기준) | — | **150.7** |

**C++ 생성자 값을 읽고 BP 오버라이드를 확인하지 않았다.** 이 프로젝트는 같은 함정을 이미 한 번 겪었다 — `BeginPlay`가 `BaseWalkSpeed`를 다시 밀어넣는 이유가 *"BP 서브클래스의 오버라이드는 C++ 생성자 이후에 역직렬화된다"* 이다. 그 교훈이 캡슐/눈높이에는 적용되지 않았다.

**불변식 2의 클램프 반지름 재계산**: 카메라는 캡슐 중심에서 +69.7, 원기둥 구간은 ±(81−34)=±47이므로 반구에 22.7 들어간 지점 → 그 높이의 캡슐 반지름 = √(34²−22.7²) ≈ **25.3cm**. (`head` 본 높이 155.1 지점은 20.5cm.) 앞서 적은 31.4cm는 반높이 88 가정에서 나온 값이라 폐기한다.

### 실측 — 조준 자세에서 눈 기준 각도

`Blu_W2_Stand_Aim_Idle` + 저작된 `SOCKET_Weapon` + 무기 85% 상태. ADS FOV 55° 기준 화면 절반은 가로 ±27.5° / 세로 ±16°.

| | 가로 | 세로 | 판정 |
|---|---|---|---|
| **조준경(`SOCKET_Aim`)** | **+29.7°** | **−27.1°** | **화면 밖** |
| 총구 | +9.7° | −17.1° | 화면 밖 |
| 오른손 | +43.9° | −66.5° | 화면 밖 |
| 왼손 | +13.3° | −34.6° | 화면 밖 |
| 총열 방향 | 시선과 **11.3° 어긋남** | | |

FOV 90(ADS보다 훨씬 넓음)으로 렌더해도 총이 우하단 모서리에 겨우 걸린다. 원인은 겹친다 — 마네킹 머리 165.5 vs Blu 눈 150.7(**15cm 낮음**), 팔이 27.5% 짧아 총이 더 안쪽·아래, 그리고 소켓은 3인칭으로 보며 맞춘 값이라 1인칭 시선은 검증된 적이 없었다.

### 결정 — ADS 중에는 무기를 카메라로 가져온다 (사용자 안, 채택)

축 3에서 채택한 "㉰ 혼합(애니 포즈 + 잔여 오차만 보정)"은 **잔여 오차가 1~3cm일 것이라는 가정** 위에 있었다. 실측은 **30° 가까이**다. 보정이 아니라 재배치가 필요하다.

- **로컬(오너)**: ADS 중 무기를 카메라 기준으로 재배치해 `AimSocket`을 화면 중앙에 올린다. **기존 `UpdateAimDownSights`의 역산 수식을 그대로 쓰고 대상만 팔 → 무기로 바꾼다.**
- **원격**: 아무것도 바뀌지 않는다. 무기는 계속 `hand_R`에 붙어 있고 몸이 조준 애니를 재생한다.

**손 문제는 없다** — 두 손 모두 ADS 화면 밖이다(왼손 세로 −34.6°, 화면 아래 한계 16°). 숨길 필요조차 없다. 단, 무기를 화면 중앙으로 올린 뒤에도 손이 계속 밖인지는 그때 다시 확인한다. 밖이 아니면 `HideBoneByName`으로 팔을 숨긴다(비용 0).

### 불변식 4의 예외 (명시)

> **불변식 4** — 로컬 플레이어와 원격 관측자는 같은 메시·같은 애님 그래프를 본다. 다른 것은 머리 가시성과 카메라뿐이다.
> **예외**: ADS 중 **무기의 부착점**은 로컬만 다르다(카메라 기준 재배치). 원격은 `hand_R` 그대로.

이 불변식이 막으려던 것은 *"두 벌의 콘텐츠 파이프라인이 따로 저작돼 어긋나는 것"* 이다(3P 필드가 한 번도 저작되지 않아 아군 무기가 안 보이던 버그가 그 예). 이 예외는 **같은 메시·같은 DA를 쓰고 한 상태에서 부착점만 바꾸는 것**이라 그 목적은 지킨다. 새 콘텐츠 축이 생기지 않는다.

`판단` — 이 예외가 늘어나기 시작하면(예: 재장전 중에도, 근접 공격 중에도) 불변식이 사실상 무력해진다. **예외는 ADS 하나로 묶어두고, 두 번째 예외를 넣으려 할 때 불변식 4 자체를 다시 본다.**

### 머리 숨김 검증 — `head` 하나로 충분

`HideBoneByName('head')`가 머리·머리카락·얼굴을 한 번에 지운다(사용자가 스켈레톤 에디터에서 직접 확인). 별도 처리 불필요.

> ⚠️ 검토자 오류 — `hide_bone_by_name` **직후 같은 프레임에 렌더**하면 갱신 전 화면이 나온다. 그걸 보고 "모자가 남았다"고 잘못 보고했다(캐릭터는 모자를 쓰고 있지도 않다). **본 가시성을 바꾼 뒤에는 한 프레임 지나서 확인할 것.**

## 눈 앵커 실측 — 축 2 공식 수정 (2026-07-29, 4차 · B+C 커밋 이후)

B+C(`0a05baa6`)로 True First Person이 실제로 켜지자 축 2가 **아직 없다는 사실이 증상으로 드러났다.** 사용자 PIE 실측:

- 앞뒤좌우 시야 정상 · 머리 숨김 정상 · ADS 정상
- **아래를 볼 때만** 자기 몸을 관통해서 보인다

원인은 카메라가 `(0, 0, BaseEyeHeight)` = **목 높이의 몸통 중심축**에 있어서다. 앞을 볼 땐 몸이 절두체 밖이라 무해하지만, 아래로 돌리면 절두체가 **거리 0에서 시작하는 자기 가슴**을 향한다. `NearClipPlane`이 1.0(엔진 기본 10을 1인칭 무기 때문에 낮춰 둠)이라 잘려 나가지도 않는다.

### 수정 1 — 감쇠 하나로는 안 된다. 항이 둘이다

원안은 `카메라 = head 본 위치 × 감쇠 + 클램프`였고 "감쇠 0 = 현행과 동일"을 되돌리기 장점으로 들었다. **그 장점이 곧 결함이었다** — 감쇠는 *흔들림*을 줄이는 값인데, 몸에서 빠져나오려면 *가만히 서 있을 때도* 유지되는 고정 보정이 필요하다. 한 계수가 두 요구를 동시에 만족할 수 없고, 감쇠를 낮추면 카메라가 다시 몸 안으로 들어간다.

```
최종 = StanceBase(BaseEyeHeight + 스탠스 블렌드)
     + FirstPersonCameraOffset      // 고정. 감쇠 대상 아님. 이번에 구현
     + Damping × (본 rest 기준 편차) // 동적. 미구현
     → 클램프
```

이름을 `EyeOffset`이 아니라 `FirstPersonCameraOffset`으로 둔 것도 결정이다 — "눈 위치"가 아니라 *이 캐릭터+이 캡슐 조합의 보정값*이며, 이름이 해부학을 약속하면 나중에 "본 위치로 대체하면 되잖아"가 나온다(Codex 지적).

**동적 항은 구현하지 않았다.** 바디 AnimBP가 로코모션 전용이라(`d0150852`가 한계로 기록) 따라갈 머리 움직임이 없다. 지금 감쇠를 튜닝하면 4단계 후 전부 다시 해야 하고, 동적 항이 곧 **카메라의 본 읽기 틱 순서/URO 의존**을 끌고 들어온다. Codex 판정: *"미뤄도 되는 것이 아니라 아직 넣으면 안 되는 것에 가깝다."*

### 수정 2 — 클램프는 캡슐 봉쇄가 아니라 **반지름 봉쇄**다

원안의 "캡슐 안으로 클램프"를 문자 그대로 구현하면 **기존 스탠스 블렌드가 깨진다.** 앉기 전환 중 `UpdateStanceCamera`는 시야를 **일부러 캡슐 위에** 붙들어 둔다(40 높이 캡슐 안에서 상대 Z ≈ 81) — 그래야 시야가 뚝 떨어지지 않고 내려온다. Z를 클램프하면 그 블렌드가 잘려 스냅이 되고, 그 높이의 단면(반지름 ≈ 0)으로 횡 오프셋을 재면 **앉는 순간 전방 오프셋이 0으로 붕괴했다 복구**된다.

→ **횡 성분만, 캡슐 반지름 기준으로 잡는다. Z는 건드리지 않는다.**

근거: 이 클램프가 막으려는 건 실패 흐름 ①(벽) 하나다. 사격 원점이 카메라 그 자체이므로 **카메라가 벽 너머로 나가면 총알이 벽 너머에서 나온다.** 벽은 수직이고, 캡슐은 자기 축을 벽에서 `Radius`보다 가깝게 가져갈 수 없다. 따라서 **"축에서 Radius 이상 멀어지지 않는다"만으로 벽 너머 도달이 높이와 무관하게 불가능**해진다. 엄밀한 캡슐 봉쇄가 추가로 막는 건 천장·바닥뿐인데, 그건 스탠스 시스템이 이미 묶어 두고 있고 아무도 그리로 쏘지 않는다.

> **불변식 2의 표현을 정정한다** — "카메라는 캡슐을 벗어나지 않는다"는 실은 **한 번도 참인 적이 없었다**(스탠스 블렌드가 매 앉기마다 위반해 왔다). 참이었고 앞으로도 참인 문장은 **"카메라는 캡슐 축에서 반지름 이상 멀어지지 않는다"** 이고, 벽 너머 사격을 막는 것도 이쪽이다.

### 곁가지로 확정된 것

- **기본값 = `(10, 0, 0)`** — 순수 전방. 증상의 원인은 카메라가 가슴보다 *뒤*에 있는 것이지 *낮은* 것이 아니다. Z를 올리면 (엄밀 캡슐 기준으로 보면) 단면이 빠르게 줄기도 한다: dZ 0 → 25.3cm / +5 → 19.7 / +8 → 14.6
- **튜닝은 BP 클래스 기본값에서** — PIE 인스턴스에서만 바꾸면 서버·클라가 서로 다른 사격 원점을 계산한다(Codex 지적)
- **클램프 발동 계측**을 `#if ENABLE_DRAW_DEBUG` 상단 readout에 넣었다. 조용히 깎이면 디자이너 눈엔 "값이 안 먹는다"로 보인다
- **사격 원점이 앞으로 10cm** 이동한다. 근접(`ViewLocation + Forward × Radius × 0.5`)은 체감 사거리가 그만큼 앞당겨진다

### 아직 확인 못 한 것

- 조준·재장전 포즈가 들어오면 어깨/팔이 카메라에 새로 들어올 수 있다. 고정 오프셋이 **현재 로코모션 포즈만** 덮은 것인지 모든 포즈를 덮는지는 4단계에서 다시 본다(Codex 지적)
- 앉은 상태에서 10cm가 충분한지 / 몸이 너무 멀어 보이지 않는지 = PIE 튜닝
