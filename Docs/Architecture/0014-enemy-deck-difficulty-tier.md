# 0014. 적 스폰 구성 = 난이도 등급별 「덱」 교체

- 상태: 채택
- 날짜: 2026-08-27
- 되돌리기 비용: 비쌈

## 맥락

현행 스폰 구성은 **런당 하나로 고정**이다. `UFPSRRunDirectorSubsystem::StartRun` 이
`DA_RunSchedule.EnemyRoster` 를 스폰 서브시스템에 한 번 밀어 넣고, `AcquireEnemy` 가 그 로스터의
가중랜덤(`UFPSREnemySpawnRule::GetWeight`)으로만 아키타입을 고른다. 즉 **런의 처음부터 끝까지 같은 비율**이다.

로그라이트에서 이건 두 가지를 못 한다.
- **진행에 따른 구성 변화** — 후반에 더 위험한 아키타입이 섞이는 것이 티어 축([ADR 0013](0013-enemy-tier-axis-and-elite-gas.md))의
  본래 목적인데, 로스터가 하나면 엘리트가 **1스테이지부터 같은 확률로 나온다**(0013 후속 3 착지 시점의 실제 상태).
- **런 간 다양성** — 매 런이 같은 구성이라 반복 플레이의 변주가 스폰 위치와 카드에만 의존한다.

⚠️ **이 결정은 "없던 것을 만드는" 것이 아니라 "이미 있는 축을 켜는" 쪽에 가깝다.** 아래 「근거」에서 보듯
덱 자료구조도 교체 경로도 이미 존재한다.

## 목표와 비목표

**목표**
- 몬스터 **비율**을 구성해 둔 **덱**을 난이도 등급별로 여러 개 두고, 등급에 맞는 덱 중 하나로 스폰한다.
- 난이도는 **스테이지·시간·인원수**를 종합한 점수로 정하고, 등급이 바뀌면 덱을 교체한다.
- 같은 등급 안에서도 **런마다 다른 덱**이 뽑혀 반복 플레이에 변주가 생긴다.

**비목표**
- **덱은 적 「수」를 정하지 않는다.** 수의 소유자는 디렉터로 유지한다(불변식 1).
- **런 재현성 없음.** 시드는 "한 런 안에서 등급별 덱 선택이 결정적"인 것까지만 보장한다(아래 반론 ①).
- **덱 비교 저작 도구 없음.** 직렬 편집이 기본이다(반론 ②).
- **스폰 위치·타이밍은 건드리지 않는다.** 이 결정은 "무엇을 뽑는가"만 바꾼다.
- **클라이언트 노출 없음.** 점수·등급은 서버 전용이고 복제하지 않는다.

**규모 상한**
- 난이도 등급 **1~10**, 등급당 덱 **1~4개**(평균 2) ≈ **로스터 자산 20개**.
- 저작값: 점수 가중치 4개(Base·Stage·Time·Party) + 하강여유 1개 = **5개**.

## 불변식

1. **적 「수」의 단일 소유자는 디렉터다**(`ComputeTargetAliveCount`). 덱은 수를 정하지 않는다.
   *(없으면: 소유자가 둘이 되어 `AliveCountByLevel`·`StageDifficulty` 두 축이 죽는다 — 이 논의의 최초 `치명` 쟁점.)*
2. **구성 점수의 입력 = 스테이지·시간·인원수.** 팀 레벨은 구성 점수에 넣지 않는다(수 축 전용).
   스테이지가 수·억제기 내구도·구성 셋을 동시에 미는 것은 **의도된 계단**이다([ADR 0010](0010-arena-topology-and-stage-transition.md) D6 —
   *"일찍 부수려 할수록 비싸다"*, 파티가 선택하는 대가).
   ⚠️ **배제형("-에만")으로 쓰지 말 것** — 시간은 레거시 폴백에서 수를 올리고, 인원수는 억제기 내구도를 올린다.
   이 불변식은 **점수의 입력 정의**이지 각 축의 배타적 용도 선언이 아니다.
3. **덱은 비율이고, 절대 상한은 기존 캡이 강제한다**(`GlobalAliveCap`·`MaxEliteAlive`·`MaxActiveEnemies`).
   *(없으면: 덱이 "엘리트 20%"를 말하고 캡이 2마리를 말할 때 충돌한다. 엘리트 게이트가 로스터 픽의
   다운스트림이라 어떤 덱 저작도 캡을 뚫지 못한다 — 0013 불변식 6 보존.)*
4. **덱 교체는 로스터 포인터 교체 하나뿐이다.** 이미 스폰된 적을 건드리지 않고 스웜 리셋·풀 조작을 동반하지 않는다.
   🔴 **이것이 성립하는 기제 = `AcquireEnemy` 가 로스터를 매 스폰마다 읽는 것**(`FPSREnemySpawnSubsystem.cpp:1435-1443`;
   리포 전체에서 `EnemyRoster` 소비자는 그 한 곳뿐임을 grep 전수로 확인). **푸시 시점 캐시·프리워밍을 넣으면
   이 불변식이 조용히 깨진다.** 지금 옳게 돼 있는 것은 우연이며, 아무도 그렇게 하기로 정한 적이 없었다.
5. **등급 전환은 히스테리시스를 가진다.** 상승 임계 ≠ 하강 임계.
   *(없으면: 인원이 경계에서 들락거릴 때마다 구성이 바뀐다. 시간·스테이지는 단조 증가지만 인원수는 이탈로 줄어든다.)*
6. **난이도 점수와 덱 선택은 서버 권위이고 월드 비의존 순수 함수다** — `덱 = 목록[등급][Hash(런시드, 등급) % N]`.
   *(없으면: ① 순수 함수가 아니면 단위 테스트가 안 되고 가중치→앵커 곡선 교체가 국소적이지 않다
   ② 전환마다 재추첨하면 히스테리시스 flap 이 덱 churn 을 만들고 "이번 런의 3등급 = 이 구성"이라는
   플레이어 학습이 불가능해진다.)*

## 검토한 대안

### 안 A — 덱 = 기존 로스터 자산, 등급 매핑은 스케줄 필드 (채택)

`UFPSREnemyRosterDataAsset` 를 그대로 덱으로 쓰고, `DA_RunSchedule` 에
`TArray<FFPSRDeckTier{ Tier, TArray<TObjectPtr<UFPSREnemyRosterDataAsset>> }>` + 점수 가중치 5개를 둔다.
디렉터가 틱마다 점수를 계산해 등급이 바뀔 때만 `SetEnemyRoster` 를 부른다.

- **장점**: **신규 자료구조 0개, 신규 C++ 클래스 0개.** 폴리모픽 `UFPSREnemySpawnRule` 확장점·풀 버킷화·
  엘리트 캡이 전부 무손상 생존. 교체 경로(`SetEnemyRoster` public)도 이미 존재. 난이도 손잡이가
  스케줄 한 곳에 모여 검증기 교차검사가 에셋 경계를 안 넘는다(`StageDifficulty`·`InhibitorDurabilityByPartySize` 선례).
  에셋 참조 배열을 struct 로 스케줄에 두는 것도 선례가 있다(`FFPSRMissionWindow::MissionPool`).
- **단점**: 덱 20개가 개별 자산이라 나란히 비교 저작이 안 된다(반론 ②).
- **채택.**

### 안 B — 덱을 테이블 안에 인라인 struct 로 (기각)

`TArray<FFPSRDeck{ TArray<FFPSRDeckEntry{class, weight}> }>` 형태로 한 자산에 전부 인라인.

- **장점**: 자산 1개. 덱을 한 화면에서 나란히 본다(저작·밸런싱에 유리).
- **단점**: 덱 안에 `UFPSREnemySpawnRule`(EditInlineNew Instanced)을 중첩해야 하는데,
  **이 리포는 "폴리모픽 Instanced 는 UObject 직속 `TArray` 만" 이라는 제약**을 갖고 있다(struct 중첩은 미검증·회피 대상).
  인라인하면 `Enemy.md` §2-6 이 **확장성-우선으로 명시한 폴리모픽 룰 시임을 포기**하거나 회피 패턴을 쓰게 된다.
- **기각 사유: 얻는 것(저작 편의)이 잃는 것(확장점)보다 작고, 잃는 쪽이 이미 문서화된 설계 원칙이다.**
  ⚠️ 단 **저작 편의 문제는 해결되지 않은 채 남는다**(반론 ②) — 기각이 그 비용을 없애지는 않는다.

### 안 C — 난이도 점수 없이 스테이지 인덱스로 직접 덱을 고른다 (기각)

`StageDifficulty` 앵커에 덱 참조를 얹어 스테이지당 덱을 지정.

- **장점**: 가장 단순. 점수식·히스테리시스·시드가 전부 불필요.
- **단점**: 사용자 요구("시간·스테이지·인원수 **종합**")를 담지 못한다. 인원 4인과 1인이 같은 구성을 받고,
  같은 스테이지에 오래 머무는 것이 난이도에 반영되지 않는다.
- **기각 사유: 요구를 구조적으로 담지 못한다.** 요구가 "스테이지만"으로 줄면 이 안이 돌아온다(전환 조건).

## 결정

**안 A를 채택한다.**

| 항목 | 규칙 |
|---|---|
| 점수 | `Base + StageIndex×W_s + (RunClock/60)×W_t + (PartySize-1)×W_p` |
| 등급 | `clamp(floor(Score), 1, 10)` |
| 전환 | **스냅** — 한 틱에 `while(Score>=T+1) ++T; while(Score<T-여유) --T;` 로 수렴, `SetEnemyRoster` 는 수렴 후 **1회**. 점프 크기만큼 중간 등급을 건너뛰는 것은 의도 |
| 시드 | `StartRun` 에서 서버가 런 시드 1개를 굴려 보관(서버 전용, 복제 없음). `덱 = 목록[등급][Hash(런시드, 등급) % N]` |
| 초기 평가 | **오프닝 시드 해제 지점**(StartRun 시점 참가자 수는 과소집계 — 억제기 축이 같은 이유로 권위 적용을 그 지점으로 미룬 선례) |
| 인원수 | `AFPSRGameMode::GetParticipantCount()` — **DBNO 포함**. `GetLivingPlayerCount` 는 고의 다운으로 난이도를 깎는 악용이 열린다(억제기 축이 같은 이유로 이걸 골랐다) |
| 빈 등급 | **직전 덱 유지**(스폰이 멈추지 않는다) + 검증기 경고. **시작 등급이 비면 Error** — 직전 덱이 없어 단일 `EnemyClass` 폴백으로 개전한다 |

**덱 회전 × 풀 기아 = (a) 감수 + (b) 저작 지침 병행.**
- (a) 불변식 4를 유지하고 lazy 축출을 문서화한다. `EvictionCount` 를 판정 지표로 삼고,
  축출 로그는 **전환당 집계로 스로틀**한다(킬 페이스 스팸 방지).
- (b) **인접 등급 덱은 클래스 집합을 공유하게 저작**한다(신규 아키타입 도입을 계단식으로 분산).
  검증기가 인접 등급 간 신규 클래스 수를 경고한다.

**검증기 9개** — 신규 6(등급 1~10 각 덱 ≥1[시작 등급은 Error] · `floor(Base)>1` 이면 하위 등급 죽은 저작 ·
`W_s≥1` 이면 전환 1회가 등급 2개 점프 · 최대 점수 <10 이면 상위 덱 미도달 · 하강여유 ∈[0,1) 강제 ·
가중치 전부 0) + **이관 3**(`NoEnemyRoster`·`RosterEliteButCapZero`·`EliteCapButRosterNone` 이 현재
단일 `EnemyRoster` 필드만 순회한다 — 덱 테이블로 옮기지 않으면 조용히 커버리지를 잃는다)
+ **전-엘리트 덱 강한 경고**(엘리트 캡 포화 시 `AcquireEnemy` 가 전부 null 을 반환해 **그 등급에서 스폰이 통째로 멎는다**).

## 근거

**왜 안 A인가.** 조사해 보니 **덱 자료구조도 교체 경로도 이미 있었다.**
- `UFPSREnemyRosterDataAsset` = `(클래스, 가중치)` 집합 = 그대로 덱이다.
- `SetEnemyRoster()` 는 이미 public 이고, 로스터는 `AcquireEnemy` 안에서 **매 스폰마다** 읽힌다.

따라서 이 결정이 실제로 추가하는 것은 **점수 계산기**와 **등급→덱 매핑** 둘뿐이다. 기존 인프라를
대체하지 않고 그 위에 선택층을 얹는다(DESIGN-FIRST).

**무엇을 포기했는가.** 덱 비교 저작이다(반론 ②). 안 B가 그걸 해결하지만 폴리모픽 확장점을 대가로 요구하고,
그 확장점은 `Enemy.md` §2-6 이 명시한 설계 원칙이다.

## 전환 조건

- **안 C 로 되돌아간다**: 요구가 "스테이지만으로 구성을 정한다"로 줄어들 때. 점수식·히스테리시스·시드가 전부 불필요해진다.
- **점수식을 앵커 곡선으로 바꾼다**: 평탄 가중치로 페이싱이 표현되지 않을 때(예: *"첫 3분은 거의 안 오르다가 급상승"*).
  클론2의 `EvalStageAt`/`EvalAliveCountByLevel` 과 같은 관용구·같은 테스트 하네스라 `저렴` 한 교체다.
- **불변식 4를 좁힌다**: `EvictionCount` 가 유의미하게 잡힐 때(축출 상시화 = 사실상 풀링 무효).
  그때는 등급 전환 시 이전 덱 전용 클래스 휴면체를 틱당 1개씩 선제 소각(paced trim)하는 안을 다시 본다.
- **덱 비교 뷰를 만든다**: 20개 직렬 편집이 밸런싱 병목으로 실측될 때. 기존 `FPSRogueliteEditor` 모듈에
  추가한다(신규 모듈 금지 규약).

## 검증 시나리오

**정상 흐름 — 인원 3, 5분 경과, 스테이지 2**
1. 디렉터 틱 → `Score = Base + 2×W_s + 5×W_t + 2×W_p` = 3.4 → **Tier 3**
2. 이전 Tier 가 3이면 아무 일도 안 한다. 2였다면 → `목록[3][Hash(런시드,3) % N]` 로 1개 뽑아 `SetEnemyRoster`
3. 다음 `AcquireEnemy` 부터 새 덱 비율로 뽑힌다. **이미 나와 있는 적은 그대로**(불변식 4)
4. 적 **수**는 여전히 `ComputeTargetAliveCount`(팀레벨 × 스테이지)가 정한다(불변식 1·2)
5. 덱이 "엘리트 20%"를 뽑아도 `min(곡선, 하드캡)` 게이트가 상한을 강제한다(불변식 3)

**실패 흐름 — 참여자 이탈 후 재접속**
1. 인원 3→2 → `Score` 3.4→3.0
2. 하강 임계는 `3 - 0.3 = 2.7`. **3.0 > 2.7 이라 등급 유지** → 덱 교체 없음(불변식 5)
3. 재접속 → 3.4 복귀. **교체가 0회** 일어났다
4. 2명이 더 나가 `Score` 가 2.5 로 떨어지면 → Tier 2 로 하강, 2등급 덱으로 교체.
   **이미 나온 적은 그대로 살고 새 적만 순해진다**(불변식 4)
5. 다시 4인이 되어 Tier 3 으로 복귀하면 — `Hash(런시드, 3)` 이 같으므로 **아까 그 덱**이 돌아온다(불변식 6).
   히스테리시스 flap 이 덱 churn 을 만들지 않는다

## 논의 중 제기된 반론

**① 「시드 고정 = 런 재현」이 거짓이다** (해소 — 보장 범위를 좁힘)

설계 초안은 `UFPSRStageDirectorSubsystem::ComputeStageSeed(BaseSeed, StageIndex)` 관용구를 근거로
"시드를 쓰면 런이 재현된다"고 적었다. **두 절 다 거짓이었다**(`확인됨`):
- `BaseSeed` 는 런마다 굴리는 값이 아니라 `AFPSRArenaActor::InitialSeed` — **레벨에 저작된 고정값**(기본 1).
  그대로 이식하면 **모든 런에서 같은 등급은 영원히 같은 덱**이 나와 "덱 중 랜덤 1개" 요구가 죽는다.
- 런의 나머지 무작위성이 전역 비결정 RNG 다(`FMath::FRand` 스폰 픽 · `FMath::FRandRange` 미션 창 ·
  `FMath::RandRange` 스폰 포인트). 덱만 시드로 묶어도 런은 재현되지 않는다.

→ **런 시드를 새로 굴리고, 보장 범위를 "한 런 안에서 등급별 덱 선택의 결정성"으로 좁혔다.**
그 부산물로 3→4→3 재진입 시 같은 덱이 돌아오는 성질을 얻었고, 이것이 불변식 6이 되었다.

**② 덱 20개를 나란히 비교 편집할 수단이 없다** (미해소·감수)

설계 초안은 "UE 내장 Property Matrix 로 해결, 코드 비용 0" 이라 적었으나 **엔진 소스로 반증됐다**(`확인됨`):
- `EditInlineNew`(Instanced) 프로퍼티 노드는 **다중 선택에서 read-address 가 실패하도록 명시**돼 있다
  (`PropertyNode.cpp:312` `bSingleSelectOnly` → `ObjectPropertyNode.cpp:214`).
- 다중 선택에서 배열은 **원소 수가 전부 같아야만** 유효 노드가 된다 — 덱마다 룰 수가 다르다.
- Property Matrix 의 배열 지원은 **2012년산 미해결 TODO** 다(`PropertyTable.cpp:1202`).

실제로 되는 것은 "에셋 목록을 띄워 놓고 **한 행씩** 우측 패널에서 편집"이다.
→ **안 B 기각은 유지된다**(1차 근거는 리포의 폴리모픽 Instanced 제약이고 그건 참이다).
**다만 저작 부담은 보상책 없이 남는다.** 사용자가 이 사실을 알고 규모 20개를 유지하기로 결정했다.
비교 뷰가 필요해지면 전환 조건 참조.

**③ 스테이지가 수·내구도·구성 셋을 동시에 민다** (해소 — 의도로 승격)

불변식 2의 초안("시간·스테이지·인원수는 구성에만")은 **스테이지에 대해 거짓이었다** —
`StageDifficulty.AliveCountBonus`·`AliveCountMultiplier` 가 이미 적 수를 올린다.
사용자가 팀레벨에서 피하려던 이중 상승이 스테이지에 그대로 있었다.

→ **감수로 판정.** 근거는 사후 합리화가 아니라 기존 결정이다: ADR 0010 D6 이 스테이지 상승을
*"일찍 부수려 할수록 비싸다"* 로 **파티가 선택하는 대가**로 이미 규정했고, 구성 점프는 그 대가의 연장이다.
반면 팀레벨은 조용히 자동 누적돼 추적이 어렵다 — 두 축을 다르게 취급할 근거가 된다.
불변식 2를 **배제형에서 입력 정의형으로** 다시 썼다.

**④ 덱 회전이 풀링을 무효화할 수 있다** (미해소·감수 + 완화)

등급마다 새 아키타입을 도입하면(그게 티어 진행의 목적이다) 서로소 클래스 집합 2~3세대에
`TotalSpawned` 가 500에 닿고, 이후 **모든 등급 전환마다** 축출 + `Destroy()` + `SpawnActor` 가
킬 페이스로 발생한다(`판단` — 전환 창당 최대 ~192쌍 추정). 제1원리가 풀링으로 갚기로 한 비용이
전환마다 부활한다.

→ **(a) 감수 + (b) 저작 지침** 병행으로 완화하되 **구조적으로 해소하지는 않았다.**
축출 대상 선정(가장 큰 다른 버킷)이 이 시나리오에서 정확히 이전 덱의 주력 클래스를 먼저 소각하므로
방향 자체는 옳다. `EvictionCount` 가 유의미해지면 전환 조건의 paced trim 을 본다.

**⑤ 등급 점프 시 중간 덱을 건너뛴다** (해소 — 스냅으로 명시)

`W_s ≥ 1` 로 저작하면 스테이지 전환 1회가 등급 경계를 2개 이상 넘을 수 있고, 인원이 한 틱에
여럿 이탈해도 마찬가지다. 틱당 1스텝으로 올리면 중간 덱이 한 스폰 배치(최대 3마리)만 뱉고 사라지고,
스냅하면 그 런에서 영원히 미사용일 수 있다.
→ **스냅으로 확정**하고 "점프 크기만큼 건너뛰는 것이 의도"로 문서화했다. 검증기가
`W_s ≥ 1` 일 때 경고해 저작자가 알고 선택하게 한다.
