# 0001. 플레이어 이동 상태의 소유와 예측 구조

- 상태: 채택
- 날짜: 2026-07-28
- 되돌리기 비용: 비쌈

## 맥락

`refactor/character` 트랙에서 **플레이어 캐릭터부터 구조를 다시 설계**하기로 했다(사용자 결정 2026-07-27). 그 첫 대상이 이동(무브먼트)이다.

참조 자료는 사용자가 제공한 Apex Legends 사격 훈련장 플레이 영상(9.75초, 60fps)이다. 60fps 원본 프레임과 탄약 카운터를 추적해 아래 순서를 실측했다.

| 시각 | 동작 | 판별 근거 |
|---|---|---|
| ~2.0s | 달리기 | 시야 안정, 무기 힙 자세 |
| 2.03~2.07s | 슬라이드 진입 | 카메라 높이 급강하 |
| 2.07~2.20s | 슬라이드 지속 (~0.15s) | 낮은 시점 유지 |
| 2.20~2.30s | 벽 접촉 | 화면이 벽면으로 가득, 무기가 우하단으로 |
| **2.30~2.40s** | **벽 매달림 — 무기가 화면에서 완전 소실** | 6프레임 연속 무기 없음 (양손 사용) |
| 2.40~2.55s | 등반 종료, 무기 복귀 | |
| 2.55~3.18s | 공중 이동/하강 | 탄약 27 유지 = 사격 없음 |
| 3.18s | 첫 발사 (힙) | 탄약 27→26 |
| ~3.4s | ADS 진입 | 무기가 화면 중앙 정렬 |
| 3.4~4.6s | ADS 연사 | 탄약 26→0 |
| 4.6~5.4s | 재장전 | |

**왜 지금 결정해야 했는가.** 현재 코드는 엔진 기본 `UCharacterMovementComponent`를 그대로 쓰고 커스텀 서브클래스가 없다(`SetDefaultSubobjectClass` 0건, `FSavedMove` 파생 0건, Crouch 사용 0건). 유일한 특수 이동인 대시는 **서버 RPC 후 `LaunchCharacter`** 방식이다([FPSRCharacter.cpp:705](../../Source/FPSRoguelite/Private/Hero/FPSRCharacter.cpp)). 이 방식을 그대로 복사해 슬라이드를 만들면 반드시 깨지므로(아래 안 ㉰ 참조), 코드를 쓰기 전에 방식을 확정해야 했다.

## 목표와 비목표

**목표**

- 🔴 **개정 2026-08-31 (사용자 결정) — 이동 상태 5개: 서기 / 달리기 / 앉기 / 슬라이딩 / 공중 체공.**
  **벽 매달리기는 폐기됐다.** 벽은 이제 상태가 아니라 **순간 임펄스**다 — 낙하 중 이동 입력을 벽 쪽으로 유지한 채
  벽에 닿으면 즉시 튕겨나간다. 지속 구간이 없으므로 커스텀 무브먼트 모드도, 매 프레임 물리도, 프록시에 알릴
  포즈도 없다. 경위·근거 = 아래 「반론 1」 및 「4단계」.
  - ~~이동 상태 6개: … / 벽 매달리기~~
  - ~~벽 매달리기는 **지속 상태**이며 출구가 셋이다(W 유지 → 등반 / W 해제 → 미끄러져 떨어짐 / 점프 → 튕겨나감)~~
- 사격/ADS는 이동 상태와 직교한다. 단 이동 상태가 **사격 허용 여부**와 **확산 배수**를 제공한다.
  - 앉기 = 확산 ×0.8 / 공중 = 확산 ×1.6(부정확해짐) / 슬라이드 = 사격 가능(배수 적용)
  - 🔴 **개정 2026-08-31**: ~~벽 매달리기 = 사격 불가~~ — 사격을 막던 **유일한** 상태가 사라졌다.
    `CanFireInCurrentState()`는 현재 항상 참이다. 술어 자체는 남긴다(호출처 11곳의 단일 판정원).
- 4인 협동 · 리슨 서버 · 서버 권위

**비목표** (사용자 확정)

- **벽달리기(월런)를 만들지 않는다.**
- ~~**움직이는 벽에 매달리기를 지원하지 않는다.**~~ → **무의미해짐(2026-08-31)**: 매달림이 없으므로 "매달린 채
  벽이 움직이는" 상황 자체가 성립하지 않는다. 임펄스는 접촉 프레임 하나로 끝난다.
- **카드/스킬로 새 이동 상태를 추가하지 않는다.** 카드 확장 범위는 **수치·조건까지**로 한정한다(아래 "카드 확장 범위" 참조).

**규모 상한**

- 동시 플레이어 4명, 전용 서버 없음(리슨 서버 = 호스트가 자기 화면 렌더 + 서버 시뮬 동시 부담)
- 적 동시 200~300 (`Docs/SSOT/Performance.md §5`)

**카드 확장 범위 = A (수치·조건까지만)**

| | A. 수치·조건 확장 (채택) | B. 새 이동 상태 추가 (비목표) |
|---|---|---|
| 예시 | 점프력 +30%, 슬라이드 거리 +50%, 점프 횟수 1→2, 대시를 공중에서도 허용 | 월런, 공중 부양, 갈고리 이동 |
| 필요한 것 | GAS 어트리뷰트 추가 (기존 배선 재사용) | 새 커스텀 이동 모드 + C++ 물리 코드 |
| 되돌리기 비용 | 저렴 | 일방통행 |

논의 중 사용자가 예시로 든 "이단 점프"와 "공중 대시"는 **둘 다 A에 해당한다.** 이단 점프는 엔진의 `JumpMaxCount`를 1→2로 바꾸는 것이고(엔진이 예측까지 이미 지원), 공중 대시는 현행 대시의 지상 조건을 푸는 것이다.

## 불변식

어떤 세부 결정도 아래를 위반할 수 없다.

| # | 불변식 |
|---|---|
| 1 | 이동 상태의 주인은 **무브먼트 컴포넌트 하나**다. 캐릭터·GAS·애님BP는 읽기만 한다 |
| 2 | 모든 이동 상태는 **클라이언트가 예측하고 서버가 같은 물리로 확인**한다. 서버 응답을 기다렸다 움직이는 이동은 없다 |
| 3 | 무브먼트 수치는 **GAS 어트리뷰트로 복제**되어 서버·클라이언트가 같은 값을 본다 |
| 4 | 사격/ADS는 이동 상태를 모른다. **이동 상태가 "지금 사격이 되는가"를 알려준다** |
| 5 | 확산 계산의 주인은 **기존 heat 시스템 하나**다. 이동 상태는 배수만 제공한다 |
| 6 | **애니메이션은 이동 상태를 소유하지 않는다.** "몽타주가 끝나야 상태가 끝난다"를 만들지 않는다 |
| 7 | **모든 이동 상태는 시간 상한 또는 조건 없는 탈출 경로를 갖는다** |
| 8 | **프리즈/DBNO는 이동 시작만이 아니라 진행 중인 이동도 멈춘다** |
| 9 | 무브먼트 수치는 **데이터(어트리뷰트/DataAsset)에 둔다.** C++ 상수로 박지 않는다 |

각 불변식이 막는 사고:

- **6번** — 등반 몽타주 재생이 실패하면(패킷 손실·에셋 미할당) 등반 상태에서 영영 못 나온다. 이 프로젝트는 같은 종류의 사고를 이미 겪었다(W2-B P1: 카드 프리즈 자기봉인 데드락, 시핑 복구 불가).
- **7번** — 이 게임에는 파괴되는 문이 있다(`Door/`). 탈출 조건을 "벽이 있을 때"에 의존시키면 벽이 사라진 순간 탈출도 같이 사라진다.
- **7번 적용례(2026-08-10)** — 슬라이드의 시간 상한은 급경사 내리막에서 무기한 유예된다(슬로프 타이머 되감기, `fix/slope-slide-duration`). 그 구간에서 불변식 7은 "시간 상한"이 아니라 **"조건 없는 탈출 경로" 분기**로 충족된다: 크라우치 해제·지면 이탈·특수이동 게이트가 경사와 무관하게 매 프레임 검사되고, 경사가 끝나면 시간 상한이 즉시 재개된다. 벽 매달리기의 무조건 시간 상한(`WallHangMaxDuration`)과는 분기가 다름에 유의.
- **8번** — 대시에서 실제로 났던 문제다. 시작은 막았는데 이미 날아가던 대시가 안 멈춰서 카드 선택 화면 뒤에서 캐릭터가 계속 미끄러졌다([FPSRCharacter.cpp:1020](../../Source/FPSRoguelite/Private/Hero/FPSRCharacter.cpp)에 그 수정이 남아 있다). 슬라이드는 지속 상태라 같은 문제가 더 크게 난다.

## 검토한 대안

논의는 두 축으로 갈렸고, 되돌리기 비용에 따라 **축 2만 지금 결정하고 축 1은 구현 시점으로 미뤘다.**

| 축 | 내용 | 되돌리기 비용 | 처리 |
|---|---|---|---|
| 축 1 | 슬라이드 물리를 *걷기 모드 확장*으로 할까 *커스텀 모드*로 할까 | 저렴 | **구현 시점으로 연기** |
| 축 2 | **상태 전이를 누가 결정하나** | 비쌈 | 이 문서에서 결정 |

축 1을 미룰 수 있는 이유는 아래 "결정"의 외부 인터페이스가 축 1과 무관하기 때문이다. 축 1을 뒤집어도 사격·애님BP·HUD는 한 줄도 바뀌지 않는다.

### 안 ㉮ — 무브먼트 컴포넌트가 상태를 결정하고, GAS는 효과만 붙인다 **[채택]**

```
슬라이드 키 → 커스텀 플래그(FLAG_Custom_0) → 이동 패킷에 실려 서버로
                                              ↓
                        무브먼트 컴포넌트가 조건 검사 + 상태 전이 + 물리
                        (클라·서버가 같은 코드를 각자 돌림 = 예측 성립)
                                              ↓
                        GAS는 옆에서 쿨다운·무적·카드 수치만 담당
```

장점: 예측이 엔진의 저장-재생 구조 위에서 그대로 작동한다. 불변식 1·2를 구조로 강제한다.
단점: 게임플레이 규칙(쿨다운 등)과 물리가 서로 다른 시스템에 나뉜다.

### 안 ㉯ — GAS 어빌리티가 상태 전이를 결정하고 무브먼트에 지시한다 **[기각]**

```
슬라이드 키 → 어빌리티 활성화 → 어빌리티가 조건 검사 → 무브먼트에 "슬라이드 시작해" 지시
```

장점: 쿨다운·비용·태그 차단이 공짜로 따라오고, 카드로 조건을 바꾸기 쉽다.

**기각 사유 — 서버 보정이 올 때마다 상태 주인이 둘로 갈라진다.**

| 단계 | 안 ㉮ | 안 ㉯ |
|---|---|---|
| 클라가 t=100ms에 슬라이드 시작 | 저장된 이동 기록에 플래그가 남음 | 어빌리티가 활성화됨 |
| 서버 보정 도착 — t=80ms로 되감으라 | 무브먼트가 t=80ms부터 저장된 입력을 순서대로 재생. 슬라이드도 같이 재생됨 | 무브먼트는 되감기지만 **어빌리티는 안 되감김** |
| 결과 | 클라·서버가 같은 상태로 수렴 | **어빌리티는 "슬라이드 중"인데 무브먼트는 "달리기 중"** |

이건 예외 상황이 아니라 패킷이 하나만 늦어도 매번 일어난다. 불변식 1과 2를 동시에 깬다.

근거의 신뢰 수준: `FSavedMove_Character`가 재생하는 항목이 `Acceleration`·`bPressedJump`·`bWantsToCrouch`·커스텀 플래그뿐이고 어빌리티 활성화가 그 목록에 없다는 것은 **엔진 소스로 확인함**(`CharacterMovementComponent.h` 2920~2990행대). GAS가 별도 되감기 장치를 갖는다는 것은 **일반적 패턴**이며 이 엔진 소스에서 직접 대조하지는 않았다.

**㉯가 노렸던 이점은 ㉮ 안에서 그대로 살린다** — 쿨다운·무적·카드 수치는 GAS가 계속 담당한다. 갈라지는 건 "상태 전이를 누가 결정하는가" 하나뿐이다.

### 안 ㉰ — 현행 대시 방식(서버 RPC 후 이동)을 슬라이드로 확장 **[기각]**

**기각 사유 — ping 46ms(참조 영상 실측값)에서 캐릭터가 뒤로 튕긴다.**

1. 클라가 슬라이드 키를 누름
2. RPC가 서버 도착 — 23ms
3. 서버가 속도를 바꿈. 그동안 클라 화면은 아직 "달리기"로 계속 시뮬레이션
4. 서버 위치 보정이 클라 도착 — 다시 23ms
5. 두 위치가 다르므로 캐릭터가 뒤로 튕김

대시에서 이 문제가 안 보였던 이유는 `LaunchCharacter`가 속도를 한 번 꽂고 끝나는 충격이라 엔진 기본 예측(걷기/떨어지기)이 대충 따라가기 때문이다. **슬라이드는 지속 상태**여서 속도 곡선·마찰·캡슐 높이·지속 시간이 매 프레임 이어져야 하므로 같은 방식이 성립하지 않는다.

              ▲                    │

의존 방향 규칙 — 불변식 1과 4를 구조로 강제한다:

| 규칙 | 뜻 |
|---|---|
| 무브먼트 컴포넌트는 사격·애님BP·HUD를 **모른다** | 아래쪽 의존이 없다. 사격 코드를 바꿔도 무브먼트는 안 바뀐다 |
| 사격·애님BP·HUD는 무브먼트에 **묻기만** 한다 | 상태 복사본을 갖지 않는다. 복사본이 생기면 원본과 어긋난다 |
| GAS는 무브먼트에 **수치만** 밀어넣는다 | [FPSRCombatSet.cpp:96](../../Source/FPSRoguelite/Private/AbilitySystem/Attributes/FPSRCombatSet.cpp)의 기존 방향과 동일 |

무브먼트 컴포넌트가 밖으로 내주는 것은 이것이 전부다:

```cpp
bool  CanFireInCurrentState() const;   // 불변식 4
float GetSpreadMultiplier() const;     // 불변식 5 — 배수만 제공, 계산은 heat 시스템이
bool  IsSliding() const;               // 애님BP·HUD 표시용
bool  IsOnWall() const;
```

| 매달린 벽 정보 | **무브먼트 컴포넌트** (내부) | 아무도 안 봄 | 안 함 |
| **기본 수치** (가속/감속 곡선, 최소 속도, 등반 각도 상한) | DataAsset / EditDefaultsOnly | 무브먼트 | 안 함 (모두가 같은 에셋을 봄) |
| **런타임 배수** (카드 효과) | **GAS 어트리뷰트** (PlayerState) | 무브먼트 | GAS가 복제 |
| **장비 걷기속도** (무기별 `WalkSpeed`) | **무기 DataAsset** | 무브먼트 | 안 함 (장착 슬롯이 복제되고, 양쪽이 같은 에셋에서 값을 읽음) |
| 확산 배수 | 무브먼트가 제공 | heat 시스템이 소비 | 안 함 (양쪽이 같은 상태에서 같은 값 계산) |

수치를 기본값 층과 런타임 배수 층으로 나눈 것은 기존 `BaseWalkSpeed`(고정) × `MoveSpeedMultiplier`(어트리뷰트) 패턴과 동일하다. 새 규칙이 아니라 검증된 것의 확장이다.

### 통신 예산

엔진 소스 확인 결과 커스텀 확장 슬롯은 `FLAG_Custom_0~3` **4개가 상한**이다(`GetCompressedFlags()`가 `uint8`을 반환하고 4비트는 엔진 예약). 이번 설계에 필요한 슬롯은 **1개**다.

| 필요한 신호 | 출처 |
|---|---|
| W 유지 (등반/미끄러짐 분기) | `FSavedMove_Character::Acceleration` — 기본 제공 |
| 점프 (벽에서 튕김) | `bPressedJump` — 기본 제공 |
| 앉기 | `bWantsToCrouch` — 기본 제공 |
| **슬라이드 원함** | **커스텀 슬롯 1개** |

카드 확장을 A로 한정했으므로 새 이동 상태가 늘지 않아 3슬롯이 여유로 남는다.

## 근거

**왜 ㉮인가.** 불변식 2(예측)를 채택한 이상, 상태 전이는 클라이언트와 서버가 **같은 입력으로 같은 코드를 각자 돌려** 같은 결론에 도달해야 한다. 엔진의 저장-재생 구조가 재생해 주는 것은 무브먼트 컴포넌트가 소유한 것뿐이므로, 상태 주인은 거기여야 한다.

**무엇을 포기했는가.** ㉯를 택했다면 쿨다운·조건·태그 차단을 GAS의 기성 기능으로 공짜로 얻었을 것이다. ㉮에서는 진입 조건 검사를 무브먼트 컴포넌트 안에 직접 쓴다. 대신 쿨다운·무적·카드 수치는 여전히 GAS가 담당하므로 손실은 "조건 검사 코드를 직접 쓴다" 한 가지로 국한된다.

**엔진 기본 무브먼트를 버리는 것이 아니다.** 엔진은 커스텀 이동 모드(`MOVE_Custom` + `PhysCustom`)와 커스텀 플래그(`FLAG_Custom_0~3`)를 확장 지점으로 열어두었고, 앉기는 `bWantsToCrouch`로 예측까지 이미 제공한다. 이 결정은 그 확장 지점을 쓰는 것이다.

단 `PhysCustom()`은 블루프린트 이벤트 하나만 호출하는 **빈 함수**다(`CharacterMovementComponent.cpp:6172`). 커스텀 이동 모드를 쓰면 바닥 감지·계단 오르기·경사면·벽 미끄러짐을 직접 써야 한다. 이것이 축 1(걷기 확장 vs 커스텀 모드) 비교의 핵심 비용이며, 구현 시점에 다룬다.

## 전환 조건

무엇이 참이 되면 이 결정을 다시 봐야 하는가.

- 이동 상태 진입 조건이 **서버만 아는 정보**에 의존하게 될 때 (예: "팀원이 근처에 있어야 슬라이드 가능"). 클라이언트가 예측할 수 없어 구조가 바뀐다.
- 커스텀 플래그 4개를 다 쓰고 더 필요해질 때. 현재 1개만 쓰므로 여유가 크다. 초과 시 `FCharacterNetworkMoveData` 확장이 다음 수단이다.
- **카드 확장 범위가 A에서 B(새 이동 상태 추가)로 바뀔 때.**

## 검증 시나리오

**정상 흐름** — 달리기 → 슬라이드 → 벽 접촉 → 매달리기 → (W 유지) 등반 → 공중 → 사격 → ADS → 착지

각 단계에서 상태를 들고 있는 주체는 언제나 무브먼트 컴포넌트 하나다. 사격은 `CanFireInCurrentState()`와 `GetSpreadMultiplier()`만 보고, 자기가 어느 상태인지 묻지 않는다. 애님BP는 `IsSliding()`/`IsOnWall()`을 읽어 표시만 한다.

**실패 흐름 — 매달린 벽이 파괴된다** (이 게임에는 부서지는 문이 실제로 있다)

| 시각 | 서버 | 클라이언트 | 화면 |
|---|---|---|---|
| t=0 | 벽 있음 / 매달림 | 벽 있음 / 매달림 | 정상 |
| t=0 | 문 파괴됨 | 아직 모름 (복제 지연) | 정상 |
| t=0 | 벽 확인 실패 → 매달리기 해제 → 공중 | 아직 매달려 있음 | 잠깐 어긋남 |
| t=+지연 | | 파괴 복제 + 서버 보정 도착 | **떨어짐** |

벽이 부서지고 짧은 지연 뒤 떨어진다. 예측 실패가 아니라 서버가 옳고 클라이언트가 따라가는 정상 동작이므로 **수용한다.**

여기서 나오는 구현 결론: 매달리기 상태는 **매 프레임 벽이 아직 있는지 확인**해야 한다. 이는 추가 비용이 아니다 — 등반하려면 어차피 매 프레임 벽 위치가 필요하다. 불변식 7(탈출 경로)이 이로써 자동 충족된다.

### 반론 1 — "벽점프가 맞다" (사용자, 게임 재확인 후) → **수용, 판정을 뒤집음**

검토자는 프레임 분석(2.30~2.40s 무기 소실)만 보고 "Apex의 벽 오르기는 진입 후 입력을 받지 않는 단일 자동 동작"이라고 판정했다. 사용자가 게임을 직접 다시 확인해 **W 유지 여부로 등반/미끄러짐이 갈리고 점프로 이탈 가능**함을 제시했고, 이는 새로운 근거이므로 판정을 뒤집었다.

수정된 모델: 매달리기는 **상태 1개 + 출구 3개**다. 벽점프는 별개 상태가 아니라 매달리기의 출구 중 하나다.

무기 소실 관찰 자체는 유효하며, **"매달리기 중 사격 불가"의 근거**로 남는다.

#### 🔴 재역전 (2026-08-31, 사용자 결정) — 판정을 **세 번째로** 뒤집는다

**결정: 매달리기·등반·미끄러짐을 전면 폐기하고, 벽 접촉 = 자동 튕김(순간 임펄스)으로 간다.**
사용자 원문: *"벽점프 자동발동으로 매달리기 클라이밍등 벽 관련 사항들은 폐기 자동 튕김으로 진행"*

판정 이력을 지우지 않고 쌓아두는 이유는, 이 축이 **관찰이 아니라 게임필 선호로 갈렸다**는 사실 자체가 근거이기 때문이다:

| 시점 | 판정 | 근거 |
|---|---|---|
| 최초 | 자동 단일 동작 (입력 없음) | 검토자의 프레임 분석 — 2.30~2.40s 무기 소실 |

| **2차 역전 (현행)** | **상태 없음, 순간 임펄스** | **사용자 게임필 결정** — 매달림이 원하는 감각이 아니었다 |

즉 최초 판정의 *"입력을 받지 않는 자동 동작"* 이 결과적으로 현행에 더 가깝다. 다만 도달 경로가 다르다 —
최초 판정은 **등반을 자동으로 하자**였고, 현행은 **등반 자체를 없애자**다.

**설계상 실제로 바뀐 것**
- 발동 = `UpdateCharacterStateBeforeMovement`의 `TryAutoWallJump()`. 조건 = 낙하 중 + 이동 입력이 벽 쪽
  (`WallJumpInputDot`) + 프로브 성공. **점프 키는 관여하지 않는다.**
- 벽점프가 **점프 예산과 완전히 분리**됐다. 종전엔 그랩 시 1회를 환급했는데(`CheckJumpInput`이 `DoJump`보다
  먼저 `CanJump()`를 보기 때문), `DoJump`를 안 타므로 환급도 불필요해졌다. 부작용이던
  *"벽 터치 = 점프 1회 회복"* 도 함께 사라진다.
- **진입 모멘텀 창(0.25s)이 필요 없어졌다.** 매달림이 없으니 진입 속도를 따로 포착할 이유가 없다 —
  접촉 시점의 속도가 곧 접근 속도다. *"빠르게 부딪히면 빠르게 튕긴다"* 는 보상은 더 단순한 형태로 살아남았다.
- **불변식 7(시간 상한/무조건 탈출)이 이 축에서 무의미해졌다.** 지속 상태가 아니면 갇힐 구간이 없다.
  대신 **두 개의 유계**가 그 자리를 대신한다 — 아래.

**⚠️ 쿨다운만으로는 무한 상승을 못 막는다 (값과 무관한 결론)**
사이클당 순 상승 = `Vz·T − ½g·T²` 이고, 이는 `T < 2Vz/g` 인 모든 `T`에서 **양수**다.
`2Vz/g` 는 점프의 전체 체공시간이므로, **반응성 있는 어떤 쿨다운도 사이클당 순증을 남긴다**(두 벽 왕복·같은 벽 반복).
→ 유계 두 개를 **역할을 나눠** 둔다:
- `WallJumpCooldown` = **지터 방지**(한 프레임 뒤 재발동 차단). 상승을 막지 못한다.
- `MaxWallJumpsPerAirborne` = **상승 유계**. 착지만이 리셋한다 — 총 상승이 `N × 사이클당 상승`으로 구조상 유계.

**감수한 리스크 (사용자 명시)**
1. 자동 튕김이 **4인 대형을 깬다** — back-to-back 사각 엄호(`Concept.md §1-C-6` 축1)가 USP인데 의도치 않게
   팀에서 튕겨나갈 수 있다.
2. 1인칭에서 **조준하지 않은 방향으로 튕긴다** — `WallJumpAimBlend`(0.5)가 시선을 절반 섞어 완화하지만,
   자동이라 "시선을 맞출 시간"이 없다.
3. 위 점프 환급 소멸.

완화 장치 = **입력 게이트를 유지한 것**(`WallJumpInputDot`). 벽 쪽으로 미는 중일 때만 발동하므로,
아레나 구조물 사이를 스쳐 달리는 기본 동선에서 오발동이 억제된다. 여기서 과하면 이 값을 올려 원뿔을 좁힌다.

## 구현 결과 (2026-07-28, 1·2단계)

이 결정을 코드로 옮기며 확정·수정된 사항. 결정 자체는 유효하며, 아래는 그 위에서 드러난 사실이다.

**축 1 해소 = 혼합.** 슬라이드는 `MOVE_Walking`을 유지하고 속도/마찰 훅(`GetMaxSpeed`·`GetMaxAcceleration`·`GetMaxBrakingDeceleration`·`CalcVelocity`)만 오버라이드한다. 벽 매달리기는 예정대로 `MOVE_Custom`. 근거 = 슬라이드는 지면 이동이라 `PhysWalking`의 바닥 추종·계단·경사·벽 미끄러짐이 전부 필요한데 `PhysCustom()`은 빈 함수라 그 전부를 재구현해야 한다.

**커스텀 통신 슬롯 = 0개** (문서 본문의 "1개 필요" 예상을 수정). 설계 요구가 "앉기 입력으로 슬라이드 진입"이라, 엔진이 이미 모든 이동 패킷에 싣는 `bWantsToCrouch`로 진입 의도가 충족된다. 파생 상태(슬라이드 여부·경과·진입속도·쿨다운·지상가속 경과)는 `FSavedMove_FPSR`에 **로컬 재생용으로만** 저장되고 전송되지 않는다 → 스톡 CMC 대비 **네트워크 비용 증가 0**. `FLAG_Custom_0~3` 4개가 그대로 남는다.

**구현 중 확인한 엔진 제약 3건** (전부 오버라이드로 처리):
- `CanCrouchInCurrentState()`가 `IsFalling()`도 허용 → 공중 앉기/슬라이드가 되어버림. 지면 전용으로 좁혔고, 부수 효과로 앉은 채 점프하면 자동 기립한다.
- `PhysWalking`이 브레이킹에 `GroundFriction`(8)을 넘기고 `BrakingFrictionFactor`(2)가 곱해져 **실효 마찰 16** → 900→250 cm/s가 약 0.08초에 끝나 슬라이드가 순간 정지로 보인다. 슬라이드 중 마찰을 0으로 대체(등감속 경로 진입).
- `CanAttemptJump()`에 `!bWantsToCrouch`가 있어 **슬라이드 중 점프가 원천 차단**. 크라우치 항만 제외하고 점프 횟수·홀드 규칙은 엔진 그대로 둔다.

**속도 곡선 = 절대값**(사용자 결정 2026-07-28). 배수가 아니라 literal cm/s로 저작한다(`Curve_GroundSpeed` 0→600, `Curve_SlideSpeed` 900→300, `/Game/Config/Character/`). 카드로 `MaxWalkSpeed`가 오르면 `SpeedCurveReferenceSpeed`(=BaseWalkSpeed) 대비 비율로 곡선 전체가 스케일되므로 불변식 3과 충돌하지 않는다. 슬라이드 곡선은 **실제 진입 속도로 상한**을 걸어, 느리게 진입해도 곡선 시작값으로 튀지 않는다. 두 곡선 모두 **null 허용**(등가속/등감속 폴백).

**대시 이관은 아직 하지 않았다.** 폐기만 된 상태이며 재제작은 별도 작업이다.

### 2단계 후속 (2026-07-28, 같은 날 이어서)

**속도 곡선을 절대 cm/s → 정규화(0~1)로 재전환**(사용자 판단). 곱하는 기준은 서기 `MaxWalkSpeed` / 앉기 `MaxWalkSpeedCrouched` / 슬라이드 **진입 속도**. 절대값일 때는 곡선이 기준값과 경쟁해서, 빠르게 진입한 슬라이드가 곡선 시작값으로 깎이는 문제가 있었고 이를 막으려 넣은 분기가 사실상 런타임 정규화였다. 처음부터 정규화하니 그 분기와 `GetSpeedCurveScale()`·기준속도 중복이 함께 사라졌다. 불변식 3(카드 수치 변경)은 기준값이 이미 카드 반영값이라 자동 충족된다.

**엔진 제약 3건 추가 발견**(구현 결과 절의 3건에 이어):
- `ACharacter::CanJumpInternal_Implementation` = `!IsCrouched() && JumpIsAllowedInternal()` — 크라우치 차단이 `CanAttemptJump` 와 **별개로 한 곳 더** 있다. 앞의 것만 풀면 앉기·슬라이드 점프가 여전히 전부 거부된다.
- `Acceleration = GetMaxAcceleration() * InputVector` — 슬라이드 중 최대 가속을 0으로 두면 **입력 방향 정보까지 소실**된다. 입력이 속도에 영향을 주지 않게 하려면 `CalcVelocity` 단계에서 막아야지 가속을 0으로 만들면 안 된다.
- 슬라이드 시간 상한이 곡선 길이보다 짧으면 곡선 후반이 실행되지 않는다. 곡선이 있으면 **곡선 길이가 곧 지속시간**이어야 한다(두 값을 손으로 맞추게 두면 함정).

**경사 슬라이드** = 바닥 법선의 수평 성분(방향=내리막, 크기=sin θ)에 진행 방향을 투영한 값 하나로 내리막/오르막을 모두 표현. 속도(중력 성분 누적)와 시간(곡선 진행 속도 조절) 양쪽에 적용 — 가속만으로는 긴 내리막에서 시간 상한에 걸리고, 시간만으로는 빨라지지 않기 때문이다. 레퍼런스(Apex)도 두 현상이 함께 일어난다.

**진입 상한 분리** — `SlideMaxEntrySpeed`(900)와 `SlideMaxSpeed`(1400). 상한이 하나면 점프-슬라이드 반복이 진입 배수를 매번 재적용해 속도를 계단식으로 쌓는다. 진입 상한은 **올려주기만 하고 깎지 않는다**(내리막 관성을 점프로 옮겨온 경우를 보존).

### 3단계 — 벽 매달리기 (2026-07-28) · ⚰️ **폐기 2026-08-31 — 아래는 경위 보존용이다**

> 🔴 **이 절이 서술하는 구현은 더 이상 존재하지 않는다.** 2026-08-31 사용자 결정(위 「반론 1 → 재역전」)으로
> `CMOVE_WallHang`·`PhysCustom()`·등반/미끄러짐·진입 모멘텀 창·턱 넘김 부스트·복제 프로퍼티 2개
> (`WallYawByte`·`WallSideSign`)·SavedMove 6필드가 전부 삭제됐다. **현행 = 4단계.**
> 지우지 않고 남기는 이유는 여기서 발견된 **엔진 제약 5건**이 앞으로 커스텀 무브먼트 모드를 다시 만들 때
> 그대로 재사용되는 지식이기 때문이다(§6-9 (6)과 같은 원칙).

예정대로 `MOVE_Custom`(`CMOVE_WallHang`) + 직접 구현한 `PhysCustom()`. 결정 자체는 유효하고, 아래는 그 위에서 드러난 사실이다.

**커스텀 통신 슬롯 여전히 0개.** 진입 의도는 이동 입력 방향, 이탈 의도는 `bPressedJump` — 둘 다 엔진이 이미 모든 이동 패킷에 싣는다. 매달리기의 파생 상태 4종(경과·미끄러진 시간·이번 체공의 사용 여부·매달린 벽 법선)은 `FSavedMove_FPSR`에 **로컬 재생용으로만** 저장된다. `FLAG_Custom_0~3` 4개가 그대로 남았다.

**`IsOnWall()`은 무브먼트 모드에서 파생한다** — 별도 복제 bool을 만들지 않았다. 엔진이 `PackNetworkMovementMode`로 이미 모드를 싣고 보정 시 `ApplyNetworkMovementMode`로 복원하므로, 사본을 두면 원본과 어긋날 길만 생긴다. 같은 이유로 `PrepMoveFor`도 모드는 복원하지 않고 **재생이 스스로 도출할 수 없는 것만** 되돌린다.

**조합(move combining)은 매달리는 동안 전면 금지.** 매달리기는 2초 미만이라 조합을 포기해도 대역폭 손해가 없고, 발산 경로 하나를 통째로 없앤다.

> 🔴 **정정 2026-08-31 (G2 레드팀)** — 이 절은 원래 근거를 *"엔진 `CanCombineWith`가 **packed movement mode를 보지 않는다**"* 로 적었다. **틀렸다.** UE 5.7 `CharacterMovementComponent.cpp:12930-12939`가 `StartPackedMovementMode`·`EndPackedMovementMode`를 둘 다 비교한다. 즉 매달리기 구간의 조합은 엔진이 이미 걸러줬고, 커스텀 가드는 **중복 안전장치**였다. 이 절을 보존하는 이유가 "재사용되는 엔진 지식"이므로 오류를 그대로 두면 보존 목적 자체를 배반한다 — 그래서 결론(가드 존재)은 남기고 근거만 정정한다.

**엔진 제약 5건 추가 발견**:
- `CanAttemptJump()`가 `IsMovingOnGround() || IsFalling()`을 요구한다. 매달리기는 둘 다 아니라 **출구 ③(벽점프)이 원천 봉쇄**된다.
- 그걸 풀어도 `JumpIsAllowedInternal()`의 점프 **예산**이 막는다. `JumpMaxCount=1`에서 점프로 벽에 붙으면 예산이 이미 0이다. 진입 시 `JumpCurrentCount = Min(현재, MaxCount-1)`로 **딱 한 번치만** 환급한다 — 0으로 리셋하면 이단점프 카드(카드 확장 A)에서 공중 점프가 순증한다. 환급이 진입 시점인 이유는 `CheckJumpInput`이 `DoJump`보다 **먼저** `CanJump()`를 보기 때문이고, 그 부작용으로 벽점프를 안 하고 미끄러져도 점프 1회가 손에 남는다(체공 1회당 1회로 상한).
- **`ProcessLanded()`를 커스텀 모드에서 직접 부르면 안 된다.** `SetPostLandedPhysics`가 `if (IsFalling())`로 감싸여 있어 모드 전환이 통째로 스킵되고 벽 모드에 갇힌다. 바닥 착지는 `MOVE_Falling`으로 넘겨 다음 틱의 `PhysFalling`이 처리한다.
- `SlideAlongSurface`가 넘긴 `FHitResult&`를 **자기 스윕 결과로 덮어쓴다**. 바닥 판정은 호출 전에 읽어야 한다.
- 벽이 사라진 프레임에 점프하면, 환급된 예산 때문에 "없는 벽에서 수직 점프"가 서버에서도 합법 처리된다. 재프로브 실패 시 그 프레임엔 점프를 만들지 않는다.

**턱 넘김 부스트 = 범위 추가**(사용자 승인). 등반해서 벽을 잃으면 앞·위로 가속한다. 없으면 다 올라가도 캡슐이 벽 위로 올라타지 못해 도로 떨어져 **기능이 성립하지 않는다**. 별도 상태가 아니라 출구 ①의 마무리 속도이므로 "상태 1개"는 유지된다.

**재부착 = 공중 체공 1회당 1번**(`bWallHangConsumed`, 착지 시 해제). 슬라이드식 쿨다운만 두면 등반이 얻는 높이가 쿨다운 동안 잃는 높이보다 커서 임의 높이 벽을 무한 사다리로 오를 수 있다. 착지를 요구하면 구조적으로 불가능해진다.

**진입 모멘텀 = 상태가 아니라 감쇠하는 수치**(1차 PIE 후 사용자 결정). 벽에 붙는 순간 속도를 지우면 매달리기가 "벽돌에 박은" 느낌이 된다. 그렇다고 "빠른 진입"을 별도 상태로 만들면 상태 1개 원칙이 깨진다. 대신 진입 속도를 값 하나(`WallEntryVelocity`)로 저장하고 `WallEntryMomentumDuration` 동안 선형으로 0까지 감쇠시켜 **글라이드 속도와 벽점프 보너스 양쪽을 같은 숫자에서 뽑는다** — 두 효과가 서로 다른 양의 모멘텀을 볼 수 없다. 상태 수는 그대로 1개.

**벽점프 방향 = 시선과 벽 법선의 블렌드**(사용자 결정). 순수 법선은 조작이 아니라 스크립트처럼 느껴지고, 순수 시선은 벽을 마주본 채 점프하면 벽으로 다시 처박힌다. 블렌드 후 **바깥 성분의 하한**(`WallJumpMinOutward`)을 보장해 두 실패를 모두 막는다. 하한 적용은 "모자란 만큼 더하기"가 아니라 단위벡터의 sin·cos로 재구성한다(더하면 정규화 때문에 하한에 못 미친다).

### 자세 전환 블렌딩 (2026-07-29)

**전환은 "상태"가 아니라 가중치 하나다.** 앉기↔서기가 한 프레임에 끝나 시야가 ~70cm 순간이동했다.
해법으로 *전환 중* 이라는 상태를 새로 만들지 않았다 — 그러면 상태 수가 늘고 불변식 7(모든 상태에 탈출 경로)이
전환에도 적용돼야 한다. 대신 **가중치 `StanceBlend`(0~1) 하나**를 무브먼트 컴포넌트가 소유하고,
카메라·속도 상한·(추후)애님BP가 **읽기만** 한다. 상태(`bIsCrouched`·캡슐·슬라이드 진입)는 여전히 즉시 뒤집힌다.

**갱신 위치가 핵심**: `UpdateCharacterStateBeforeMovement`는 `PerformMovement`(소유 클라·서버)뿐 아니라
**`SimulateMovement`(원격 프록시)에서도 호출된다**(엔진 소스 확인). 그래서 한 곳에서 갱신하면 4인 전원의
가중치가 맞는다. 별도 틱을 만들었다면 역할별로 갈라졌을 것이다.

**등속(rate) 고정, 시간은 거리 비례.** 시간을 고정하면 5% 어긋난 걸 되돌리는 데도 꼬박 한 창이 걸려
연타 시 흐물거린다. `FInterpConstantTo`로 완전 전환 = 정확히 `StanceBlendDuration`.

**카메라는 가중치로 눈높이를 계산하지 않는다.** 캡슐 리사이즈의 기준점이 상황마다 다르기 때문이다 —
지상은 발 고정, 공중은 중심 고정, **원격 프록시는 캡슐이 아예 안 움직인다**(엔진에서 그 `MoveComponent`가
`!bClientSimulation` 안에 있음). "발 기준 눈높이"를 계산하면 점프로 자동 기립할 때 절반높이만큼 튄다.
대신 **직전 프레임 위치를 붙잡고 이완**한다 — 튄 거리를 예측하지 않고 재기 때문에 원인이 무엇이든 맞고,
DBNO 관전(`CalcCamera`가 같은 카메라를 씀)에서도 같은 코드가 옳다. **진행도만** 가중치에서 받아
시야·속도·애니메이션이 같은 프레임에 끝난다.

**속도는 결과값을 이완한다.** `Lerp(MaxWalkSpeed, MaxWalkSpeedCrouched, StanceBlend)`로 앞단에서 섞으면
`FindCurveTimeForSpeed`의 정규화 기준이 함께 흔들려, **일어설 때 상한이 300이 아니라 150으로 떨어진다**
(2단계에서 만든 커브 재매핑을 깨뜨린다). 커브 로직은 건드리지 않고 최종 상한만 전환 직전 값에서 이완한다.

**가중치가 물리에 닿는 순간 예측 상태가 된다.** 속도 상한에 쓰이므로 `FSavedMove_FPSR`에 저장하고,
전환 중에는 무브 조합을 금지한다 — 엔진의 `MaxSpeedThresholdCombine`(10)이 60fps에선 우연히 막아주지만
프레임률과 전환 길이에 따라 통과한다. "표현 전용이면 저장 안 함"이라는 경계는 유지하되,
**무엇이 표현 전용인지는 지금 읽는 쪽이 아니라 앞으로 읽을 쪽까지 보고 판단해야 한다.**

**진입은 공중 전용이 사양이다**(사용자 확정 2026-07-29). 구현된 진입 조건은 `IsFalling()` — 체공 상태에서만 벽에 붙는다.

아래 "검증 시나리오"의 정상 흐름이 `슬라이드 → 벽 접촉 → 매달리기`로 적혀 있으나, 그것은 참조 영상을 분해한 서술이지 진입 조건의 명세가 아니었다. 지상 진입을 열면 **벽을 보고 W만 눌러도 계속 붙는** 문제를 막을 조건이 하나 더 필요해지고, 그만큼 "언제 붙는가"가 플레이어에게 불투명해진다. 체공 전용은 **점프라는 명시적 행동을 거쳐야만 벽에 붙는다**는 뜻이라 규칙이 하나로 끝난다. 슬라이드로 벽에 접근하려면 점프로 이어가면 된다.

### 걷기 속도 상한의 단일 기록자 (2026-07-29)

무기별 이동속도(근접/맨손 = 700)를 넣으려다 **`MaxWalkSpeed`에 쓰는 곳이 이미 네 군데**라는 걸 발견했다 —
생성자·`ApplyMoveSpeedMultiplier`·`ApplyDownedLocomotion`의 다운/부활 두 분기. 각자 자기 층만 알고 통째로 덮어쓰므로
서로를 지운다. 장비 층을 다섯 번째 기록자로 추가했다면 *3번 슬롯을 든 채 속도 카드를 먹으면 장비 보너스가 사라지는*
버그가 설계 단계에서 확정된다. **불변식 1을 지킨다는 것은 "상태"만이 아니라 그 상태를 만드는 수치의 기록자도
하나여야 한다는 뜻이다.**

`RefreshWalkSpeedCap()` 하나만 `MaxWalkSpeed`에 쓰고, 나머지는 전부 층을 **밀어넣기만** 한다
(`SetAuthoredBaseWalkSpeed` / `SetLoadoutWalkSpeed` / `SetMoveSpeedMultiplier` / `SetDownedLocomotion`).
합성은 무브먼트 컴포넌트 안에서 끝난다. 층 표는 `PlayerFeel §2-13`.

**기존에 있던 버그가 이 합성만으로 사라졌다** — 예전엔 DBNO로 쓰러진 동안 속도 카드가 적용되면
`ApplyMoveSpeedMultiplier`가 `MaxWalkSpeed`를 0에서 되살려 쓰러진 플레이어가 움직였다.
다운 층이 합성의 일부가 되면서 구조적으로 불가능해졌다.

**프로퍼티는 옮기지 않았다.** `BaseWalkSpeed`를 캐릭터에서 무브먼트 컴포넌트로 이관하는 쪽이 "소유"에 더 가까워
보이지만, 클래스 간 이동은 BP에 저장된 오버라이드 값을 잃고 조준 흔들림의 정규화 기준·GE 참조까지 함께 흔든다.
그리고 **단일 기록자를 얻는 데 필요한 조건이 아니다** — 저작값이 어디에 적혀 있든 밀어넣기만 하면 된다.
소유권 정리와 프로퍼티 이사를 같은 것으로 묶지 않는다.

**장비 속도는 예측하지 않는다.** 슬롯 전환은 서버 권위(`ServerEquipSlot` RPC)이고, 클라가 입력 시점에 선적용하면
*서버가 장착을 거절했을 때 아무것도 복제되지 않아* 클라가 빠른 속도에 영구 고착된다(`CurrentSlotIndex`가 안 바뀌니
`OnRep`도 안 온다). 대신 서버 `EquipSlot`과 클라 `OnRep`에서만 적용하고 1 RTT 지연을 받아들인다 —
걷기 상한은 가속 램프가 *접근하는* 값이라 46ms 지연이 체감되지 않기 때문이다.

이 판단이 성립하려면 **슬라이드가 장착 시점에 의존하지 않아야 한다**. 진입 임펄스는
`min(max(V, min(V×1.5, SlideMaxEntrySpeed)), SlideMaxSpeed)`로 *그 순간 속도 V*에서 파생되므로,
상한을 900→1000으로 한 번 올리면 걷기 600은 900 그대로·걷기 700은 1000이 된다.
**무기 DA에 슬라이드 값을 따로 두지 않는 이유가 여기 있다** — 그렇게 했다면 진입 속도가 "장착이 언제 반영됐나"에
좌우돼, 3번을 누른 직후 앉으면 가끔 슬라이드가 덜 나가는 *재현 안 되는* 버그가 됐을 것이다.
V는 이미 예측·보정되는 이동 상태라 클라와 서버가 항상 같은 값을 본다.

### 에어 스트레이프 (2026-07-29)

**공중 이동은 새 상태가 아니라 낙하의 가속 규칙 교체다.** "체공 조작이 안 된다"에서 출발했지만 목표는
**에어 스트레이프** — 속도를 잃지 않고 공중에서 도는 기술이었다. 새 이동 상태를 만들지 않았으므로
불변식(상태 주인 하나)과 비목표(카드가 새 상태를 추가하지 않는다)는 그대로다.

**엔진 기본 모델로는 성립하지 않는다.** `CalcVelocity`는 속도 벡터 **전체**를 입력 쪽으로 가속하고 총합을
클램프한다. 그래서 진행 방향과 어긋나는 입력은 속도를 **깎는다** — 가속을 아무리 올려도 "속도를 유지한 채
회전"이 나오지 않는다. 이건 튜닝 문제가 아니라 **알고리즘 문제**였고, 처음 세운 "공중 가속을 올린다" 안은
그래서 폐기했다.

**채택 = Quake 계열.** 입력 방향으로 **이미 가고 있지 않은 만큼만** 더한다
(`AddSpeed = WishSpeed − dot(v, WishDir)`). 진행 방향에 수직인 작은 벡터를 더하면 크기는 거의 그대로 방향만
회전하고(|v+εp|≈|v|), 수직일 때 예산이 가득 남아 계속 돈다. 반대로 진행 방향으로 입력하면 예산이 0이라
공중에서 W로는 아무것도 얻지 못한다. **이 비대칭이 기술의 전부이며, 그래서 "공짜 회전, 공짜 속도는 없음"이 된다.**

**난이도는 값 하나로 정한다**(사용자 결정 = 대중적). `AirStrafeWishSpeed`는 곧 "마우스를 돌리지 않고
방향키만 유지했을 때 도는 각도"다 — 기술을 못 해도 기본 회전은 되고, 마우스를 함께 돌리면 더 간다.
숙련이 **요구되지 않되 보상되는** 구조.

**엔진 확장 지점의 함정 2건**(Codex 검토):
- `GetFallingLateralAcceleration()`이 돌려주는 벡터는 방향 전달용만이 아니다. 벽에 부딪힌 뒤
  `LimitAirControl()`이 그 **크기를 재가속 값으로 그대로 쓴다.** 원시 `Acceleration`을 넘기면 벽을 스치는
  것만으로 가속이 몇 배로 뛴다.
- `CalcVelocity`는 한 프레임에 여러 번 불린다(서브스텝 + 충돌 후 재호출). 알고리즘이 상태를 갖지 않고
  `AddSpeed`가 방향별 총속도를 묶기 때문에 반복 호출에 **수렴**한다 — 이 성질에 의존하므로 프레임당 1회를
  가정하는 코드를 넣으면 깨진다.

**최고 속도를 하나로 통일했다.** `SlideMaxSpeed`·`AirStrafeMaxSpeed`·`WallJumpMaxSpeed` = 1400.
셋이 다르면 "슬라이드로 번 속도가 벽점프에서 사라지는" 식의 설명 불가능한 손실이 생긴다. 상한을 낮춰야 할
때도 셋을 함께 움직인다.

**공중에서 `MaxWalkSpeed` 상한이 사라진 것은 부작용이 아니라 전제다.** 걷기 속도를 못 넘으면 스트레이프로
속도를 벌 수 없다. 대신 `AirStrafeMaxSpeed`가 그 자리를 대신하고, **들고 온 속도는 클램프가 깎지 않는다**
— 줄어드는 유일한 경로는 플레이어가 진행 반대 방향으로 입력하는 것(= 공중 브레이크)이다.

### 카메라 FOV의 단일 기록자 (2026-08-05)

슬라이드 중 화각을 넓히려다(`+5도`, 주변이 더 보이게) **FOV를 쓰는 코드가 무기 발사 컴포넌트 틱 안**에 있는 걸
발견했다. 거기에 슬라이드를 얹으면 무기 컴포넌트가 `IsSliding()`을 묻게 되는데, 그건 **불변식 4**("사격/ADS는
이동 상태를 모른다")를 정면으로 깬다. 위 `걷기 속도 상한의 단일 기록자`와 같은 결론이 카메라에서 한 번 더 나온다 —
**층이 여럿인 수치는 기록자가 하나여야 한다.** FOV의 층은 셋이다: 설정 기준값 · 자세 보정(슬라이드) · 무기의 ADS/스코프 줌.

`AFPSRCharacter::UpdateCameraFieldOfView()` 하나만 `FieldOfView`에 쓴다. 무기는 **ADS 의도(`bIsAiming`)와
스탯의 ADS 수치만** 제공하고, 슬라이드 여부는 캐릭터가 무브먼트 컴포넌트에 **묻는다**(불변식 1 — 읽기만).
카메라 **위치**가 이미 `UpdateStanceCamera` 한 곳에서만 조립되는 것과 같은 규칙이고, 같은 `Tick`에 나란히 있다.

**옮기면서 버그 하나가 같이 사라졌다** — 옛 코드는 장착 무기가 없으면 틱이 먼저 `return`해서 **맨손일 때 FOV가
아예 갱신되지 않았다.** 캐릭터 `Tick`은 무기와 무관하게 돈다.

**보정은 더하지 않고 대체된다.** 조준 중에는 `ResolveADSTargetFOV`가 힙 목표값을 통째로 무기/사이트의 ADS FOV로
바꾼다. 더하는 쪽을 택했다면 스코프(FOV 30도 근처)에서 5도가 **17% 배율 변화**로 보인다 — 자세 보정이 조준경
배율처럼 읽히면 안 된다.

**기준값은 절대값이 아니라 참조점이다.** 옛 `DefaultFOV`는 첫 틱에 카메라에서 한 번 훔쳐다 캐시했으므로 나중에
설정 메뉴가 기준 FOV를 바꿔도 낡은 값으로 남았다. `BaseFieldOfView` + `SetBaseFieldOfView()`로 바꾸고 모든 보정을
그 위의 **차이값**으로 표현했다 — 그래서 FOV 슬라이더가 붙을 때 이 파일들은 손대지 않아도 된다.
허용 범위(`BaseFieldOfViewRange`)도 캐릭터에 둔다. 슬라이더가 자기 숫자를 따로 들면 **클램프가 조용히 지워 버리는
값을 슬라이더가 제시**하게 된다.

**기각안 — 무브먼트의 `GetSlideBlend()`(0→1, `SlideBlendDuration`)를 FOV 알파로 재사용.** 시계가 하나로 묶여
포즈와 카메라가 같은 프레임에 끝나는 장점이 있다. 그런데 그 값은 **애니 포즈용으로 고른 0.12초**라, 나중에 포즈
블렌드를 튜닝하면 카메라 느낌이 같이 흔들린다. 카메라는 자기 속도(`SlideFieldOfViewInterpSpeed`)를 갖는다.

### 4단계 — 벽 = 순간 임펄스 (2026-08-31) · **현행**

3단계를 통째로 걷어내고 `TryAutoWallJump()` 하나로 대체했다. 3단계 대비 실제로 달라진 것:

**커스텀 통신 슬롯 여전히 0개, 그리고 이제 복제 프로퍼티도 2개 줄었다.** 3단계는 프록시에 벽 포즈를 알리려고
`WallYawByte`·`WallSideSign`을 복제했다. 임펄스에는 알릴 포즈가 없다 — 프록시가 봐야 하는 것은 **결과 속도**이고
그건 이동 복제가 이미 나른다. `FLAG_Custom_0~3` 4개는 여전히 전부 미사용이다.

**SavedMove 6필드 → 2필드.** 되돌려야 할 것이 "매달린 벽·두 타이머·사용 여부"에서 **두 유계**로 줄었다.
`PrepMoveFor`의 원칙(*"재생이 스스로 도출할 수 없는 것만 복원"*)은 그대로다 — 쿨다운·카운터는 **이력**이라
재생이 도출할 수 없고, 복원하지 않으면 재생이 서버가 시뮬레이션하지 않은 두 번째 발사를 만들어낸다.

**🔴 조합(move combining) 금지가 여전히 필요하다 — 이유가 바뀌었다.**
3단계에선 엔진이 **packed movement mode를 비교**해(`CharacterMovementComponent.cpp:12930-12939`) 매달리기 구간의
조합을 이미 걸러줬다 — 커스텀 가드는 중복 안전장치였다. 임펄스에는 **모드 변화 자체가 없다**(양쪽 다 Falling).
그래서 그 보호가 사라지고, **커스텀 가드가 이제 유일한 방어선이 된다**: 엔진 검사에서 자동 벽점프를 걸러낼 수 있는
항목은 **입력 엣지**(`bPressedJump`·압축플래그·가속 방향)뿐인데 자동 발동에는 **엣지가 하나도 없다**. 낙하 중, 모드는 양쪽 다 Falling, 이동 입력은 변화 없음 —
게다가 트리거가 *"입력을 벽 쪽으로 유지"* 를 요구하므로 **가속 방향 일치 검사를 오히려 잘 통과한다**.
(슬라이드는 `bWantsToCrouch` 엣지가 있어 엔진이 걸러준다. 벽점프엔 그 보호가 없다.)
그리고 `FSavedMove_Character::CombineWith`는 캐릭터를 이전 이동 시작 지점으로 되돌리면서 **커스텀 필드는
복원하지 않고 `PrepMoveFor`도 부르지 않는다** → 캐릭터는 발사 전으로, 유계는 발사 후로 갈라지고,
재시뮬이 이미 그려진 점프를 거부해 **스냅백**이 난다. 조합은 클라 fps가 송신율을 넘으면 상시 일어난다.
→ 신설 2필드에 대한 **대체 가드**를 `CanCombineWith`에 둔다(스탠스 가드와 동일 패턴·동일 비용 논거).

**엔진 제약 5건 중 3건이 해소됐다** — 원인이 사라졌기 때문이다: `CanAttemptJump` 봉쇄·점프 예산 환급·
"벽이 사라진 프레임의 유령 점프"는 전부 **`DoJump` 경로를 타지 않게 되면서** 성립하지 않는다.
나머지 2건(`ProcessLanded` / `SlideAlongSurface`)은 커스텀 모드 일반의 지식이라 위 3단계에 그대로 남는다.

**엔진 `DoJump`는 대입이 아니라 `Max`다** (`CharacterMovementComponent.cpp` — `Velocity.Z = FMath::Max(Velocity.Z, JumpZVelocity)`).
3단계에선 차이가 없었다(매달림이 이미 상승을 죽인 뒤에 점프가 읽었다). **4단계에선 다르다** — 임펄스는
**상승 중에도** 발동하므로(슬라이드 점프로 벽을 스치는 경우) 대입이면 플레이어가 이미 벌어둔 상승을 깎는다.
그래서 `WallJumpUpSpeed == 0`(기본)일 때 `Max`를 쓴다. 이는 *"실려온 속도를 깎지 않는다"* 는
이 컴포넌트의 일관 규약(`SlideMaxEntrySpeed`·`AirStrafeMaxSpeed`)과도 정합한다.

**유계 2개의 역할 분리**는 위 「재역전」의 부등식 참조. 산술이 순수해서 **월드리스 테스트로 검증**한다
(`FPSRWallJumpBoundsTest.cpp`, `FPSRWallJumpBounds` 네임스페이스). 발사 자체는 캡슐·레벨·스윕이 필요해
자동 테스트 범위 밖이고, 그 부분은 PIE 스모크가 담당한다.
