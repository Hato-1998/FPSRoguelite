# 설계 근거 — 왜 이 형태인가 (규칙마다 낳은 실사고)

프로토콜을 다른 프로젝트에 맞게 손볼 때, 규칙을 지우기 전에 **그 규칙이 막고 있는 사고**를 확인하는 표다. 원형 = FPSRoguelite `Docs/SSOT/Workflow.md` §6-9 (2026-08-07 도입, 08-11·08-26·09-05 개정).

| 규칙 | 낳은 사고 / 근거 |
|---|---|
| 작업 상태 SSOT를 git 밖(Notion)에 둔다 | git 문서는 브랜치-로컬 → 머지 전엔 병렬 세션이 서로 안 보인다. 실사고: 다른 세션이 phase 브랜치를 체크아웃해 내 커밋이 그 브랜치에 얹힘. 공유 가변 상태는 git 밖에 산다 |
| 하드 게이트(MCP 미연결 = 착수 금지, 우회 권한은 사용자만) | 게이트가 "권고"면 세션이 바쁠 때 건너뛴다. 예외를 사용자에게만 두어야 에이전트가 스스로 예외를 만들지 않는다 |
| `PROGRESS.md`는 포인터만 | 문서와 보드에 같은 내용이 있으면 둘이 갈라진다(이중 SSOT). 포인터는 SessionStart 훅이 매 세션 출력해 게이트를 상기시킨다 |
| 보드 I/O는 서브에이전트 단일 창구(`/board`) | 클레임 7단계+마감 5단계를 메인이 직접 밟으면 ①빠뜨리고 ②조회 덤프가 메인 컨텍스트를 먹고 ③SQL 한도 관리 주체가 없다 |
| 에이전트는 "추가만"(신규 행·로그 append), 속성 변경은 메인 | 상태·담당·우선순위를 서브에이전트가 바꾸면 메인이 모르는 상태 전이가 생긴다. 판정 주체 = 메인, 조사 주체 = 에이전트 |
| 가드 훅이 `command != insert_content`를 deny | 도구 화이트리스트로는 못 막는다 — `notion-update-page` 하나가 append와 덮어쓰기를 `command` 인자로 가른다. 훅 입력 파싱 실패 시 `ask`(deny도 allow도 아님) |
| 훅 배선은 클론마다 수동 | `.claude/settings.json`은 gitignore(머신 로컬). 스크립트만 커밋된다. 배선 없는 클론에선 경계가 규칙일 뿐 — 설치 보고에 반드시 적는다 |
| 에이전트 정의는 절차를 복제하지 않고 프로토콜 문서를 읽는다 | 복제하면 개정 때 어긋난다. 실사고(2026-08-11): 문서에 마일스톤 기입 의무를 넣었는데 에이전트 파일의 "릴레이션은 선행작업만 쓴다" 줄이 신설 규칙의 반대를 지시 → 의무를 늘리는 개정은 세 파일 같은 커밋 |
| 전수 SQL은 세션당 1~2회 | Notion MCP 무료 플랜 호출 한도. 표적 조회(`notion-search`)·행 fetch는 무제한이라 2회차부터 그것만 |
| 전수 SQL이 `검증중`·`보류`·`완료`·`폐기`를 뺀다 | `검증중` = 사람이 직접 확인해야 끝나는 것이라 에이전트가 집을 작업이 아님. 넣으면 시작 목록만 길어진다(17→29건). **단 전수 백필엔 이 SQL을 기준 삼지 말 것** — 검증중 12행을 놓칠 뻔함 |
| 듀얼 릴레이션은 한쪽만 만들고 한쪽만 쓴다 | 양쪽을 각각 ADD하면 독립 단방향 2개(후행 전부 null 실사고). 쓸 때도 `선행작업`만 — 둘 다 쓰면 어긋남 |
| 한글 select 값은 리터럴 | `미듐`을 유니코드 이스케이프로 쓰다 두 번 틀림(듬/듄) |
| 크리티컬 = 사용자 전용 | 에이전트가 자기 작업을 크리티컬로 올리면 우선순위 축이 무너진다. 승격/강등 제안은 로그로만 |
| 완료 vs 폐기 분리 | 폐기 건을 완료로 넣으면 "완료 = 실제로 한 것"으로 셀 수 없다. 폐기는 사유 본문 필수, 되살릴 땐 신규 행(코드가 달라져 스펙을 다시 써야 함) |
| 완료·폐기 행은 지우지 않는다(아카이브 뷰) | 활성 SQL이 제외하므로 비용 0. 폐기를 지우면 "왜 안 했는지"가 사라져 같은 걸 다시 착수한다 |
| 클레임 직후 재조회(경합 확인) | Notion에 트랜잭션이 없다. 두 세션이 동시에 같은 행을 잡을 수 있다 |
| `크기` S/M/L/XL은 상호배타, XL은 클레임 금지 | 종전 정의(M=2~3세션 / L=여러 세션+검증)는 겹치고 "+검증"은 모든 작업의 공통 의무라 변별력 0. XL을 쪼개지 않고 집으면 완료 판정이 불가능 |
| 마일스톤 page ID를 문서에 정적으로 박는다 | 신규 행에 `마일스톤`을 채우라면서 마일스톤 DB 조회는 금지 → 자기모순. 마일스톤은 불변 집합이라 1회 박으면 양쪽이 성립 |
| 마일스톤 = 순서, 우선순위 = 마일스톤 안의 순서. 크리티컬만 인터럽트 | 두 축을 섞으면 뒤 슬라이스 작업이 우선순위만 높다고 먼저 집힌다. 개시 규칙: M(n) Exit 전 M(n+1) 착수 금지, 예외 3종은 로그에 사유 |
| 마일스톤 미배정은 비워 두고 보고 | 임의 배정은 착수 순서를 틀어놓는다. 감사 D8이 무보고 미배정 누적을 잡는다 |
| 완료·폐기 행에 마일스톤 소급 배정 안 함 | 얻는 것이 과거 그래프뿐 |
| 감사 D1~D8은 git이 1차 진실 | 보드는 stale해질 수 있다. 감사는 고치지 않고 보고+인자 인계만. git 리포가 없으면(원격 세션) 성립하지 않음 |
| 트렁크 기반 전환 후 D1/D2/D4 기준 변경 | 전 행이 `main`이면 "브랜치 존재"가 판별력 0 → `담당`·커밋 scope 기준. 머지 커밋이 없으면 `merge:` 기준 D4는 영원히 안 발화 → scope ID 대조 |
| 상시 폴링(크론) 미채택 | 실측: 로컬 스케줄러는 앱이 켜져 있어야 돌고, 무인 실행은 권한 프롬프트에서 정지. 세션 시작 1회+커밋 전 1회 무조건 부르므로 폴링이 더해 주는 게 없다. **다시 제안하지 말 것** |
| 새 에이전트 정의는 세션 시작 때만 로드 | 설치 직후 그 세션에서 `Agent type not found`는 정상. 검증은 다음 세션 |

## 원형과 달리 스킬이 선택형으로 돌린 것

| 요소 | 원형에서의 의미 | 왜 선택형인가 |
|---|---|---|
| `추천모델` 열 (Fable/Opus) | "무거운 2게이트(플랜·머지 레드팀)를 타는 코어 갈래인가" — 기준 SSOT는 별도 모델 정책 문서 | 모델 정책은 프로젝트마다 다르다. 열은 "게이트 갈래"로 일반화, 이름·옵션은 부트스트랩 입력 |
| 마일스톤 DB + `마일스톤` relation | 출시(EA→정식)까지의 큰 묶음 순서 축 | 순서 축이 없는 프로젝트(라이브러리·유틸)에선 유지비만 든다 |
| `성격`·`동결선` 열 | 마일스톤의 성질(기반/수직슬라이스/출시)·콘텐츠 동결선 | 게임 출시 파이프라인 전용 어휘 |
| `영역` 옵션 | 게임 시스템 경계 | 병렬 충돌 감지용이라 그 프로젝트의 모듈 경계여야 의미가 있다 |
| 감사 D2/D4의 커밋 scope 대조 | `type(scope): …` scope = 유닛 ID 관례 | 관례가 없는 리포에선 대조 불가 → "수동" 표기 |
