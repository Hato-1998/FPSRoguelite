# 워크스페이스 구조 — 보드 밖의 노션 층 (읽는 문서 · 결정 기록 · 논의)

> 작업 보드가 **"지금 누가 무엇을 하는가"** 를 담는다면, 이 층은 **"왜 그렇게 하기로 했는가"** 를 담는다.
> 설치 순서는 `SKILL.md` §2 를 따르고, 이 문서는 **무엇을 만들지(DDL·본문)** 와 **왜 그 형태인지**를 준다.

---

## A. 먼저 — 이 층이 무너지는 방식 (원형 실사고, 2026-09-07~09)

원형 프로젝트는 이 층을 만들면서 **"SSOT 를 노션으로 역전한다"** 로 출발했다. repo 의 `.md` 41개를 노션에 **축자 사본**으로 올렸고, 이틀 뒤 사용자 결정으로 **전부 폐기**했다.

기각 사유가 이 문서 전체의 전제다:

> **같은 내용이 두 곳에 있으면 한쪽이 반드시 낡는다. 그리고 옮겨서 새로 얻는 정보가 0이었다.**
> 41개를 옮긴 것은 "이중 SSOT 를 41번 만든 것" 이었다.

그래서 현행 형태는 **역전이 아니라 분업**이다. 아래 표가 이 층의 헌법이고, 충돌하면 이 표가 이긴다.

| 대상 | 정본 | 노션에 있는 것 |
|---|---|---|
| 수치 · 스키마 · 클래스명 · 설계 명세 | **repo** | **색인만** — 제목 · 한 줄 목적 · repo 경로 · 주제 링크 |
| 아키텍처 결정 **원문** | **repo** | 요약(배경·결정·근거·기각안·영향) + **대체 관계**(repo 가 못 하던 것) |
| 기획 · 아트의 「왜 · 무엇」 | **노션 주제 페이지** | 목적 · 경위 · 뒤집힌 결정 · 그림 |
| 작업 현황 | **노션 작업 보드** | 프로토콜 문서 (1)~(8) |
| 워크플로 · 에이전트 프로토콜 | **repo** 프로토콜 문서 | 요약 + 링크 |
| 작업 이력 · 함정 사전 | **repo** | 이관하지 않는다 |

🔑 **노션이 repo 보다 나은 딱 두 가지**만 노션에 원본으로 둔다.
1. **결정 사이의 관계** — "이 결정이 저 결정을 부분 대체한다" 는 relation 이라야 표현된다. 마크다운으로는 매번 손으로 고쳐야 하고 반드시 낡는다.
2. **사람이 읽고 싶은 서술** — 기획·아트의 「왜」는 그림과 함께 읽힌다.

⚠️ **문서 DB 행은 「색인」이지 본문이 아니다.** 거기서 수치를 읽지 말고 행의 `원본경로` 가 가리키는 repo 파일을 열 것. 이 규칙을 안 박아 두면 세션이 색인의 낡은 요약을 근거로 코드를 고친다.

## B. 분야 페이지 4개 — `notion-create-pages` (parent = 허브)

허브 아래 **분야별 진입점** 4개. 각각이 그 분야의 「왜·무엇」 주제 페이지들의 부모가 된다.

| 페이지 | 아이콘 | 담는 것 |
|---|---|---|
| 기획 | 🎲 | 게임/제품이 무엇을 하려는가 · 뒤집힌 기획 결정 |
| 아트 | 🎨 | 아트 방향 · 레퍼런스 · 저작 규칙 |
| 프로그래밍 | ⚙️ | 구조 개요 · 모듈 지도(명세 원문은 repo) |
| **AI · 워크플로** | 🤖 | **형식이 나머지 셋과 다르다 — 아래** |

### B-1. AI 분야 페이지는 형식이 다르다 (원형 사용자 결정)

다른 셋은 사람이 읽는 산문이지만, AI 페이지는 **첫 화면만 사람용**이고 하위 문서는 **AI 작업자가 세션 시작에 그대로 따라 하는 절차서**다.

첫 화면(사람용)에 담을 것:
- 이 구역이 왜 있는가 — *"세션은 기억이 없어서 매번 처음부터 들어온다. 「이 프로젝트에서 일하는 법」을 글로 못박지 않으면 세션마다 다르게 판단하고, 그 편차가 그대로 코드에 쌓인다."*
- **사람이 알아야 결과를 이해할 수 있는 규칙만** 표로: 보드 클레임 없이 시작 안 함 · 검증 없이 완료 안 함 · 이름 바꾸지 않음 · 손댈 값과 안 댈 값의 경계 · 금칙(강제푸시·훅우회·시크릿커밋)
- 모델 배분 요약 — 사람이 "왜 이 작업은 오래 걸리나" 를 이해하는 근거
- **위 §A 역할 분담 표** — ⚠️ 원형에서 *가장 자주 틀린 자리*다. 반전 경위(축자 사본 41개 → 폐기)를 한 줄로 남길 것.

하위 문서 3종(AI 가 읽는다):

| 문서 | 무엇 | 언제 |
|---|---|---|
| **온보딩 · 착수 절차** | 프로젝트 한 줄 요약 · repo 지도 · 착수 체크리스트 · 절대 규칙 전문 | 세션 시작 |
| **함정 사전** | 증상 → 원인 → 처방 | 막혔을 때 |
| **보드 스냅샷 설치** | 사람이 1회 하는 토큰 설치(프로토콜 문서 (10)) | 설치 시 1회 |

🔒 **하위 문서에 규칙 원문을 복제하지 말 것.** 규칙의 정본은 repo 프로토콜 문서이고, 여기는 요약 + 링크다. 어긋나면 repo 가 옳다는 문장을 각 문서에 박아라.

## C. 문서 DB — `notion-create-database` (parent = 허브, title `문서`)

repo 문서의 **색인**. 본문을 옮기는 곳이 아니다(§A).

```sql
CREATE TABLE (
  "제목"     TITLE,
  "문서상태" SELECT('초안':gray, '검토중':yellow, '확정':green, '폐기':default) COMMENT '작업 보드의 상태와 뜻이 달라 이름을 갈랐다',
  "분야"     MULTI_SELECT('기획':pink, '아트':orange, '프로그래밍':blue, 'AI·워크플로':purple),
  "원본경로" RICH_TEXT COMMENT 'repo 경로 — 이 행이 가리키는 진짜 문서',
  "코드경로" RICH_TEXT COMMENT '관련 모듈·파일. 프로그래밍 문서는 필수',
  "담당"     RICH_TEXT COMMENT '작업 보드와 동일 표기'
)
```

🪤 **`문서상태`·`논의상태` 처럼 이름을 갈라 쓰는 것은 의도다.** 작업 보드에도 `상태` 가 있어서, 같은 이름을 쓰면 다중 DB 조회나 사람의 눈에서 뜻이 섞인다.

## D. 결정 기록 DB — `notion-create-database` (parent = 허브, title `결정 기록`)

아키텍처 결정의 **읽는 판**. 원문은 repo(`Docs/Architecture/*.md` 등)에 남는다.

```sql
CREATE TABLE (
  "결정"         TITLE,
  "ADR번호"      RICH_TEXT COMMENT 'repo ADR 번호. 코드 주석·문서가 이 번호로 참조한다',
  "결정상태"     SELECT('유효':green, '부분대체':yellow, '대체됨':default),
  "되돌리기비용" SELECT('저렴':green, '보통':yellow, '비쌈':red),
  "분야"         MULTI_SELECT('기획':pink, '아트':orange, '프로그래밍':blue, 'AI·워크플로':purple),
  "날짜"         DATE
)
```

🔑 **`결정상태` 가 3단계인 이유** — ADR 은 **부분 대체**를 쓴다(예: 0010 의 D2·D5 만 0011 이 대체). 유효/대체됨 2단계로는 그게 표현이 안 되어, 세션이 "대체됨" 을 보고 문서 전체를 버린다.

🔑 **`되돌리기비용`** 은 repo ADR 에 없던 축이다 — 나중에 뒤집을지 고민할 때 가장 먼저 묻는 값인데 원문에는 안 적혀 있었다. 이런 **노션이 더 잘하는 축**만 추가한다(원문 복제 금지).

## E. 아이디어 · 논의 DB — `notion-create-database` (parent = 허브, title `아이디어·논의`)

아직 작업이 아닌 것. 보드에 `백로그` 로 넣으면 보드가 불어나므로 갈라 둔다.

```sql
CREATE TABLE (
  "제목"     TITLE,
  "논의상태" SELECT('아이디어':gray, '검토중':yellow, '채택':green, '보류':brown, '기각':red),
  "분야"     MULTI_SELECT('기획':pink, '아트':orange, '프로그래밍':blue, 'AI·워크플로':purple),
  "제안자"   RICH_TEXT
)
```

🔑 **`기각` 을 지우지 말고 남긴다** — 왜 안 하기로 했는지가 사라지면 같은 것을 다시 논의한다(작업 보드의 `폐기` 와 같은 이유).

## F. 릴레이션 배선 — `notion-update-data-source`

**DB 3개를 먼저 다 만든 뒤** 배선한다(상대 DS ID 가 있어야 한다). 생성 순서 = 작업 보드 → 결정 기록 → 문서 → 아이디어·논의.

```sql
-- 결정 기록 쪽
ADD COLUMN "관련작업"   RELATION('<TASKS_DS uuid>',    DUAL '관련결정')
; ADD COLUMN "대체결정" RELATION('<DECISIONS_DS uuid>', DUAL '대체된결정')

-- 문서 쪽
ADD COLUMN "관련작업"   RELATION('<TASKS_DS uuid>',     DUAL '관련문서')
; ADD COLUMN "관련결정" RELATION('<DECISIONS_DS uuid>', DUAL '관련문서')

-- 아이디어·논의 쪽
ADD COLUMN "채택작업"   RELATION('<TASKS_DS uuid>',     DUAL '관련아이디어')
; ADD COLUMN "채택결정" RELATION('<DECISIONS_DS uuid>', DUAL '관련아이디어')
```

🪤 **반대편 열을 직접 ADD 하지 말 것** — `DUAL` 이 자동 생성한다. 각각 만들면 서로 모르는 단방향 2개가 되고 **겉보기로는 구분되지 않는다**(원형 실사고). 되읽기에서 양쪽 `propertyUrl` 이 같은 쌍인지 본다.

🪤 **`ADD COLUMN` 으로 DUAL 을 만들면 한 번에 양쪽이 생긴다 — 두 번 부르면 중복쌍이 생긴다.** 원형에서 실제로 밟고 `DROP` 으로 정리했다.

⚠️ 위 DUAL 이름(`관련결정`·`관련문서`·`관련아이디어`)이 **작업 보드에 새 열로 생긴다.** 작업 보드의 열 수가 늘어나는 것이니 프로토콜 문서 (2) 의 조회 SELECT 에는 **넣지 않는다**(세션이 쓰지 않는 열이다).

## G. `영역` → `분야` 매핑 (보드와 이 층을 잇는 규칙)

작업 보드의 `영역`(세밀)에서 `분야`(4분류)를 **기계적으로** 도출한다. 사람이 매번 고르면 어긋난다.

| `영역` 예 | `분야` |
|---|---|
| 기획 · 밸런스 · 런플로우 · 콘텐츠 설계 | 기획 |
| 아트 · VFX · 오디오 · UI 스킨 | 아트 |
| 코드 · 성능 · 네트워크 · 툴 · 빌드 | 프로그래밍 |
| 문서 · PM · 워크플로 | AI·워크플로 |

- 한 행이 둘 이상에 걸치면 **둘 다** 넣는다.
- **완료 · 폐기 행은 백필하지 않는다** — 활성 행만. 과거 그래프를 얻자고 수백 행을 쓰는 값이 없다.

## H. 되읽기 검증 (필수)

DB 3개를 `notion-fetch` 로 다시 받아:

1. `분야` 옵션 4개의 **철자**가 세 DB에서 동일한가 — 특히 `AI·워크플로` 의 가운뎃점(`·`, U+00B7). 다르면 다중 DB 뷰에서 갈라진다.
2. `문서상태`·`논의상태` 가 `상태` 로 잘못 만들어지지 않았는가.
3. 릴레이션 반대편이 **자동으로** 생겼는가(작업 보드에 `관련결정`·`관련문서`·`관련아이디어`, 결정 기록에 `대체된결정`).
4. 테스트 행 1개씩을 만들어 서로 연결한 뒤 **반대편에서 보이는지** 확인한다. 확인 후 사용자에게 알리고 상태를 `폐기`/`기각` 으로 둔다(삭제는 사용자 몫).

⚠️ **다중 데이터소스 SQL 은 플랜에 따라 거부된다** — DB 하나씩 조회할 것.
